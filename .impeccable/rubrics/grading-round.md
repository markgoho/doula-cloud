# A grading round

One round scores one screen against its rubric (`clients-list.md` and `invoices-list.md` are the models). It is what turns "the critique says 34" into a number that means the jobs work.

## Before the baseline

1. **Seed first.** `dev:full`'s demo Practice holds a realistic book for this screen: enough rows to page, sort and scroll, and one row in every state the screen can show. Extend `app/scripts/demo-practice.ts` until it does. A round graded on three rows measures nothing. A seeded act has its own effects (naming a Doula on a Visit attaches her to the Engagement), so the seed build's brief lists the sibling screens' numbers that must not move, and the agent reads them on the rendered page before and after: the Schedule's first seed put five Doulas on one Client and the Clients list scrolled sideways.
2. **Read the siblings first.** Open every screen already climbed (the Clients list, the Invoices list) and start from its `FilterBar` and `DataTable` usage, its control sizes and its wording for a shared state. Where this screen must differ, write the reason in the surface brief. "Unlike the Clients list" was the Invoices climb's last lost point for four rounds.
3. **Name the category baseline.** Before the rubric is drafted, one Opus agent lists what a screen of this kind has taught its readers to expect, from Stripe Dashboard, Linear, the GOV.UK and MOJ design systems and the tools the personas already use, and says where each expectation was learned. The claim about each expectation is read, never remembered: the agent reads the product's own documentation page for each claim and quotes it with its address, and a claim it could not read is marked unread. No "Declined" may rest on an unread claim. The first baseline declined a sort on three lists on a remembered claim that Stripe's lists are fixed in order; Linear's and Stripe's own pages say a reader chooses the order, and the decline was reversed the same day (#2869). It covers at least: sortable headers, search, filters and views, date navigation, grouping, paging and counts, density and column choice, bulk actions, export, row actions, a calendar view, a today marker and relative days, keyboard shortcuts, the states, deep links and the time zone; a screen that is not a list gets the list its own kind calls for. The orchestrator decides each one and writes it into the surface brief as a table: convention, verdict, reason. Each "Build" becomes a rubric check or a job. Each "Declined" names its reason: no job on record, a recorded decision by its number, or the control that already does the job. Where the records are silent, three personas are asked before the verdict. A missing convention is then a decision a grader can check, never an oversight. A "Declined" is not the orchestrator's alone: the finished table gets the same two readings the rubric draft gets (an Opus agent and `agy` with Gemini), each asked which declines a reader trained by those products would not accept. "A filter already does it" is not a reason when the category offers both the filter and the order. An order the BFF does not serve is not drawn by sorting loaded rows in the browser. The Schedule closed at 40/40 with no one having asked whether its table should sort; the answer was no, for reasons, and nothing had written them down (#2866). On the three lists climbed first, the two readings overturned seven declines the orchestrator had written (a search, week stepping and the time zone on the Schedule; an export and a period on the Invoices list; an order by money owed and a due month on the Clients list) and found a recorded decision broken (the Schedule read its days in the browser's zone against ADR-0036).
4. **Settle a shared state once.** When two checks pull against each other (a state said twice against a state said the way a sibling says it), write the rule in `DESIGN.md` before building either.
5. **Have the rubric draft read twice before the baseline.** One Opus agent judges each job against the record lines it cites and each check for whether two honest graders would score it alike; `agy` with Gemini looks for checks that pass without the job working. Each found about a dozen defects in the Schedule's draft, and none overlapped much.
6. **Decide the whole arrangement before the first build.** After the baseline, one Opus agent reads the rubric, the findings, the siblings and the records, and returns each control, its words, its address parameter and the shared option it uses. The first build then carries the arrangement in one piece. The Schedule went from 25 to 39 in one round this way.

## The round

1. **Walks first.** For each task check (T1–T8), `persona-walker` walks it blind on `dev:full`, under the profile the rubric names (375px for T4, keyboard only for T7, accessibility snapshot only for T6, the BFF refusing for T8), with a brief built as `docs/agents/persona-walk.md` says. The task is given as the persona's goal, never as the path. Each walk returns its act log. Record `git rev-parse HEAD`. A job that belongs to a role the graders' session is not (a Doula with no Owner or Admin role) is always walked, signed in as that person. A walker's brief tells it to apply `emulate` to its own page only. Read each act log before any grader spawns: what a walk shows wrong is fixed first and the walk repeated, which takes about two minutes, so the graders and the logs describe one screen. Each walker is asked, at the end, what the persona reached for on the screen and did not find; the Schedule's fourth round learned of the Visit's missing type that way.
2. **Freeze the tree.** From the first grader's spawn to the third grader's report, the worktree holds still: the dev server hot-reloads, so an edit changes the page under a grader. Builds start when the third report is in.
3. **Sign the chrome-devtools browser in.** Graders check width and forced colors through chrome-devtools (see `grader-brief.md`), and its profile starts empty. Once, before any grader spawns, the orchestrator does `new_page` to `<origin>/login`, fills "Email address" with `renata.alvarez@sim.doula.cloud` and "Password" with `demo-password-local-only` (`dev:full` prints both), and clicks "Sign in". No second factor is asked; the two-factor banner on the Overview is optional. Then a plain `new_page` on the screen's URL must land signed in; close that page. Every later plain `new_page` shares the session, and graders never sign out or in.
4. **Three graders, blind.** Spawn three graders in parallel, each briefed from `grader-brief.md` with its placeholders filled. Each gets the rubric, the screen's URL and source paths, and the act logs. None gets an earlier score, this branch's history, the other graders' output, or any word on what changed. Each scores all ten heuristics strictly by the rubric's rule (4 = every check passes with evidence) and returns, for each heuristic, the score, the checks that failed, and the evidence behind each pass. Each grader also returns "Expected and missing", written before reading the surface brief (`grader-brief.md`).
5. **Median per heuristic.** The round's score is the sum of the ten medians. A check two of three graders fail is a finding; one grader's lone fail is a note. An expected-and-missing item that two of three graders name, and that the baseline neither builds nor declines with a reason, is a finding under H4. A lone item is a note, and the orchestrator adds it to the baseline with a verdict before the next round. A grader also judges each "Declined" the grader's own list ran into: two of three graders finding a decline's reason unsound is a finding under H4, whatever the baseline says. A note that names no failed check is built only after the brief lists every rubric check that reads the same element and how the fix keeps each one passing: on the Schedule a comma hidden to answer such a note failed two checks in the next round.
6. **Record.** Write the round with `impeccable critique-storage write` (meta: target, total, max 40, P0/P1 counts), with the per-heuristic medians, the failed checks and the walked SHA. Confirm `git status` lists the new snapshot; if git reports it ignored, stage it with `git add -f`. The snapshot lists what the graders expected and did not find, with how many named each, and which declines they judged.
7. **Plateau rule.** Two rounds in a row at the same score, on different failed items, end the climb's own judgment: bring the founder the score, the items, and the choice to accept or continue.

## Each build between rounds

- **Fix by the job, not the grader.** Every fix names the check it makes pass and is verified the same way the check is graded. A change that moves a score without changing what a person can do is reverted.
- **Hold-still table.** The build brief lists the measurements that must stay as they are (column positions at 1280px and 1920px, the first screen's row count, each accessible name the rubric reads, the sibling screens' layout). The build agent measures them before and after on the rendered page and returns both as a table. A moved number is a regression until the brief says it was the goal.
- **Shared component first.** A fix a sibling list also needs goes into `FilterBar`, `DataTable` or the shared component the first time, and the sibling is checked on the rendered page in the same build.
- **Commit each build through the gate** before the next one starts. An agent stopped mid-build is not committed. The gate does not run the duplication check: the orchestrator runs `bun run dupes:check` from the repo root after each build.
- **A build agent runs in the foreground.** Its brief forbids background commands and monitors, the commit included: a build that left monitors behind kept waking and sending its report again. The brief names the reading it requires (`impeccable context`, `craft-floor.md`, the Voice section) as required, and the agent's report says which it read.
- **A second model reviews, three graders score.** For a rubric draft or a large build, `agy` with Gemini reviews from a diff file: `git diff <a> <b> --output=<file> -- <paths>`, under about 100KB, one concern per run, `--mode plan --add-dir <dir>`. Plan mode reads files and runs no command. Its findings are review; the score stays the three graders' (ADR-0063).

## The rubric

The rubric changes only when a check proves wrong about the person's job or contradicts a recorded decision, never because it is hard to pass, and the change is recorded with its date and reason at the foot of the rubric.

## Closing the climb

Before the last round's score is taken as final, see on the page once what every round judged from specs: with the browser's network off, press "Load more" and apply a filter, and say what the screen does. Then a fresh Opus agent reads the code diff (`git diff origin/trunk...HEAD -- app/src`) for defects, with no word on the scores; the Schedule's review found six small ones no round had. Rebase before either, run the whole gate on the rebased tip, and measure the sibling lists again.

Before `gh pr create`, `git push` runs `scripts/hooks/pre-push` (the duplication check, and the API message gate when Go changed). Run the Go tests for every `api/` package the branch touched as well; the hook leaves those to CI because they start Postgres.
