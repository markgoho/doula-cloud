# A grading round

One round scores one screen against its rubric (`clients-list.md` and `invoices-list.md` are the models). It is what turns "the critique says 34" into a number that means the jobs work.

## Before the baseline

1. **Seed first.** `dev:full`'s demo Practice holds a realistic book for this screen: enough rows to page, sort and scroll, and one row in every state the screen can show. Extend `app/scripts/demo-practice.ts` until it does. A round graded on three rows measures nothing. A seeded act has its own effects (naming a Doula on a Visit attaches her to the Engagement), so the seed build's brief lists the sibling screens' numbers that must not move, and the agent reads them on the rendered page before and after: the Schedule's first seed put five Doulas on one Client and the Clients list scrolled sideways. A build or seed agent that started `dev:full` in the background leaves it running after its report, and a restart it makes later reseeds the stack with new ids: on the Engagement record the seed agent's last restart landed a minute after the baseline graders opened the screen, the shared browser went to /login, and the baseline was graded from source. Every build brief ends with the agent stopping its own stack; the orchestrator starts the stack the round uses, in its own background task, and reads the ids off it.
2. **Read the siblings first.** Open every screen already climbed (the Clients list, the Invoices list) and start from its `FilterBar` and `DataTable` usage, its control sizes and its wording for a shared state. Where this screen must differ, write the reason in the surface brief. "Unlike the Clients list" was the Invoices climb's last lost point for four rounds.
3. **Name the category baseline.** Before the rubric is drafted, one Opus agent lists what a screen of this kind has taught its readers to expect, from Stripe Dashboard, Linear, the GOV.UK and MOJ design systems and the tools the personas already use, and says where each expectation was learned. The claim about each expectation is read, never remembered: the agent reads the product's own documentation page for each claim and quotes it with its address, and a claim it could not read is marked unread. No "Declined" may rest on an unread claim. The first baseline declined a sort on three lists on a remembered claim that Stripe's lists are fixed in order; Linear's and Stripe's own pages say a reader chooses the order, and the decline was reversed the same day (#2869). It covers at least: sortable headers, search, filters and views, date navigation, grouping, paging and counts, density and column choice, bulk actions, export, row actions, a calendar view, a today marker and relative days, keyboard shortcuts, the states, deep links and the time zone; a screen that is not a list gets the list its own kind calls for. The orchestrator decides each one and writes it into the surface brief as a table: convention, verdict, reason. Each "Build" becomes a rubric check or a job. Each "Declined" names its reason: no job on record, a recorded decision by its number, or the control that already does the job. Where the records are silent, three personas are asked before the verdict. A missing convention is then a decision a grader can check, never an oversight. A "Declined" is not the orchestrator's alone: the finished table gets the same two readings the rubric draft gets (an Opus agent and `agy` with Gemini), each asked which declines a reader trained by those products would not accept. "A filter already does it" is not a reason when the category offers both the filter and the order. An order the BFF does not serve is not drawn by sorting loaded rows in the browser. The Schedule closed at 40/40 with no one having asked whether its table should sort; the answer was no, for reasons, and nothing had written them down (#2866). Each reading is asked to open every record line a verdict cites and say whether the line says what the row claims: on Contracts one decline cited #973 backwards and another quoted words that were not on the cited line, and the reader who opened them overturned both. A "Later" names its ticket by number before the baseline round; "Later (ticket)" with no ticket is a decline with no reason. In `agy`'s prompt say "run no command; open only these files with your file reader" and name the files: plan mode ends with no output when the model tries a shell command. On the three lists climbed first, the two readings overturned seven declines the orchestrator had written (a search, week stepping and the time zone on the Schedule; an export and a period on the Invoices list; an order by money owed and a due month on the Clients list) and found a recorded decision broken (the Schedule read its days in the browser's zone against ADR-0036).
4. **Settle a shared state once.** When two checks pull against each other (a state said twice against a state said the way a sibling says it), write the rule in `DESIGN.md` before building either.
5. **Have the rubric draft read twice before the baseline.** One Opus agent judges each job against the record lines it cites and each check for whether two honest graders would score it alike; `agy` with Gemini looks for checks that pass without the job working. Each found about a dozen defects in the Schedule's draft, and none overlapped much.
6. **Decide the whole arrangement before the first build.** After the baseline, one Opus agent reads the rubric, the findings, the siblings and the records, and returns each control, its words, its address parameter and the shared option it uses. The first build then carries the arrangement in one piece. The Schedule went from 25 to 39 in one round this way. A call that adds a control to a filter bar also decides, in the same call, what folds below a 42rem bar and what the Tab rule is, and names the first card's bottom at 375×740 it must keep, which the first build measures and reports (On call's call named none for its Days radios, and the first card ended at 825 of 740 through every round): each control costs the phone a card and the keyboard a stop, and the Schedule's Order select alone moved the first Invoice card from 716 to 856 of 740 before a second call reversed "Order never folds". On a screen with almost nothing on it, the call may run while the baseline's graders do: Contracts' baseline was two bare tables, its findings were the brief's "Build" rows, and running both at once saved about 25 minutes; the call's result is still checked against the baseline's findings before the first build. A rule the call sets for every control at once (the Schedule's "everything waits for Apply") is walked blind on the first build that has it; both of round 5's walks waited on a select, a box and a radio that had not applied (#2888).

## The round

1. **Walks first.** For each task check (T1–T8), `persona-walker` walks it blind on `dev:full`, under the profile the rubric names (375px for T4, keyboard only for T7, accessibility snapshot only for T6, the BFF refusing for T8), with a brief built as `docs/agents/persona-walk.md` says. The task is given as the persona's goal, never as the path. Each walk returns its act log. Record `git rev-parse HEAD`. A job that belongs to a role the graders' session is not (a Doula with no Owner or Admin role) is always walked, signed in as that person. A walker's brief tells it to apply `emulate` to its own page only. Read each act log before any grader spawns: what a walk shows wrong is fixed first and the walk repeated, which takes about two minutes, so the graders and the logs describe one screen. "Wrong" means a defect: a control that does nothing, a wrong fact, a page that does not fit. One fix build and one repeat of the walk, then the graders; anything else a walk shows is a finding for the round. On call's first round ran three fix builds before a grader looked and added about three hours. Each walker is asked, at the end, what the persona reached for on the screen and did not find; the Schedule's fourth round learned of the Visit's missing type that way. A walk that changes the Practice (Dee sending a Draft) changes what the other walkers and the graders see: the walks run on one stack, and the stack is started again, so the seed is whole, before the graders spawn. A baseline of a screen with no control to walk needs no `persona-walker`: the orchestrator signs in as each role the graders are not and writes what the nav and the typed address show. Read the seed's days off the rendered page before writing a walk's goals: the seed's days move with the hour it is run, and round 5's brief sent Dee after a "Friday" Visit that had become a Saturday.
2. **Freeze the tree.** From the first walk's spawn to the third grader's report, the worktree holds still and nothing commits: the dev server hot-reloads, so an edit changes the page under a walker or a grader, and a commit's gate regenerates the dev server's own files, which on the Schedule's fourth round left it answering no page while a walk was under way. Builds and commits start when the third report is in. A spec that reads a day takes a fixed instant and states its zone: the suite runs in UTC in CI and in Eastern here, and four of the Schedule's specs passed only while the two zones shared a date. Before a push, run the touched specs under `TZ=Asia/Tokyo` as well. `bun run --cwd app check` stops the dev server the same way a commit does (it runs `svelte-kit sync`): a build agent that measures on the page runs `check` last, and the orchestrator stops the stack before every commit and starts it again after. A round does not straddle an hour the seed turns on: On call's seeded gap for tonight is written differently before and after 10:00am, so a round begun at 9:30 would have walked two seeds. Everything a round leaves for the next one (the design call, the rubric readings, act logs, grader reports, briefs) is written under `.impeccable/` in the worktree, never only in the scratchpad: a Claude Code restart clears the scratchpad, and on the Engagement record it took the design call, both readings and the baseline reports with it mid-build. When the orchestrator must verify a save the graders may not make (a payment, a reply, a new Visit), it does so on a record no job grades, or reseeds before the walks.
3. **Sign the chrome-devtools browser in.** Graders check width and forced colors through chrome-devtools (see `grader-brief.md`), and its profile starts empty. Once, before any grader spawns, the orchestrator does `new_page` to `<origin>/login`, fills "Email address" with `renata.alvarez@sim.doula.cloud` and "Password" with `demo-password-local-only` (`dev:full` prints both), and clicks "Sign in". No second factor is asked; the two-factor banner on the Overview is optional. Then a plain `new_page` on the screen's URL must land signed in; close that page. Every later plain `new_page` shares the session, and graders never sign out or in. Claude in Chrome keeps its own session for each origin, so a stack on a new port finds it signed out: sign it in on that origin as well, or tell the graders to do every walk in chrome-devtools. All three of round 5's graders found it signed out and fell back. Walkers signed in as other people (Priya, Dee, Lena) each open their page with `isolatedContext` named for the persona, so their sign-ins do not replace the graders' session; three walks then run in parallel. A grader never passes `isolatedContext`.
4. **Three graders, blind.** Spawn three graders in parallel, each briefed from `grader-brief.md` with its placeholders filled. Each gets the rubric, the screen's URL and source paths, and the act logs. None gets an earlier score, this branch's history, the other graders' output, or any word on what changed. Each scores all ten heuristics strictly by the rubric's rule (4 = every check passes with evidence) and returns, for each heuristic, the score, the checks that failed, and the evidence behind each pass. Each grader also returns "Expected and missing", written before reading the surface brief (`grader-brief.md`). The brief gives a grader 25 minutes. The orchestrator knows the usual time before spawning (the Schedule's first four rounds took 11 to 17 minutes from the walk logs to the scores) and looks every five minutes at each grader's last activity and report file, without messaging a blind grader; a report file may hold only the "Expected and missing" list. A grader at twice the usual time is told to stop gathering and report from the evidence in hand, with each check it did not reach marked unverified and not counted as a fail. Round 5's graders ran 35 minutes with two more jobs and walk logs twice as long, and reported within five minutes of being told. A check a grader could not reach is unverified and never caps the heuristic: the heuristic scores on the checks verified (`grader-brief.md` says so). In the Engagement record's round 1 one grader capped two heuristics at 3 for unreached checks, and another failed 1a on the dev server's own Slow 4G behavior; both were measurement, not the page.
5. **Median per heuristic.** The round's score is the sum of the ten medians. A check two of three graders fail is a finding; one grader's lone fail is a note. An expected-and-missing item that two of three graders name, and that the baseline neither builds nor declines with a reason, is a finding under H4. A lone item is a note, and the orchestrator adds it to the baseline with a verdict before the next round. A grader also judges each "Declined" the grader's own list ran into: two of three graders finding a decline's reason unsound is a finding under H4, whatever the baseline says. A note that names no failed check is built only after the brief lists every rubric check that reads the same element and how the fix keeps each one passing: on the Schedule a comma hidden to answer such a note failed two checks in the next round.
6. **Record.** Write the round with `impeccable critique-storage write` (meta: target, total, max 40, P0/P1 counts), with the per-heuristic medians, the failed checks and the walked SHA. Confirm `git status` lists the new snapshot; if git reports it ignored, stage it with `git add -f`. The snapshot lists what the graders expected and did not find, with how many named each, and which declines they judged.
7. **Plateau rule.** Two rounds in a row at the same score, on different failed items, end the climb's own judgment: bring the founder the score, the items, and the choice to accept or continue.
8. **Print the scores.** When the third grader reports, print one table of every round so far (usability, craft, each grader's score, the walked SHA), what holds each lost point and which ticket closes it, and an estimate of the rounds left.

## Each build between rounds

- **Fix by the job, not the grader.** Every fix names the check it makes pass and is verified the same way the check is graded. A change that moves a score without changing what a person can do is reverted.
- **Hold-still table.** The build brief lists the measurements that must stay as they are (column positions at 1280px and 1920px, the first screen's row count, each accessible name the rubric reads, the sibling screens' layout). The build agent measures them before and after on the rendered page and returns both as a table. A moved number is a regression until the brief says it was the goal. A target the build misses is reported with its number. The table also holds what a sighted reader sees on a phone's card: each visible label and the first card's bottom at 375×740. On call's fix for a fact said twice ("Due: · Due Fri Dec 4") took the visible word out and left the label for a screen reader only, so the next round's walkers read two bare dates and three graders failed it. For a table the hold-still table also holds the smallest and largest row height in every view at 1280px, and the orchestrator looks at the rendered table before a round: Contracts' first build reported its targets met while the Client column was 104px wide and 24 of 30 rows wrapped to two lines. A seeded sentence is layout too: one longer void-request reason wrapped and moved the first row from 785 to 813 of 800, so the first row is measured again after any change to seeded words. A first-screen check is not met by pressing what a person decides onto one line: Contracts' void requests were cut to a line of three tracks to keep the first row at 784 of 800, three graders passed it, and the founder read the page and called it awkward; the check changed, not the reader. When a check and legibility pull apart, the orchestrator shows the founder the page before the round. A build does not change a word to make a width fit: one fix build cut "Void requested" to "Void asked", which the Engagement does not say; it reports the missing pixels. A build never raises a layout spec's tolerance, rewrites it or deletes it to go green: the Clients order build raised one from 1 to 64 and had its merge held until a design call set the rule.
- **Shared component first.** A fix a sibling list also needs goes into `FilterBar`, `DataTable` or the shared component the first time, and the sibling is checked on the rendered page in the same build. A new shared option gets one owner and one merged build before any screen adopts it. Three lists adopted `FilterBar`'s `order` in parallel and each handled the select's width its own way; a fourth build had to undo them.
- **Commit each build through the gate** before the next one starts. An agent stopped mid-build is not committed. The gate does not run the duplication check: the orchestrator runs `bun run dupes:check` from the repo root after each build.
- **A build agent runs in the foreground.** Its brief forbids background commands and monitors, the commit included: a build that left monitors behind kept waking and sending its report again. The brief names the reading it requires (`impeccable context`, `craft-floor.md`, the Voice section) as required, and the agent's report says which it read.
- **The finish review runs on the first build, before round 1's graders,** and again on any build that changes what the screen looks like. On Contracts `impeccable-finish-reviewer` ran once, after the founder had ended the climb, and sent back four build findings (a ragged Status column, "Mine" outside "Show only", a card that is not a target, a reason with no limit) that a round's build would have carried; they were filed (#2959).
- **A second model reviews, three graders score.** For a rubric draft or a large build, `agy` with Gemini reviews from a diff file: `git diff <a> <b> --output=<file> -- <paths>`, under about 100KB, one concern per run, `--mode plan --add-dir <dir>`. Plan mode reads files and runs no command. Its findings are review; the score stays the three graders' (ADR-0063).

## The rubric

The rubric changes only when a check proves wrong about the person's job or contradicts a recorded decision, never because it is hard to pass, and the change is recorded with its date and reason at the foot of the rubric. A number in a check (a page height, a first-screen bottom) is set from what each job must show before the first build and is fixed for the climb; the Engagement record's draft capped the page at "about 4 screens" with no job behind it, the second design call showed the jobs' own first rows needed more, and the cap was reset before the build from that reasoning, never from a measured result.

## Closing the climb

Before the last round's score is taken as final, see on the page once what every round judged from specs: with the browser's network off, press "Load more" and apply a filter, and say what the screen does. Then a fresh Opus agent reads the code diff (`git diff origin/trunk...HEAD -- app/src`) for defects, with no word on the scores; the Schedule's review found six small ones no round had. Rebase before either, run the whole gate on the rebased tip, and measure the sibling lists again.

Before `gh pr create`, `git push` runs `scripts/hooks/pre-push` (the duplication check, and the API message gate when Go changed). Run the Go tests for every `api/` package the branch touched as well; the hook leaves those to CI because they start Postgres.

Before the baseline, tell the founder how long the climb is expected to take and how many rounds, and say so again the first time it doubles. On call ran past eight hours with no word, most of it building between rounds what could have been filed; the founder then chose one more round and to land at its score (32/40, 17/20, below round 1's 33 and 18 on checks the earlier graders had not reached). Between rounds, a finding that is not a defect is filed unless the founder has asked for it to be built. The estimate counts, for each round, the walks (about ten minutes), one fix build with its commit (about forty), a stack start for each (five), and the graders (twenty-five), on top of the builds: Contracts was told five to six hours and took about eight, baseline 15 to 37 in one build, because each round's fix build and restarts were not in the estimate.

When the climb's pull request has merged and the founder asks for it, the tickets the climb filed are built in the same session, in the order they depend on one another: a Sonnet agent for each, in a worktree and a pull request of its own, with an Opus design call first where the ticket asks for one. A ticket that changes what a rubric check reads is followed by a round, and its scores are printed. Filing a ticket does not finish a climb.

A loose-end build verifies each box the way its rubric check is graded, not only by eye: the Engagement record's #2991 made Details an `<h2>` and left it right after the facts in the DOM, so at 1280px heading navigation read it before On call, which is drawn above it; the box was ticked from a screenshot and the closing round's graders failed T8 on it. For a heading, read the heading order from the accessibility tree at the width the check names. A loose-end build that adds a control to a climbed screen can lower its score: the Schedule went from 39 to 37 with every job passing, on three single checks the new controls brought. A failed check from that closing round is fixed and verified on the rendered page, and the founder may end the climb there without another round; what is left is filed with acceptance criteria under #2760.

The retro's lessons are written into this file and `grader-brief.md` in the same pull request that records the last round. A comment on #2760 alone teaches no later climb: the Schedule's closing retro was posted there first and reached this file only when the founder asked whether later climbs would see it.
