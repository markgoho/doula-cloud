# Migration safety notes

A safety note says why a row-dependent statement in a migration cannot be broken by the rows a table already holds. It exists because the `migrate` job runs only on a push to trunk: a pull request builds an empty database, so a statement that only *existing rows* can refuse is green on the PR and red on trunk, with `deploy-api` and `deploy-app` stuck behind it (see #1021, and the rule stated at the top of `../rowsafety.go`).

One note per migration, named for the migration file: `00107_portal_account_client_pair_unique.md` covers `../00107_portal_account_client_pair_unique.sql`.

The note lives here rather than inside the migration because goose never re-runs a migration once it is recorded as applied, so an already-applied migration's SQL must not be edited — the file and the database would silently disagree. A new migration may still be written with its proof in the SQL comments — the note is what the guardrail reads, so write it either way.

A note must carry a `## <class>` heading for every class the guardrail reports on that migration, spelled exactly as the guardrail names it. Under the heading, a fenced ` ```sql ` block quotes the exact statement the note is proving safe, one block per statement, followed by the reason those rows cannot break it. The guardrail matches a block against `Finding.Statement` after collapsing whitespace and upper-casing both sides, so the block can be pasted straight out of the migration's SQL, semicolon and all -- but it excuses only the one statement it quotes. A migration with two statements of the same class (two `CREATE UNIQUE INDEX`, say) needs two blocks under that one heading, each proving its own statement; a block that quotes only one of them leaves the other reported. `guardrail_test.go` fails a note that covers a class the migration does not raise, or a block that quotes a statement the migration no longer contains, so a note cannot outlive the statement it justifies.
