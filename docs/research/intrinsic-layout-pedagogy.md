# How intrinsic layout is taught: Simmons firsthand, Modern CSS Solutions, and the design systems that landed it

Research for [#519](https://github.com/markgoho/doula-cloud/issues/519), part of the wayfinder map [#518](https://github.com/markgoho/doula-cloud/issues/518). Question: how is intrinsic layout actually taught — by the person who named it, by a corpus that teaches CSS by worked problem, and by design systems that put space-based component layout into production — and does any of that differ from `docs/research/intrinsic-web-design.md` and ADR-0023 in a way that matters. Research date 2026-08-30.

## 0. A note on source quality, read before the quotes below

Three strands, three different evidence problems:

- **Strand 2 (Modern CSS Solutions)**: fetched directly from moderncss.dev; content and structure quotes are short and attributed by URL.
- **Strand 3 (design systems)**: "landed it" is checked two ways — GitHub code search for `container-type`/`@container`/`cqw` inside each system's actual source repository (default branch only; GitHub's code-search index is known to skip some generated/minified/vendored files, so a `0` result means "no match found by this index," not a cryptographic proof of absence), and direct fetches of each system's own published layout/contribution docs. ## 1. Simmons, firsthand: "Designing Intrinsic Layouts"

Talk: Jen Simmons, "Designing Intrinsic Layouts," An Event Apart, filmed 5 Mar 2019 (per Jeremy Keith's live-blog dateline, below), published to YouTube 10 Mar 2020 as [`AMPKmh98XLY`](https://www.youtube.com/watch?v=AMPKmh98XLY), 59:07 runtime. Transcript retrieved 2026-08-30 via `yt-dlp` against YouTube's auto-captions: 1,545 de-duplicated caption cues, ~11,600 words, grouped by the retrieval into 129 timestamped paragraph blocks. All keyword checks below (`grep -in`) were run directly against that retrieved transcript file, not against an earlier in-session scrape of YouTube's own transcript panel, which proved unreliable mid-session (see the "breakpoint" discrepancy in §1.3) and was discarded.

### 1.1 What she demonstrates, and the order she reaches for tools

The talk is a live-coded rebuild of a podcast-site header, walked through version by version (her own naming: 7a, 7b, 7c, 7d…). The order she actually moves through tools, confirmed from the transcript:

1. **Semantic HTML first, no CSS at all** ("flow layout") — she states this is deliberate, because reader-mode and assistive-technology users see this state whether or not the page's CSS ever loads: *"why should we care about this page with no CSS... anyone who's using any kind of reader mode"* [auto-caption, ~05:52].
2. **Float, shown only as the rejected old way** (her label: "version 7c," styled as circa-2007 code) — she calls the result *"fragile"* and states plainly this was never the right tool: *"this is not what floats were designed to do... that's the only tool we had in our toolbox so we used it"* [auto-caption, ~10:50–11:18].
3. **CSS Grid as the primary, default tool** ("7d") — introduced immediately after float, with no flexbox in between: *"let's use grid... for the last two and a half years"* [auto-caption, ~12:02–12:15]. The whole outer header structure is built in Grid.
4. **Flexbox reached for once, nested inside Grid, for exactly one single row** — the nav `<ul>`: *"you know what that navigation probably really wants — flexbox — this is a perfect kind of tool for something like that"* [auto-caption, ~24:04]. She is explicit this is deliberate composition, not either/or: *"people are like, should I use grid or should I use flexbox... you're gonna use both of them... on different parts of the page, on different nested formatting contexts"* [auto-caption, ~24:31–25:04].

This is a direct, primary confirmation of ADR-0023's own stated ordering ("Lay components out with CSS Grid by default... Flexbox stays the right tool for a genuine single row or column that simply wraps") — not inferred from Keith's summary, but from watching the actual sequence of decisions in the talk.

### 1.2 The live resize demo: FR vs. percent, then layering max-content and auto

Between roughly 14:00 and 24:00 she runs one continuous demonstration, resizing the browser live in Firefox's Responsive Design Mode rather than the DevTools panel (*"you can just make the actual web page itself different sizes, while leaving the whole browser window itself pretty big"* [auto-caption, ~17:29]):

- **FR units vs. percent, same numbers**: she sets the same three column proportions (roughly 8/75/17) first as `fr` and then as `%`, live. The percent version overflows the viewport and the columns crash together at small sizes: *"it sticks way out off the edge of the page... 18 plus 75 plus 8 is not 100... don't use percents anymore, if you can help it use grid"* [auto-caption, ~20:50–21:49]. The FR version does not: *"those columns will never get too small to hold the content that's in them... that's the big difference between using FR units and using percents"* [auto-caption, ~19:54–20:19].
- **Layering `max-content`/`auto`** to stop the logo and nav columns from growing pointlessly with extra space: *"define this track as max-content, which basically says, would you please be the size of the content that's inside of you"* [auto-caption, ~22:16]; then `max-content auto max-content` for the whole row, restoring flex-wrap on the nested nav once the max-content column stops eating the wrap space [auto-caption, ~26:22–26:53].
- **A second, later demo (the "8b/8c" overlap example, ~52:00–54:00) shows differential squishing directly**: bounded image sizing that the auto-captions render as *"a min/max of a hundred pixels to 400 pixels"* [auto-caption, ~53:20–53:44] — read in context (grid tracks, "the last column," a companion `1fr` track) this is `minmax(100px, 400px)` on a grid track, not the two separate `min()`/`max()` functions; the caption engine has almost certainly collapsed the CSS keyword `minmax()` into the everyday phrase "min/max," exactly the kind of CSS-term garble §0 warns about. What she describes doing with it is unambiguous regardless of the exact spelling: *"they stayed pretty big at 400 pixels for as long as possible, but then when there's really no space left then they start to shrink, and they shrink[] later than the 1fr will shrink"* [auto-caption, ~53:44], producing exactly the "several stages of squishiness happening at different rates" behavior `docs/research/intrinsic-web-design.md` already describes — *"the space that's available gets distributed at different rates to different parts of the page"* [auto-caption, ~53:44].

This confirms the existing doc's §3 mechanism table on primary evidence: `fr`, `max-content`/`auto`, and `minmax()`-bounded sizing are shown, live, doing exactly what the doc's table says they do. (`clamp()`/`min()`/`max()` as standalone math functions are not demonstrated anywhere in this specific talk — unsurprising, since they were not yet broadly shipped in 2019; see §2.2 for where they are covered firsthand instead.)

### 1.3 Where this talk actually diverges from the existing repo doc

`docs/research/intrinsic-web-design.md` §2 attributes the quote *"This is what we need breakpoints for"* to Keith's live-blog. This session obtained Keith's raw text directly (`curl` against `adactio.com/journal/14889`, not the tool-summarized paraphrase noted as a limit in §0 — the raw fetch worked where the summarizing fetch tool did not, because Keith's site is static and progressive-enhancement-first). Keith's exact sentence, in its own surrounding context:

> "...Now we need to get rid of our gaps. But now when the layout gets small, everything squishes up. **This is what we need breakpoints for.** But now we can do something else. Let's make the logo max-content..." — [adactio.com/journal/14889](https://adactio.com/journal/14889)

That "get rid of our gaps" line anchors Keith's account to one exact ~20-second window in the video: my transcript has Simmons say, in the same sequence — grid gap, then a mention of the gap unit not being a percent, then removing the gap — *"there's the gap, right? And the gap is 2m, it's not a percent, it's an M... so let's get rid of the gap"* [auto-caption, ~21:09–21:21], immediately followed by the FR-vs-percent crash demo from §1.2 and then the pivot to `max-content` on the logo column at ~22:16. **Keith's liveblog places "this is what we need breakpoints for" in that exact window — but my transcript of the same ~21:09–22:16 window contains no occurrence of the word "breakpoint" anywhere.** A full-text search of the entire 59-minute transcript (`grep -in breakpoint` against the retrieved file) finds the word exactly once in the whole talk, roughly 19 minutes later, in an unrelated example: the poster-inspired typography/overlap header rebuild (chapters "Spreading Letters" through "The Design," ~36:48–41:03), about a layout that has run out of room to squish further rather than one that is actively breaking: *"it works really well from all the way wide to about that wide... it doesn't get any smaller, so [you] need to use a breakpoint and switch to some other kind of layout in order to deal with anything smaller than this size"* [auto-caption, ~41:12–41:37] — immediately followed by her own transition line into the next, unrelated aside, *"that's a nice little example, so here we are in the land of Canaan"* [auto-caption, ~41:37] (a joke, not the example's name).

This is a genuine, specifically-timestamped discrepancy between two independent, imperfect records of the same talk, and this session could not adjudicate it further without listening to the original audio at ~21:15 directly (out of reach with the tools available this session): either the auto-caption engine dropped a spoken word at that point (auto-captions are known to omit as well as mis-hear), or Keith's live-blog — already characterized by this repo's own existing doc as "a note-taker... not the speaker" — used "breakpoints" as his own gloss on what she meant rather than a word she said at that exact moment. What both records agree on, and what matters for ADR-0023: **the substantive point Keith and the transcript both land on is the same one** — a layout can be squished by intrinsic sizing right up to a floor, and something else (Keith's account: a breakpoint, right there; the transcript's account: a breakpoint, but for a different, later example of the same underlying situation) is needed once it hits that floor. Simmons had no other tool for that job in 2019 — the transcript contains zero occurrences of "container quer[y/ies]" and zero occurrences of "media" anywhere in the full 59 minutes (checked by exhaustive regex against the retrieved transcript) — not because she rejected the concept, but because container queries postdate this talk by roughly three years. ADR-0023's rule 2 (reach for a container query, "no justification" needed) is, concretely, what fills the gap a 2019 viewport breakpoint was the only available answer to.

### 1.4 How she talks about how she teaches, and how she learns

This bears directly on strand 3's question (does prose change what an author writes) because Simmons answers it about herself, unprompted, describing her own method:

> "I really do think one of the best ways to figure it out... is to just try something, try some sort of random experiment and go into the Firefox Grid inspector and just start throwing random things at it — that's literally how I learn the things that I know, it's how I figured out how it behaves. I didn't memorize Rachel's books, I didn't read the whole grid auto placement algorithm — 'cause I did, but I didn't really understand huge chunks of it — I would learn better by just trying and trying and trying it." [auto-caption, ~54:44–55:15]

She also frames the demonstrated layouts as genuinely unfinished, not polished patterns to imitate wholesale: three demos late in the talk are shown explicitly as work she "didn't actually end up using," including one she says outright she has not solved (*"I'm not sure that I nailed it yet, I'm still... not quite done with this demo yet"* [auto-caption, ~57:00–57:31]). Her own stated pedagogy is live experimentation against a real, resizing browser and a grid inspector — not a written principle to be read and then applied — which is the same conclusion this repo's own ADR-0023 reached about *why* it needed a runtime gate (`layout.usage.spec.ts`, the rendered width matrix) rather than a documentation update.

### 1.5 Scope note: this transcript does not cover the whole existing doc

`docs/research/intrinsic-web-design.md` §1 draws its six-characteristics list ("fluid and fixed," "multiple stages of squishiness," "media queries, as needed," etc.) from Keith's live-blog of a *different* Simmons talk — "Everything You Know About Web Design Just Changed," An Event Apart Seattle 2018, via `adactio.com/journal/13671`. This ticket's assigned video (`AMPKmh98XLY`) is "Designing Intrinsic Layouts," the 2019 follow-up talk, live-blogged separately at `adactio.com/journal/14889`. This research therefore neither confirms nor contradicts the existing doc's §1 six-characteristics list — that section rests on a talk this session did not obtain a transcript for. Everything in §1.1–1.4 above bears only on the doc's material sourced to `journal/14889` and on the 2019 talk generally.

## 2. Modern CSS Solutions (moderncss.dev, Stephanie Eckles)

### 2.1 Site structure and two distinct pedagogical modes, both present

The site is organized by topic tag (Grid, Flexbox, Container Queries, Responsive Design, Custom Properties, etc.), each tag cross-listing the same ~25 posts. Two genuinely different teaching shapes coexist:

- **Recipe/reference mode** — e.g. ["3 CSS Grid Techniques to Make You a Grid Convert"](https://moderncss.dev/3-css-grid-techniques-to-make-you-a-grid-convert/): three independent techniques, each with its own "The Code / What it does / Things to note / When to use" structure, closer to an annotated reference than a single worked problem. Representative framing: *"Then I found the following 3 powerful properties/techniques in grid that completely changed my tune."*
- **Full worked-project mode** — e.g. ["Modern CSS For Dynamic Component-Based Architecture"](https://moderncss.dev/modern-css-for-dynamic-component-based-architecture/): builds a complete, fictional design system ("Jaberwocky") end to end — four real components (buttons, cards, pagination, navigation), incrementally, using cascade layers, custom properties, and container queries together, moving "from baseline styles to progressive enhancements" and solving each layout decision as it comes up rather than stating it as a rule first. This is the closer match to the ticket's "teaches by worked problem" framing, and it is also the piece on the site most directly relevant to ADR-0023, because it is the one place in this corpus that teaches container-query component architecture by building a small design system rather than by asserting a principle about one.

So the honest characterization is: **the site's older/shorter posts lean reference-style; its most ambitious and most container-query-forward post is a full worked build.** Neither mode carries any enforcement — this is a personal blog/course series by one practitioner, read voluntarily, with no gate analogous to `layout.usage.spec.ts`.

### 2.2 Coverage of ADR-0023's named mechanisms

| ADR-0023 mechanism | Modern CSS Solutions coverage | Article |
|---|---|---|
| `clamp()` / `min()` / `max()` | Direct, worked, both for spacing and for typography — `clamp(1rem, 3%, 1.5rem)` for padding, `min(4rem, 8vh)` for margin, `clamp(1.5rem, 6vmax, 3rem)` for gaps | ["Contextual Spacing For Intrinsic Web Design"](https://moderncss.dev/contextual-spacing-for-intrinsic-web-design/) (explicitly credits Simmons and 2018 by name), ["Practical Uses of CSS Math Functions"](https://moderncss.dev/practical-uses-of-css-math-functions-calc-clamp-min-max/) |

## 3. Design systems that landed it (or didn't)

### 3.1 Method

For each system, GitHub code search (`gh api search/code`) was run against `container-type`, and for negative results, also against the `@container` and `cqw` spellings (to catch the `container:` shorthand and container query units, which wouldn't match a bare `container-type` search). Each search is scoped `in:file repo:<owner>/<repo>` against the repository's current default branch. Two systems' own published layout/contribution docs were fetched directly for corroboration.

Eleven actively maintained, widely-used design systems checked. Eight show zero evidence of container-query-based component layout anywhere in their source. The three with any hit at all have exactly one file each, and in two of the three cases that one hit is either documentation prose or an explicitly experimental/next-gen package, not a shipped, general pattern a contributor would be pointed at.

Caveat on the method: GitHub's code-search index is known to have gaps (very large or generated files, some vendored/minified bundles), so a `0` result is "not found by this index," not certified absence. Given the consistency of the pattern across eleven independent repositories and two different corroborating searches (docs pages, alternate query spellings), that caveat does not plausibly reverse the finding.

### 3.3 A closer look at GOV.UK, because this repo treats it as the reference

`docs/adr/0021-govuk-is-the-reference-for-service-patterns.md` makes the GOV.UK Design System this repo's default reference for service-pattern screens. Its own layout system is exactly the mechanism ADR-0023 moves away from. From `design-system.service.gov.uk/styles/layout/`: layout is built from named, fixed-breakpoint grid classes — e.g. `govuk-grid-column-two-thirds-from-desktop` combined with `govuk-grid-column-one-half` to render one width on tablet and a different named width "from desktop." There is no container query, no `grid-template-areas`, and no space-based component adaptation anywhere in `alphagov/govuk-frontend`'s source (§3.2). This is not a criticism of GOV.UK's choice for its own purposes — it is a fact this repo should hold alongside ADR-0021: the system named as this repo's pattern reference has not solved, and does not attempt, the layout problem ADR-0023 exists to solve. The two ADRs are answering different questions (service-pattern decisions vs. layout mechanism) and neither contradicts the other, but a reader should not assume GOV.UK's own markup demonstrates container-query practice, because it does not.

### 3.4 The one system-adjacent voice with an explicit, opposing philosophy: Every Layout

`docs/research/every-layout-css-primitives.md` (already in this repo, researched for #95) already fetched Every Layout's "Container" page in full. It is worth restating here because it directly contradicts ADR-0023's own stance on when a container query needs a reason: Every Layout frames `@container` as a deliberate, minimal-use escape hatch — *"manual intervention... They are circuit breakers we wire into layouts we know are going to error... I'd sooner not have them anywhere I know they're not needed"* — and goes on to argue, with a worked example, that Sidebar's own query-free flexbox trick is *more* capable than a container query for that specific case, not merely an adequate substitute. ADR-0023 states the opposite default explicitly: *"A component reaching for a container query does not owe anyone a justification — this is the default mechanism."* Both are considered, primary-sourced positions from people who have shipped real component layout; they simply disagree about how eagerly to reach for the tool. This repo has already chosen its side (ADR-0023); the point of recording Every Layout's contrary argument here is that it is the most substantive dissent found anywhere in this research, not a straw position.

### 3.5 Negative result, stated plainly

The honest answer to strand 3 is a negative result: **almost nobody has landed container-query-based, space-adaptive component layout as a systemic, documented, contributor-facing practice.** Across eleven major design systems, the practice does not exist in eight, and in the three with any trace it is confined to exactly one component or one documentation example, never a stated default a general contributor is pointed at before authoring a new component. The strongest positive teaching precedent found in this entire research pass — Modern CSS Solutions' "Jaberwocky" worked build (§2.1) — is a solo educator's blog post, not an institutional design system with review gates. Every Layout, the strongest *primitives* precedent, explicitly argues against defaulting to container queries at all. This repo's ADR-0023 and its enforced gate (`layout.usage.spec.ts`, the rendered width matrix) do not have a peer institution to point to as "here is where this worked at scale" — the honest evidence is that this repo is ahead of, not behind, the field it is drawing mechanism guidance from.

## 4. Which teaching mechanisms are evidenced to change author behavior, as against which merely exist

This has to be answered carefully, because none of the sources surveyed in this research offer measured, causal evidence — no A/B result, no before/after contributor-behavior study, no retrospective — that any specific teaching format changed what authors actually wrote. That evidence was not found anywhere in this pass, and it would be dishonest to imply otherwise by tone. What can be said, and separated cleanly by evidence type:

- **Merely exists, unmeasured**: every artifact surveyed above — Simmons' talk, Keith's live-blog, Modern CSS Solutions' posts (both modes), every design system's docs page checked. All of these are read-or-not-read prose/video with no mechanism that reports back whether an author who encountered them wrote different code afterward.
- **Evidenced to fail, in this repo, specifically**: ADR-0023 itself already recorded the one piece of behavioral evidence this research can point to, and it is negative — this repo's own prior state (a 288-line primary-sourced doc plus an ADR) coexisted with "roughly zero `grid-template-areas` and one `container-type`" in the app, and two real layout defects (#508, #510) reached production before anything in the repo caught them; both were found by a person opening a browser by hand, not by anything the prose taught anyone to check for. That is the one measured (if informal) data point in reach, and it is about prose failing, not about any alternative succeeding.
- **The only mechanism this repo has that is falsifiable rather than merely read**: ADR-0023's own `layout.usage.spec.ts` source checks and the rendered width matrix. These were not found in any other design system surveyed (§3), so there is no external evidence they work either — but they are structurally different from every teaching artifact above in one respect: they do not require an author to have read anything. A commit either passes or fails regardless of whether the author ever opened the ADR. That is a testable, falsifiable claim about the *next* commit, not a claim about whether documentation changed anyone's understanding — and it is the honest reason this repo chose a gate over a rewrite of the prose.

No source found in this research — not Simmons, not Modern CSS Solutions, not any design system's contributor docs — reports evidence that reading changed what its readers built. The one piece of local evidence available says the opposite about this repo's own prose. That is consistent with, not contrary to, ADR-0023's existing bet on enforcement over documentation.
