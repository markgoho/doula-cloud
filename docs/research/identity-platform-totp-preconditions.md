# What Identity Platform requires before TOTP enrollment, and what changes at the next sign-in

Research for GitHub issue [What Identity Platform requires of an account before it can enroll a second factor (#1489)](https://github.com/markgoho/doula-cloud/issues/1489), a child of the map [Onboarding, from `/signup` to First Value (#1487)](https://github.com/markgoho/doula-cloud/issues/1487). Question: what must be true of an Identity Platform account before it can enroll a TOTP second factor, and what happens at the next sign-in once one is enrolled. All four questions below are answered from Google's own Identity Platform and Firebase Auth documentation, the Identity Toolkit v2 REST reference, and the `firebase-js-sdk` source where the docs are silent.

## 1. Must the email be verified before TOTP enrollment, and is it a hard refusal?

Yes, and yes. Google Cloud's own multi-factor-user guide states it as a rule, not a recommendation: "Multi-factor users must always have a verified email address. This prevents malicious actors from registering for your app with an email they don't own, and then locking out the real owner by adding a second factor." [docs.cloud.google.com/identity-platform/docs/work-with-mfa-users](https://docs.cloud.google.com/identity-platform/docs/work-with-mfa-users)

Firebase's own TOTP guides repeat the same rule as a precondition, in both the web and Android version of the doc: "Ensure your app verifies user email addresses. MFA requires email verification." [firebase.google.com/docs/auth/web/totp-mfa](https://firebase.google.com/docs/auth/web/totp-mfa), [firebase.google.com/docs/auth/android/totp-mfa](https://firebase.google.com/docs/auth/android/totp-mfa)

The refusal is a named error code, not a generic failure: `auth/unverified-email`, message "The operation requires a verified email," defined in `firebase-js-sdk`'s own error table (`packages/auth/src/core/errors.ts`, key `UNVERIFIED_EMAIL`). [github.com/firebase/firebase-js-sdk](https://github.com/firebase/firebase-js-sdk/blob/master/packages/auth/src/core/errors.ts)

Reading the SDK source narrows exactly where the refusal lands. `multiFactor(user).getSession()` does no client-side check at all — it only wraps the user's current ID token into a session object (`mfa_user.ts`). The verification check runs server-side, on the Identity Toolkit call `generateSecret()` makes to start enrollment, or on the call `enroll()` makes to finalize it. Either way, the check happens against the account's *live* `emailVerified` flag at the moment the request is made, not against anything cached in the client.

## 2. Does enrollment need a recent sign-in, and how recent?

Yes. Google's own reauthentication guide names "enabling multi-factor authentication" explicitly among the operations that require a recent sign-in: "Some security-sensitive actions... require that the user has recently signed in. If [they] signed in too long ago, the action fails." [docs.cloud.google.com/identity-platform/docs/web/reauth](https://docs.cloud.google.com/identity-platform/docs/web/reauth)

The docs do not state a numeric window anywhere in Google's own pages — that much has to be said plainly rather than guessed. A commonly repeated figure in third-party reporting (Stack Overflow, GitHub issue threads) is five minutes, but no Google-owned page this research reached states that number, so it is not carried here as fact. What is confirmed from the primary source is only that the check exists and that a sign-in "too long ago" throws `auth/requires-recent-login`, which the app's own `mfa/enroll` screen already handles by asking her to re-enter her password as step one (`signInWithEmailAndPassword`) before ever calling `getSession()`.

## 3. Does the current session get `firebase.sign_in_second_factor` right away, or does she have to sign in again?

Both are true, at different points, and the Identity Toolkit REST reference and the SDK source pin down which.

**The enrollment call itself already mints a fresh, MFA-aware token.** `accounts.mfaEnrollment.finalize`'s response carries its own `idToken`, documented as "ID token updated to reflect MFA enrollment" — a different token from the one the request was made with, already showing the new factor. [docs.cloud.google.com/identity-platform/docs/reference/rest/v2/accounts.mfaEnrollment/finalize](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/accounts.mfaEnrollment/finalize)

`firebase-js-sdk`'s `MfaUser.enroll()` uses that response directly: it calls `this.user._updateTokensIfNecessary(finalizeMfaResponse)` before resolving (`mfa/mfa_user.ts`). `_updateTokensIfNecessary` (`core/user/user_impl.ts`) only overwrites the SDK's in-memory `stsTokenManager.accessToken` "when the response contains an `idToken` that differs from the current access token" — which it will, since enrollment just happened. So by the time `enroll()`'s promise resolves, the SDK's *cached* token in memory should already carry `firebase.sign_in_second_factor`, without a forced refresh and without signing in again. [github.com/firebase/firebase-js-sdk](https://github.com/firebase/firebase-js-sdk/blob/master/packages/auth/src/mfa/mfa_user.ts)

That is a narrower claim than what the app's own code assumes. `app/src/routes/(signed-out)/mfa/enroll/+page.svelte` calls `enrollingUser!.getIdToken(true)` right after `enroll()` (line 170), on the stated reasoning that "the SDK's cached token predates the claim `enroll()` just added." Per the SDK source above, the cached token should *already* carry the claim once `enroll()` resolves — the force-refresh looks like an unnecessary extra network round trip rather than a required one, though a harmless one. Neither Google's docs nor the SDK source say anything about whether a forced refresh (a real trip to the `securetoken` token-refresh endpoint, not the enrollment call) is guaranteed to return a token carrying the same claim without any propagation delay on Identity Platform's backend; that is exactly the case `FinishEnrollmentHandler`'s decision-4 fallback (a 400 that signs her out and sends her to `/login` to redo it as an ordinary sign-in) exists to catch. This research found no primary source that confirms or rules out that propagation gap either way — it should be treated as an observed, undocumented platform behavior, not a documented guarantee.

**At any later, ordinary sign-in, the challenge is unconditional.** Once a factor is enrolled, `signInWithEmailAndPassword` no longer completes on the first call — it throws `auth/multi-factor-auth-required`, and the app must resolve a `MultiFactorResolver` with a fresh TOTP assertion before a session is minted at all. [firebase.google.com/docs/auth/web/totp-mfa](https://firebase.google.com/docs/auth/web/totp-mfa) This matches ADR-0026's own claim that "Identity Platform challenges the second factor on every sign-in once one is enrolled," and is why the Practice-boundary gate can trust `firebase.sign_in_second_factor` as a property of the sign-in event rather than a one-time record.

## 4. Is there a supported way to enroll in the same flow that creates the account, without a mailbox round trip?

No. Firebase's own Android TOTP guide names "enroll the user's second factor as part of registration" as one of its documented enrollment patterns ("use this method if your app requires multi-factor authentication for all users") — but the same page states the email-verification precondition as unconditional, with no carve-out for that pattern: "Ensure your app verifies user email addresses. MFA requires email verification." [firebase.google.com/docs/auth/android/totp-mfa](https://firebase.google.com/docs/auth/android/totp-mfa) No page found in this research describes any enrollment path, including one embedded in registration, that skips a verified address. The mailbox round trip is not a Doula Cloud design choice layered on top of the platform; it is the platform's own floor.

## Where the app's current behavior differs from what the platform requires

**The ordering gap is real, and it produces a guaranteed first-attempt failure today.** `staffauth.Middleware` (`api/internal/staffauth/middleware.go:199`) refuses any Practice-scoped request from an Owner with no second factor — `if !secondFactor && (reader.Has(roleOwner) || requireMFA)` — with no dependency on `emailVerified` anywhere in that check. `app/src/routes/practices/[practiceId]/+layout.ts` reads that refusal (`MFA_REQUIRED`) and redirects straight to `/mfa/enroll`. `app/src/routes/(signed-out)/signup/+page.svelte`'s `land()` navigates directly to `/practices/[practiceId]` right after signup succeeds. Signup itself (`api/internal/staffauth/signup.go`) only *queues* a verification email through the outbox (`authtoken.Mint` + `authmail.QueueTokenMail`, `PurposeStaffEmailVerification`) — it does not, and cannot, wait for her to open it. Chained together: a brand-new Owner is sent into `/mfa/enroll` before she has had any chance to click the link that was just mailed to her, and her account's `emailVerified` flag is still `false` by construction at that moment.

**The failure that follows is not diagnosable from the screen she is on.** `handlePasswordSubmit` in `mfa/enroll/+page.svelte` catches whatever `generateSecret()`/`getSession()` throws and maps it through `passwordReauthRefusal` (`app/src/lib/formErrors.ts`). That function has cases for `auth/invalid-credential`, `auth/wrong-password`, `auth/too-many-requests`, and `auth/network-request-failed`, and a `default` that renders the generic `SERVICE_PROBLEM` message. There is no case for `auth/unverified-email`. So the one error this exact sequence is guaranteed to produce on a fresh signup renders as a page that only says something went wrong, on a form whose only visible field is a password box she already typed correctly — with no path forward, because resubmitting the same password does not change whether her email is verified. This is the concrete shape of the "known disagreement between records" the map issue (#1487) already flagged between ADR-0048's three-act signup and ADR-0026's TOTP requirement: it is not just two records disagreeing on paper, it is a dead end a real Owner would hit on her first visit.

**The `getIdToken(true)` call after `enroll()` is very likely redundant, not required**, per the SDK-source finding under question 3 above — `enroll()` already updates the cached token in memory before its promise resolves. This is a minor finding, not a defect: the extra round trip costs a network call, not correctness, and the decision-4 fallback it feeds is still a reasonable guard against whatever undocumented propagation timing Identity Platform's backend actually has.

**Everything else checked lines up with the platform.** The re-authentication step (`signInWithEmailAndPassword` before `getSession()`) matches the documented recent-sign-in requirement. The challenge-every-sign-in behavior the Practice gate depends on matches the documented `auth/multi-factor-auth-required` throw. The app's own verification mechanism (`RequestVerificationHandler` / `SpendVerificationHandler` in `api/internal/staffauth/verify.go`, calling `accounts.SetEmailVerified` through the Admin SDK once the BFF's own token is spent) does correctly flip the same `emailVerified` flag the enrollment check reads — so a signup that *does* wait for her to click the email link before revisiting `/mfa/enroll` succeeds on that later attempt without any platform-side obstacle. The gap is entirely in the ordering the app puts her through on her very first Practice-scoped request, and in one missing error-message case.
