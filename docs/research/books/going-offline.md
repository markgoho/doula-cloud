## 2. What this file is for

This file is the evidence: what the book argues, page by page, with its own exceptions, what has changed since 2018, and where it is weak. It records no Doula Cloud decision; where the book touches something the repo has already decided, section 6 names the ADR or ticket, and the decision belongs to that record.

## 3. The claim

The book's thesis is that a website can gain offline capability and app-like behavior through three standard, incrementally adoptable browser technologies — HTTPS, a service worker, and a Web App Manifest — without giving up the web's own model of URL-based distribution and without being rebuilt as a client-side app (Ch. 9, pp. 121, 131, 133). A service worker is not a declarative cache-configuration file like its predecessor, AppCache; it starts as an empty script that does nothing until the developer writes instructions into it, which the author calls the price paid for "these newfound powers" (Ch. 3, pp. 25–26). Because a first-time visitor can never benefit from a service worker that is not yet installed, the technology can only ever be deployed as an enhancement layered on existing functionality — a property the author calls "a brilliant piece of design" because it removes any browser-support tradeoff (Ch. 2, p. 11). The one recipe the book builds toward, restated in different forms across five chapters, is: look in the cache, otherwise fetch from the network, otherwise show a fallback — a pattern of four repeating building blocks (an if-statement, a cache lookup, a network fetch, a cache write) that recombine into different strategies per file type or URL (Ch. 6, p. 92).

What the claim is not: it is not an argument for one correct service worker. The book states plainly that no single script is "one-size-fits-all" (Ch. 9, p. 134), and a script written for one site "might not be a good fit" for another (Ch. 5, p. 66). It is not a claim that a progressive web app must be a from-scratch, JavaScript-driven single-page app; the author states that just about any existing website can become one, by layering the three technologies onto what already exists (Ch. 9, p. 131). And it is not an unqualified endorsement of app-like behavior: the closing pages name URLs, not app-store distribution, as "the standout feature of the web," the one thing a progressive web app is argued to keep rather than hide (Ch. 9, pp. 133–134).

## 4. The argument, chapter by chapter

### Foreword (Aaron Gustafson, unnumbered)

Gustafson frames the network as the web's "Achilles' heel" and service workers as the long-sought answer to the web's "complete dependence on the network," after earlier partial attempts — browser caching, AppCache, Local Storage — fell short (Foreword). He credits Keith with turning "heady concepts" into approachable prose and code.

### Chapter 1: Introducing Service Workers (pp. 1–9)

A service worker is a script with no DOM access that intercepts network requests before they reach the server; the author compares it in turn to a cookie, a virus, and a toolbox, but explicitly not to a duck-billed platypus (Ch. 1, pp. 3–6). Two policies gate installation: same-origin and HTTPS-only, quoting the spec's own warning that an unverified service worker risks "a bad eternity" for the site it impersonates (Ch. 1, p. 7). HTTPS also unlocks other secure-only APIs (geolocation, payments, notifications) and is worth adopting even without a service worker; the one exception to the HTTPS-only rule is `localhost`, which lets a developer test without deploying (Ch. 1, pp. 7–8). Certbot is offered as the way to get a free certificate, with the caveat that shared hosting may not allow the SSH access it needs (Ch. 1, pp. 8–9).

### Chapter 2: Preparing for Offline (pp. 10–24)

Because a first visit can never be served by a not-yet-installed service worker, the technology is necessarily additive: non-supporting browsers are unaffected, and supporting ones are "rewarded" (Ch. 2, p. 11). Registration is shown two ways — a future declarative `<link rel="serviceworker">`, not yet supported at the time of writing, and the JavaScript `navigator.serviceWorker.register()` used throughout the book, wrapped in feature detection because HTML silently ignores what it doesn't understand while JavaScript throws and halts (Ch. 2, pp. 12–13). The chapter teaches JavaScript fundamentals needed later — objects, properties, methods, and promises' `then`/`catch` pattern — through the registration call itself, and demonstrates with a console log that `register()` is asynchronous: code after it can execute first (Ch. 2, pp. 13–22).

### Chapter 3: Making Fetch Happen (pp. 25–39)

The chapter opens with a history of AppCache, the earlier attempt to "solve the offline problem," which the community now avoids discussing after its manifest-file model repeatedly broke sites through uncontrollable cache invalidation (Ch. 3, pp. 25–26). The root problem, in the author's telling, was a spec built by imagining developer needs rather than consulting developers; service workers instead follow the "extensible web" philosophy of giving developers low-level primitives and letting them write explicit instructions, quoting the Extensible Web Manifesto's call to "tighten the feedback loop" between standards editors and developers (Ch. 3, p. 26). The rest of the chapter builds the `fetch` event listener and the Fetch API, ending with a custom offline `Response` object — including the discovery that a `Response` must declare a `Content-type` header or the browser renders HTML as plain text (Ch. 3, pp. 27–39).

### Chapter 4: Cache Me if You Can (pp. 41–61)

Cookies (invented by Netscape's Lou Montulli) let a server remember a visitor; caching lets a browser remember a server's files (Ch. 4, p. 42). The HTTP cache is described as useful but crude — one shared pool across every site, cleaned up periodically, controlled only by server headers such as `max-age`, with cache-busting handled by renaming files (`styles-v1.css` to `styles-v2.css`) (Ch. 4, pp. 42–44). The Cache API is framed as an enhancement layered on top of the HTTP cache, not a replacement for it, giving fine-grained, named, multiple caches instead of one shared pool (Ch. 4, pp. 44–45). The chapter's central recipe follows: on `install`, open a cache and `addAll` a list of static assets, splitting must-have files (which block installation via a `return`ed promise) from nice-to-have ones; on `fetch`, check the cache first and fetch from the network only on a miss (Ch. 4, pp. 45–52). Because caches persist indefinitely, the chapter adds a `version` variable prepended to the cache name so that editing it triggers reinstallation, and an `activate` handler that deletes any cache whose name no longer matches, finishing with `clients.claim()` to take control of open tabs immediately (Ch. 4, pp. 53–60). Browsers cap the service worker script's own cache lifetime at twenty-four hours regardless of server headers, and `skipWaiting()` can bypass the "wait" step of the update life cycle entirely (Ch. 4, pp. 55–56).

### Chapter 5: Service Worker Strategies (pp. 62–78)

The recipe gains a third branch — if the file can't be fetched, show a fallback — realized as a pre-built, cached `/offline.html` page rather than an inline string (Ch. 5, pp. 62–64). The author notes Trivago's offline page offers a maze game instead of a generic dinosaur, framing a custom offline page as a branding opportunity (Ch. 5, pp. 65–66). Repeating the claim that one script "might not be a good fit" for another site, the chapter branches logic by sniffing the request's `Accept` header: HTML pages fetch the network first and fall back to the offline page; images look in the cache first, then fetch and store a copy; everything else looks in the cache first, then fetches (Ch. 5, pp. 66–77). This cache-first pattern is named **Offline First**, which the author calls "somewhat misleading" since a first visit still needs the network — but useful shorthand for treating the network itself as an enhancement (Ch. 5, p. 93).

### Chapter 6: Refining Your Service Worker (pp. 79–93)

The chapter layers refinements onto the recipes from Chapter 5: a fallback image for when neither cache nor network has one (pp. 79–80); a stale-while-revalidate pattern for images, serving the cached copy immediately while fetching a fresh one in the background to update the cache (pp. 81–82); the same idea applied to whole pages via a separate `pages` cache, populated as the visitor browses rather than at install time (pp. 82–86); and branching by URL pattern (with a regular expression) so that, for example, article pages can be served cache-first for speed while the rest of the site stays network-first for freshness (pp. 86–91). The chapter names the repeating shape underneath all of this — if-statements, cache lookups, network fetches, cache writes — as reusable "patterns," like pieces of LEGO (p. 92). It closes by introducing `async`/`await` as an alternative way to write the same promise-based logic, explicit that it doesn't provide "any new functionality" and is a matter of taste, not correctness (pp. 101–106).

### Chapter 7: Tidying Up (pp. 94–107)

There is no fixed storage quota for service worker caches; several browser technologies (`localStorage`, IndexedDB, the Cache API) share a device's available space, "sometimes gigabytes," and the shared HTTP cache is pruned before a dedicated service worker cache is (Ch. 7, p. 94). The chapter builds a `trimCache` function that caps a cache's size by deleting its oldest entry (index zero) in a loop until the count is under a limit, triggered from the page via `postMessage` after load rather than from `fetch` or `activate`, to avoid interfering with either (pp. 95–99). It then generalizes the repeated fetch-open-cache-put sequence into a reusable `stashInCache` function, and uses it to argue for `async`/`await` as a way to avoid deeply nested `then` chains once functions are reused this way (pp. 99–107).

### Chapter 8: The Offline User Experience (pp. 108–119)

The fallback offline page can do more than apologize: it can list previously visited, now-cached pages by opening the pages cache and looping through its keys to build links (Ch. 8, pp. 108–109). The chapter then builds an explicit "Save for Offline" button, injected via feature detection, whose click handler opens a `savedpages` cache and calls `cache.add()` on the current URL, giving the visitor Instapaper/Pocket-like control rather than only an accumulated browsing history (pp. 110–113). Because the Cache API alone can't store metadata, `localStorage` — simpler than IndexedDB, though synchronous — holds a JSON-encoded title and description per URL, keyed by the same URL used in the cache, so the offline page can render a readable list instead of bare links (pp. 113–117). The chapter closes by naming further possibilities left as an exercise (caching a saved page's images) and foreshadowing native-app-like capabilities: Background Sync and Notifications let a service worker act "even when the browser isn't open" (p. 119).

### Chapter 9: Progressive Web Apps (pp. 120–135)

Quoting Frances Berriman's own framing of the 2015 coinage — that the name serves "your boss," "your investor," and "your marketeer," not the developer — the author treats "progressive web app" primarily as a marketing label over a precise, three-part technical definition: HTTPS, offline support via a service worker, and a Web App Manifest file (Ch. 9, pp. 120–121). The manifest is built field by field — `lang`, `name`, `short_name` (kept under twelve characters), `description`, `theme_color`, `background_color`, `start_url`, `display` (`browser`, `minimal-ui`, `standalone`, or `fullscreen`, with a warning to weigh what a hidden address bar costs visitors), and an `icons` array with at least one 512px image (pp. 122–128). Chrome's install prompt, at the time of writing, required HTTPS, a manifest with `name`/`short_name`, an icon at least 144px square, a `display` of `minimal-ui` or higher, a service worker that shows something offline, and more than one visit in a short span (pp. 129–130). The chapter closes on two arguments: "progressive" means responsive and usable by everyone regardless of device, not a mobile-only silo — the Washington Post's early PWA, which turned away capable desktop browsers, is the counter-example — and the author lays out a layered build order (content, then the simplest working technology, then service-worker enhancement), not JavaScript-first (pp. 130–133). URLs, not app-store gatekeeping, are named as the web's one advantage worth protecting in this native-app-influenced future (pp. 133–135).

## 5. The book's own exceptions

These are the places the author limits his own claim, admits a counter-case, or says a rule does not apply.

- **HTTPS is not always reachable.** Certbot makes a free certificate easy "if you have SSH access to that machine," but on shared hosting "that might not be possible," leaving only pestering the host or switching providers (Ch. 1, pp. 8–9).
- **Scope.** A site can register more than one service worker with different scopes, but the book expects "most websites" to need only one, for the whole site (Ch. 2, p. 18).
- **No universal strategy.** The whole of Chapter 5 is framed as non-prescriptive: fetch-handling logic is left to a "case-by-case basis," and a script written for one site "might not be a good fit" for another (Ch. 5, p. 66).
- **"Offline First" is a misleading name by the author's own admission** — a visitor must reach the site online at least once before any offline benefit exists, so the term is "useful shorthand," not a literal description (Ch. 5, p. 93).
- **Caching an entire site is "somewhat presumptuous."** It can work for a self-contained thing like a game or a rarely updated book, but the author weighs this against how little "room on their devices" most people have to spare (Ch. 5, p. 93).
- **Not every browser refresh bypasses the service worker the same way.** A hard refresh (Shift-reload) skips it entirely, which the reader is warned about twice, once while testing and once while debugging (Ch. 3, p. 32; Ch. 4, p. 56).
- **Copied boilerplate need not be understood.** Install/activate code stays "largely unchanged from project to project," and the author admits his own cache-cleanup code is something he doesn't "understand... myself" (Ch. 4, p. 60).
- **`async`/`await` is a style choice, not an improvement in capability.** A reader content with the "old-school style" of promises is told nothing obliges a rewrite (Ch. 6, p. 106).
- **Display mode is a tradeoff, not a default choice.** `standalone` or `fullscreen` make a site feel native but remove the address bar and back/forward controls, so the author asks the reader to weigh what visitors "might end up missing out on"; `fullscreen` is reserved for cases like a game that needs the whole screen (Ch. 9, pp. 125–126).
- **Progressive web apps built as mobile-only silos are a mistake the book itself documents**, not a pattern it endorses — many early examples were made to "only work on mobile devices," against the book's own definition of "progressive" (Ch. 9, p. 131).

## 6. Where the book touches this repo

Each entry is the claim and its page, then the record that decided the matter.

1. **A service worker can "only be deployed as an enhancement" because a first visit is never served by one not yet installed (Ch. 2, p. 11).** Record: [#61](https://github.com/markgoho/doula-cloud/issues/61), whose acceptance criteria scope `app/`'s one service worker to push events only, "no offline caching/precaching"; `app/src/service-worker.ts`'s header comment names "no offline caching, no asset precaching, per the ticket's explicit scope."
2. **An empty service worker script does nothing by default, unlike AppCache's implicit, declarative caching (Ch. 3, pp. 25–26).** Record: the same [#61](https://github.com/markgoho/doula-cloud/issues/61) scope — `app/src/service-worker.ts` registers `activate`, `push`, and `notificationclick` handlers and no `fetch` handler, so it performs none of the caching Chapters 4–6 build.
3. **No script is "one-size-fits-all"; each is written to match the site's own profile (Ch. 9, p. 134).** Record: [#61](https://github.com/markgoho/doula-cloud/issues/61)'s scope decision is exactly this kind of site-specific choice, made for a messaging/records app rather than a content site.
4. **Background Sync and Notifications let a service worker act "even when the browser isn't open" (Ch. 8, p. 119), named as a frontier beyond the book's own recipe.** Record: [ADR-0002](../../adr/0002-message-transport-push-triggered-fetch.md), which builds this — a content-free Web Push notification wakes the service worker, which triggers a fetch against the BFF for the message content; `app/src/service-worker.ts`'s `push` and `notificationclick` handlers are the implementation.
5. **A progressive web app is defined by three things: HTTPS, offline support via a service worker, and a Web App Manifest (Ch. 9, p. 121).** Record: [ADR-0026](../../adr/0026-two-populations-two-sign-in-methods-and-one-token-table.md) states "Doula Cloud is a PWA" while reasoning about Apple sign-in; `app/static/manifest.webmanifest` exists and is linked from `app/src/app.html`, and `app/src/service-worker.ts` exists but is scoped to push only (entry 1) — two of the three conditions are met, and the third, offline support, is the one [#61](https://github.com/markgoho/doula-cloud/issues/61) deliberately left out.
6. **The manifest's fields include `lang`, `name`, `short_name`, `description`, `theme_color`, `background_color`, `start_url`, `display`, and an `icons` array with at least one 512px image (Ch. 9, pp. 122–128).** Record: the live `app/static/manifest.webmanifest` sets `name`, `short_name`, `start_url`, `display: "standalone"`, `background_color`, `theme_color`, and one SVG icon (`sizes: "any"`); it has no `lang` or `description` field.
7. **"Save for Offline" and Chrome's homescreen install prompt both depend on the service worker showing something when offline (Ch. 8, pp. 110–117; Ch. 9, pp. 129–130).** Record: [ADR-0023](../../adr/0023-layout-is-intrinsic-and-320px-is-the-floor.md) and [ADR-0024](../../adr/0024-layout-is-intrinsic-and-320px-is-a-conformance-commitment.md) both name "install prompts, camera or offline affordances" as outside the layout ADR's own scope, calling them "a separate effort."

## 7. What has changed since publication

Each figure, tool, or claim the book leans on, checked in September 2026 against a later source. "Unchecked" means no source could be reached that confirms or refutes the figure.

- **Service worker browser support "not exactly a field of green" (Ch. 2, pp. 10–11, Fig 2.1).** Reversed. caniuse.com's current data puts global support at 96.88%, with Chrome, Firefox, Edge, and Opera fully supporting it and Safari (including iOS Safari, from version 11.3) supporting it as well; only Internet Explorer and Opera Mini lack it (caniuse.com/serviceworkers).
- **AppCache as the deprecated predecessor the community avoids naming (Ch. 3, pp. 25–26).** The outcome is now total, not partial: caniuse.com's AppCache entry shows it removed from Chrome 85+, Firefox 84+, Safari 15+, and Edge 85+, with the page itself stating the technology "is being deprecated in favor of Service Workers" (caniuse.com/appcache).
- **Chrome's homescreen install-prompt criteria (Ch. 9, pp. 129–130): HTTPS, a manifest with `name`/`short_name` and a 144px+ icon, `display` of `minimal-ui` or higher, an offline-capable service worker, and more than one visit.** Changed. web.dev's current installability guidance requires one click or tap plus at least thirty seconds of engagement — not multiple visits — icons of at least 192px and 512px, not 144px, and does not name a fetch-handler or offline-content requirement at all (web.dev/articles/install-criteria).
- **`python -m SimpleHTTPServer 8000` as the localhost quick-start (Ch. 1, p. 8).** Renamed, not removed: Python 3's official documentation confirms `SimpleHTTPServer` became part of the `http.server` module, and the equivalent command is now `python -m http.server` (docs.python.org/3/library/http.server.html).
- **Certbot as the free-certificate tool, run by the EFF (Ch. 1, pp. 8–9, Fig 1.3).** Holds: certbot.eff.org still describes itself as a project of the Electronic Frontier Foundation offering free HTTPS certificates.
- **The Web App Manifest as a specification "being standardized" by the W3C (Ch. 9, p. 122).** Still true in the most literal sense, and still incomplete: the W3C's own page for the specification lists it as a Working Draft under the Web Applications Working Group, dated 2026, and states plainly that "this specification is not stable" (w3.org/TR/appmanifest/).
- **Workbox, "a collection of scripts and tools for going offline" (Resources, p. 138).** Live and maintained, under new ownership: the project's own README states that "Chrome's Aurora team will be the new owners of Workbox," with no archived or deprecated notice.
- **PWA Builder as a manifest/service-worker starter tool (Resources, p. 138).** The site is live at pwabuilder.com; its current maintainer could not be confirmed from the page's visible content, so that detail is unchecked.
- **Frances Berriman is credited with coining the term "progressive web app" in 2015 (Ch. 9, p. 120).** Complicated by the source itself: Berriman's own post says she "accidentally helped name this thing" and credits the concept as core to the work of Alex Russell, her Chrome-team colleague — crediting the term to the two of them jointly rather than to her alone (fberriman.com/2017/06/26/naming-progressive-web-apps).
- **Ethan Marcotte's offline page showing metadata for saved articles (Fig 8.2, p. 117; Resources, p. 138).** Unchecked: the live URL returned an HTTP 403 to an automated fetch.
- **Mike Riethmuller's offline page (Fig 8.1, p. 109; Resources, p. 138) and Trivago's offline maze (Fig 5.2, pp. 65–66).** Unchecked: no source was reached for either within this session's research budget.
- **Lighthouse as a PWA-testing tool "bundled into Chrome's Developer Tools" (Resources, p. 138).** Unchecked: no source was reached for its current audit categories within this session's research budget.

## 8. Where the book is weakest

- **iOS Safari is never named.** The word "iOS" does not appear in the book's discussion of service workers, Push, or homescreen installation; Chapter 8 names Background Sync and Notifications as coming native-app-like capabilities (p. 119) without noting that Apple's mobile browser was, at the time of writing, the platform where those capabilities were least available. Section 7 found the Push API reached only partial iOS Safari support in version 16.4, about five years after publication.
- **Every debugging walkthrough is Chrome-specific.** The Application panel, the `skipWaiting` link, the Offline checkbox, and the Update-on-reload option are all Chrome DevTools features (Ch. 3, pp. 27–32; Ch. 4, p. 56); the book gives no equivalent workflow for Firefox or Safari, though it does note in passing that service workers work the same way "conceptually" across browsers.
- **The homescreen install criteria are presented as a stable definition rather than one vendor's heuristic.** Chapter 9 lists Chrome's specific conditions — a 144px icon, more than one visit — as settled facts (pp. 129–130) without flagging that Google alone controlled them; section 7 found they have since changed substantially.
- **Storage limits are described only in the vague terms the author has.** "Sometimes gigabytes" of shared device storage (Ch. 7, p. 94) carries no citation and no discussion of what a quota-exceeded error looks like or how the chapter's own trimming code would behave if one occurred.
- **No discussion of testing.** The book teaches production-shaped code — cache versioning, activation cleanup, fallback strategies — but never once mentions writing an automated test for a service worker script, unit or otherwise.
- **The author states he doesn't fully understand his own code.** Of the cache-cleanup logic in the `activate` handler, he admits he doesn't "understand it myself" (Ch. 4, p. 60), and separately tells the reader not to worry about understanding install/activate boilerplate at all — an honest admission, but one that leaves that code's correctness resting on the reader's trust rather than the reader's or the author's own comprehension.
- **A race condition is flagged and only partly resolved.** The image-caching recipe notes that the service worker "might 'power down'" before a cached copy finishes writing, and patches this with `waitUntil` (Ch. 4, p. 73), but the book never discusses what happens to a large asset whose write still hasn't finished when the browser terminates the worker regardless.
