## 2. What this file is for

This file is the evidence: what the book argues, chapter by chapter, with its own exceptions, what has changed since it was written, and where it is weak. It records no Doula Cloud decision; where the book touches something the repo has already decided, section 6 names the ADR, ticket or component, and the decision belongs to that record.

## 3. The claim

The book's thesis, in the author's frame, is that the code of the web is the code of communication, interaction and "most of all accommodation", and that every line in the book serves one goal, interfaces usable by "more and different people" (Introduction, p. 6). Accessibility is "only a part of inclusive design": a control also has to make sense to users and play "an unambiguous role" in the interface (Toggle buttons, p. 13). Inclusion is an "equivalent experience" for different users, not the same one (A Todo List, p. 52), and "a decent experience" for as many people as possible rather than one experience for all (A Content Slider, p. 213). The method is the same in every chapter: start from standard HTML elements and the browser behaviors they carry, add WAI-ARIA "as a progressive enhancement" for states HTML lacks (Toggle buttons, p. 15), let "form follow function" so that the attribute that communicates state is also the styling hook (Toggle buttons, p. 17; Collapsible Sections, p. 161), and add JavaScript only where the interaction needs it, while never trading usability for a JavaScript-free solution, which the author calls "vanity" (Menus & Menu Buttons, p. 94). An inclusive component is "Clear and easy to use", interoperable across inputs and outputs, "Responsive and device agnostic", "Performant", and "Under the user's control" (A Content Slider, p. 182), and the author's mantra is that whatever cannot be done efficiently is not done "at all" (A Theme Switcher, p. 115).

The author says what the claim is not. It is not computer science: "I am not a computer scientist", HTML is "the code of writers" and CSS that of graphic designers (Introduction, pp. 4, 6). It is not a framework choice: the user does not care whether it is "Backbone or React" (A Todo List, p. 35), and the demos move between Vue, React, plain JavaScript and web components. It is not a set of exemplars: the components are not "just-copy-and-paste exemplars" (Cards, p. 313), and there is "no one way" to build any of them (Toggle buttons, p. 8). It is not a recommendation to build the components at all: four chapters open by arguing against the component they then build (Tooltips & Toggletips, p. 113; Tabbed Interfaces, p. 151; A Content Slider, p. 214; Modal Dialogs, p. 264). And it is not a rulebook: going against "standardized authoring advice" is fine where research shows a pattern failing users (Tabbed Interfaces, p. 143), and inclusive design has "no right or wrong" (Tabbed Interfaces, p. 151).

## 4. The argument, chapter by chapter

### Introduction: A personal note (pp. 4–7)

The author's frame is that the web is inaccessible not because accessibility is hard but because it is "the code where humans and computers meet", a position most programmers are neither taught nor inclined to take (Introduction, p. 6). The "Full Stack Developer" who does all the code cannot do it all well, so hiring generalist coders yields "terrible products and interfaces" (Introduction, pp. 5–6). The book is dedicated to the artists, designers and humanities scholars who write code for the web and, in the same breath, to full stack developers who may have "bitten off more" than they can chew (Introduction, p. 6). The evidence is autobiographical: the author learned to code because he worked with the web (Introduction, p. 6).

### Toggle buttons (pp. 8–34)

An unstyled checkbox is "a perfectly serviceable on/off switch": screen readers announce label, role and state ("Notify by email, checkbox, unchecked") and the state change needs no JavaScript (Toggle buttons, pp. 9–10). A radio pair under a `fieldset` and `legend` gives an explicit on/off, and JAWS and NVDA prepend the group label (Toggle buttons, pp. 11–12). The chapter's turn is that form elements carry a "longstanding association" with data collection: a person checking a box may suspect she is choosing "a value for submission", so a setting is better as a `button` with `aria-pressed` (Toggle buttons, pp. 13–15). ARIA states need an explicit true or false; the absence of the attribute means the unpressed state is not communicated; a button inside a form needs `type="button"` or some browsers submit (Toggle buttons, p. 15). NVDA reads a pressed button as "Notify by email, toggle button, pressed" (Toggle buttons, p. 17). Styling hangs off the state attribute itself ("form should follow function"), with an inset box shadow for pressed; box shadows vanish in Windows High Contrast, so the author inserts an explicit check mark there, and calls techniques that also work in High Contrast Mode "generally better" (Toggle buttons, pp. 17–20). Green for on and red for off is fine as long as color is not the only signal, which fails WCAG 2.0 1.4.1 (Toggle buttons, p. 20). Focus styles are required on every interactive component and "should not affect layout"; `outline` draws a box, so a box shadow follows curved corners, plus a transparent outline that becomes visible in High Contrast Mode (Toggle buttons, pp. 20–21). The rule for changing labels: "never change pressed state and label together", because a "pause" label in a pressed state reads as contradiction (Toggle buttons, pp. 22–25). Voice-control users say what they see, so a play/pause icon is better with a changing label than a changing state (Toggle buttons, p. 24). `aria-label` is not translated by Google's and Microsoft's translation services; a visually hidden span is (Toggle buttons, pp. 25–26). Auxiliary "on/off" labels in a settings list use `aria-labelledby` to a description span and the `switch` role with `aria-checked`, which some screen readers vocalize as "on"; ChromeVox did not recognize `switch` at the time of writing (Toggle buttons, pp. 27–32). The checklist: use checkboxes for toggles only where the user will not think she is "submitting data"; use buttons, not links; do not change label and state together; meet contrast requirements (Toggle buttons, pp. 33–34).

### A Todo List (pp. 35–63)

TodoMVC's implementations all show the delete control only on hover, "an entirely inaccessible feature by keyboard" (A Todo List, pp. 35–36). Every major section is introduced by a heading, and heading level "is actually a question of belonging", not importance; screen readers navigate by heading, and the author's React Context approach automates levels in a design system (A Todo List, pp. 37–39). A `section` adds little unless labeled by its own heading through `aria-labelledby`, which then announces "My Todo List region" on entering by focus (A Todo List, pp. 39–40). Lists are announced and enumerated ("list of three items") (A Todo List, p. 40). Empty states are neglected "at your peril", because new users are among the most vulnerable, and the `:empty` pseudo-class reveals the empty state without querying data (A Todo List, pp. 41–43). A `form` element is needed so that Enter submits, and Léonie Watson reports Firefox plus JAWS needs it for text inputs (A Todo List, pp. 44–45). A placeholder is not a label: placeholders disappear on focus and under autocomplete; a visible label sits above or to the left of the input "in almost all cases", with the exception of an input/submit pair whose button label is descriptive enough; "E.g." as a placeholder prefix stops it reading as a value; default placeholder gray fails WCAG 1.4.3 (A Todo List, pp. 45–48). Disabling the submit button until the input is valid works but unfocusable buttons are often missed, and it is "usually better" to let the person press the button and then report any errors (A Todo List, p. 49). Feedback after adding an item goes to a live region (`role="status"` plus `aria-live="polite"`, both for compatibility) rather than a focus move, and the visual list update and the announcement are "already equivalent", so the region is visually hidden (A Todo List, pp. 50–52). In testing at Bulb, some users hearing a live region announcement thought their focus had moved to a new element (A Todo List, p. 53). Checkboxes are right for done items because "you check them off", styled through `:checked` and a sibling combinator (A Todo List, pp. 53–55). A delete button gets a visually hidden label, the SVG gets `focusable="false"`, and icons repeated many times use `<use>` to keep the DOM small (A Todo List, pp. 55–57). Icons without text "risk being misapprehended"; where deletion is critical "a confirmation dialog should be provided" (A Todo List, p. 57). Deleting the focused element leaves browsers to guess where focus goes; the fix is to focus the list heading with `tabindex="-1"` and no focus style, then announce "[item] deleted" politely so the heading is read first (A Todo List, pp. 58–62). A focusable non-interactive element fails WCAG 2.4.3 unless focus is moved by script (A Todo List, pp. 59–60).

### Menus & Menu Buttons (pp. 64–94)

Naming is the argument: "dropdown" covers a `select`, a navigation submenu and a true menu, and giving different things the same name leads to "a semantically and behaviorally inappropriate component" (Menus & Menu Buttons, pp. 64–65). Navigation is nested lists of links, and ARIA menu roles do not belong there, because ARIA menus are for "application behavior", not navigation, and a top-level link stays usable as a link (Menus & Menu Buttons, pp. 65–67). Hover submenus fail on touch, where the first press must both open and follow; the fix is an in-page table of contents on each top-level page, which the author calls "a superior way" of navigating, used by GOV.UK and Wikipedia (Menus & Menu Buttons, pp. 68–72). Touch cannot be detected by screen size, since some of the largest screens are touch screens (Menus & Menu Buttons, p. 69). A table of contents is a `nav` labeled by its heading through `aria-labelledby`, and same-page links get `tabindex="-1"` on the target so focus follows (Menus & Menu Buttons, pp. 70–72). Information architecture is "a big part of inclusion" (Menus & Menu Buttons, p. 73). A hamburger button identifies as a button with `aria-expanded`, sits inside the `nav` so the landmark is not empty, and the list it reveals is next in focus order; `aria-controls` is supported only in JAWS (Menus & Menu Buttons, pp. 73–78). Without JavaScript the navigation is "just… some navigation" (Menus & Menu Buttons, pp. 74–75). `menuitem` roles on links would override the link role, so the navigation button is "a kind of hybrid component" (Menus & Menu Buttons, pp. 79–80). A `select` used as navigation triggers an unexpected change of context, a WCAG 3.2.2 failure (Menus & Menu Buttons, pp. 80–81). A true menu, for "choosing options in the subject application", carries `aria-haspopup="true"`, `aria-expanded`, `role="menu"`, `menuitem` children, and the focus behavior of WAI-ARIA Authoring Practices 1.1: arrow keys move between items with roving `tabindex="-1"`, Escape closes and refocuses the button, and a project that does not "closely imitate a desktop application" is very unlikely to want an ARIA menu at all (Menus & Menu Buttons, pp. 81–85). The checkbox hack for a JavaScript-free menu cannot deliver the focus behavior (Menus & Menu Buttons, pp. 86–88). `menuitemradio` with `aria-checked` persists a choice, and opening focuses the checked item (Menus & Menu Buttons, pp. 91–93). The component ships with Hugo Giraudel as inclusive-menu-button, built on a11y-dialog (Menus & Menu Buttons, p. 94).

### Tooltips & Toggletips (pp. 95–114)

The `title` attribute, quoting The Paciello Group, hides content from mobile, tablet, assistive-technology and keyboard-only users alike; the author's answer is a "permanently visible label" (Tooltips & Toggletips, p. 96). Tooltips exist to supply information missing because an icon stands alone; text beside icons is the answer "most of the time", and there is always room for text "if you make it" (Tooltips & Toggletips, pp. 97–98). Where a tooltip is the primary label, `aria-labelledby` connects it, with `role="tooltip"` on the target for reliability; where it is auxiliary, `aria-describedby` is used and the button keeps a visually hidden text label; descriptions are announced last, after a pause (Tooltips & Toggletips, pp. 98–103). A `title` identical to the link text is "completely redundant" (Tooltips & Toggletips, p. 101). A notification count joins the label through multiple `aria-labelledby` ids, read as "3 notifications" (Tooltips & Toggletips, pp. 101–102). Tooltips appear on focus as well as hover; on touch, focus and active coincide, so the tip shows only while the button is pressed, and one alternative is showing labels inline for newcomers and icons alone for established users (Tooltips & Toggletips, pp. 104–105). A toggletip is a button whose only job is to reveal a bubble; it must not use `aria-describedby`, because a screen reader user would already have the information and the press would "appear not to do anything"; instead an empty live region is populated on click, after a short delay so repeated clicks re-announce (Tooltips & Toggletips, pp. 106–110). The better baseline is the content inline, with the toggletip button created by script (Tooltips & Toggletips, p. 111). A script can refuse to run on a non-`button` and a CSS selector can paint an error outline with a made-up `ERROR` property visible in dev tools (Tooltips & Toggletips, pp. 111–113). Conclusion: tooltips are rarely needed, and toggletips are "a complex way" of delivering what could be prose (Tooltips & Toggletips, p. 113). Do not put interactive content in either (Tooltips & Toggletips, p. 114).

### A Theme Switcher (pp. 115–130)

Theme options are "nice-to-haves" that satisfy the Offer choice principle only if built efficiently; separate stylesheets are a performance and maintenance cost (A Theme Switcher, pp. 115–116). A low-light "night mode" is one of the few themes that "adds real value", including for migraine and light sensitivity (A Theme Switcher, p. 116). The implementation is `filter: invert(100%)` on `html`, a stated light `background-color`, `background-color: inherit` as a low-specificity fallback for children, and a double inversion on raster `img` elements so photographs are not negatives, "153 bytes uncompressed", shown applied to The Boston Globe, The Independent, The New York Times and Private Eye (A Theme Switcher, pp. 116–119). The switch is a React toggle button with `aria-pressed`, whose visible "on"/"off" text is hidden from assistive technology so it cannot contradict the state (A Theme Switcher, pp. 119–121). The preference persists in `localStorage`; Chrome needed the `style` text rewritten to repaint; the component renders only where `filter` is supported, by feature detection and without Modernizr (A Theme Switcher, pp. 122–125). Windows High Contrast Mode: no background images as content, `currentColor` for SVG fill and stroke, a transparent border on buttons that appears under the theme, and the `-ms-high-contrast` media query for special cases (A Theme Switcher, p. 127). An operating-system dark mode is honored by default through `prefers-color-scheme: dark` when nothing is stored (A Theme Switcher, p. 128). The switch belongs in a landmark other than `main`, in the same place on every page, per the Be consistent principle (A Theme Switcher, p. 129).

### Tabbed Interfaces (pp. 131–151)

Most basic interactions show or hide something, and the boundaries between tab panels, application views and document fragments are "not as clearly defined" as people pretend (Tabbed Interfaces, p. 131). The embryonic tabbed interface is a table of contents with same-page links to sections; `:target` can show only the chosen section, but that hides the rest from assistive technology and breaks links to subsections, and a table of contents that controls section visibility is unconventional and avoided (Tabbed Interfaces, pp. 132–134). A true tabbed interface is "a paradigm imported from desktop applications"; what makes it one is "the ergonomics of its keyboard behavior", and the ARIA semantics exist to tell screen reader users which keyboard behaviors to expect (Tabbed Interfaces, p. 134). The structure is `role="tablist"`, `role="tab"` with `aria-selected`, `role="tabpanel"` labeled by its tab through `aria-labelledby`, `role="presentation"` on the list items, `hidden` on inactive panels, arrow keys with wrap-around and `tabindex="-1"` on unselected tabs so Tab moves into the panel; a screen reader says "[tab label], selected, tab, 2 of 4" (Tabbed Interfaces, pp. 135–141). Then the problems: testing cited in "Danger! ARIA tabs" and a workshop session run by Hidde de Vries found that users, including "a blind, tech savvy user", did not know to use arrow keys and expected Tab; a screen reader user cannot move into a panel by focus unless it holds interactive content; `tabindex="0"` on a panel breaks VoiceOver and fails WCAG 2.4.3; `aria-controls` works only in JAWS (Tabbed Interfaces, pp. 141–143). The author's advice to clients: no tabbed interface with more than four tabs, let tabs take focus by Tab key, and focus the panel on click; the BBC GEL tabs do this after "extensive user testing" (Tabbed Interfaces, p. 143). "Responsive design is inclusive design": full-page zoom triggers breakpoints as narrowing does; below the breakpoint the tabs become a single column, still marked; converting to an accordion is complexity "just not worth it"; the author's preference is to not run the enhancement at narrow widths and leave the table of contents (Tabbed Interfaces, pp. 143–146). Single-page application views are not tab panels: use links, which "will navigate the user"; manage focus onto the view's heading or a labeled region; update the `title` with the view name; centralize this in the router, and Reach Router "comes highly recommended" (Tabbed Interfaces, pp. 146–150).

### Collapsible Sections (pp. 152–180)

The collapsible section is "the most rudimentary" interactive pattern, and in 2018 it had no consistent native implementation across browsers, which makes it the "hello world" of ARIA (Collapsible Sections, p. 152). Without JavaScript it "is simply a section" under a subheading (Collapsible Sections, p. 153). Collapsing gives an overview and keeps hidden content out of the focus order (Collapsible Sections, pp. 153–154). The control is a `button` placed inside the heading, so a screen reader hears "My section, button, heading level 2"; converting the heading with `role="button"` would destroy the heading (Collapsible Sections, pp. 154–156). `aria-expanded` goes on the control, not the content, because state is communicated through the control that switches it; `aria-haspopup` does not apply and `aria-controls` is not needed when the content follows in source (Collapsible Sections, pp. 156–157). The button inherits the heading's look and gets a plus/minus SVG made of two `rect` elements, `focusable="false"`, with the vertical strut hidden by `[aria-expanded="true"]`: tying state to its visual representation is "a very good thing", and the author rejects the "absolute separation" of HTML semantics from CSS (Collapsible Sections, pp. 157–161). `fill="currentColor"` makes the icon follow High Contrast themes (Collapsible Sections, p. 161). A progressive script can add the buttons to plain prose after the fact, since small interactions do not warrant "large libraries" (Collapsible Sections, pp. 164–165). The chapter's main build is a `<toggle-section>` web component with Shadow DOM, a `<slot>`, a heading level copied from the Light DOM heading's tag name, `role="region"` for a navigational cue and a `:defined` styling hook, and an `open` attribute tethered to `aria-expanded` through `attributeChangedCallback`; where custom elements are unsupported the element "is treated like a mere `div`" (Collapsible Sections, pp. 166–176). The author notes web components are limited in "data binding and state" but that native code makes a design system more "interoperable, reusable, and future proof" (Collapsible Sections, p. 167). Expand/collapse all is two grouped buttons in a list, not one toggle, because the initial state of every section is unknown (Collapsible Sections, pp. 176–177). URL hashes open the matching section on load and `history.replaceState` tracks the open one (Collapsible Sections, pp. 178–179). The checklist adds: do not override "important element roles", and give sections labels more descriptive than "Section 1" (Collapsible Sections, p. 180).

### A Content Slider (pp. 181–214)

Carousels are not inherently bad, but there is "a culture of making them bad", and the right solution is often in "what you don't do" (A Content Slider, p. 181). WCAG 2.2.2 requires a pause control for movement, which the author finds "not good enough": an inclusive carousel never moves "without the user's say-so", hence "content slider" (A Content Slider, pp. 182–183). Browsers are "multimodal by default", so the MVP is `overflow-x: auto` on a row of content, scrolled by wheel, trackpad or swipe, animated by the browser rather than "a JavaScript function fired every five milliseconds" (A Content Slider, pp. 183–184). Keyboard users need the region focusable with `tabindex="0"`, which then requires a role and a label ("gallery", `role="region"`, `aria-label`), a focus style, a styled WebKit scrollbar for affordance, and an instructions element ("scroll for more") revealed on hover or focus and joined by `aria-describedby`; "If in doubt, spell it out" (A Content Slider, pp. 185–192). Touch is detected by the first `touchstart` event, never by device, and the instruction becomes permanent (A Content Slider, p. 193). Full-width slides use Flexbox and `calc` to keep image and caption within a fixed height (A Content Slider, pp. 194–197). Citing shouldiuseacarousel.com, where 1% of visitors clicked a carousel feature and 89% of those clicks were on "the first position", later images load through `IntersectionObserver` with a data-URL SVG placeholder, `noscript` fallbacks, and a `<noscript>` trick by Rik Schennink for failed JavaScript (A Content Slider, pp. 198–202). Previous and next buttons build on the scroll position rather than replacing it, sit in a list labeled "gallery controls", and are rendered only where `IntersectionObserver` exists (A Content Slider, pp. 202–205). `scroll-behavior: smooth` and CSS snap points, the latter for Safari, which then lacked `scroll-behavior` (A Content Slider, p. 206). Disabling the previous or next button at the ends is weighed and left open: disabled buttons vanish from focus order, gray-out is not read as disabled by everyone, and a scroll listener needs a debounce; `aria-disabled` plus `tabindex="-1"` keeps a disabled button discoverable (A Content Slider, pp. 207–210). Links in hidden slides get `tabindex="-1"` where the buttons exist, but `aria-hidden` is not applied, so screen reader users can traverse the list with the virtual cursor (A Content Slider, pp. 211–213). The script is "less than 2KB minified"; the first Google result for "carousel plugin" was 41.9KB and misused ARIA (A Content Slider, p. 213). The conclusion names "unprogressive non-enhancement": leaving flow content unreconstructed can beat enhancement, and the author later built a BBC carousel of cards (A Content Slider, p. 214).

### Notifications (pp. 215–233)

Statefulness is what makes a page feel like an app, and the chapter's premise is that users are "kept abreast of changing state" (Notifications, p. 215). Two kinds of message: those asking for action, which belong in a dialog with focus moved into it, and "Just FYI messages", which a notification is, and to which focus is not moved: a tool with nothing to do is not put "in the person's hand" (Notifications, pp. 216–217). A live region is a container that "sets a perimeter" around live content; `aria-live` and the live-region roles are equivalent APIs, and using both "maximizes compatibility" (Notifications, pp. 217–218). A visually hidden live region supplements an animation ("product added successfully"), and content added in the same instant as the region is unreliable (Notifications, p. 219). Most messages are for "just users", seen and heard at once (Notifications, p. 220). In a chat application, live regions in a hidden tab still speak, so `document.hidden` and the Page Visibility API switch the region off; `aria-relevant="additions"` announces only new messages in a list; a refinement announces a message only when it addresses the user directly (Notifications, pp. 220–224). Flash messages are one live region, and the first thing the author does is make sure they "can be switched off" from a settings screen, which is "just headings, subheadings, and form controls" with descriptive words, not "General" and "Content", and which uses `fieldset` and `legend`; headings may now sit inside `legend` (Notifications, pp. 225–227). Turning a type off silences it visually and aurally alike, so "We're not making assumptions" for screen reader users (Notifications, p. 228). Message types are differentiated by content, not style alone: a bold "Error:" prefix at minimum; icons need alternative text and `currentColor` (Notifications, pp. 228–229). Dismiss buttons are "not something worth encountering"; messages disappear on a timer in the author's script, and a missed message is no loss because a notification refers only to things "discoverable elsewhere" in the updated interface (Notifications, pp. 230–232). The checklist warns against `aria-atomic="true"`, visually hidden live regions used freely, announcing every change (a carousel plugin that announces each slide), and desktop notifications, which the author has never wanted from any site (Notifications, p. 233).

### Data Tables (pp. 234–263)

"Don't use tables for layout" was sound but poorly qualified; the real reason is that table markup makes screen readers "subject to this information and behavior" (Data Tables, pp. 234–235). `role="presentation"` strips a layout table's semantics; in 2018 there are better layout tools anyway (Data Tables, pp. 235–237). A table of `td` cells "does not make an accessible table"; column headers are `th` elements, which makes a screen reader read the header on entering a cell (Data Tables, pp. 237–239). Row headers are never strictly necessary but `scope="col"` and `scope="row"` make the direction explicit, with a Bulb fuel-price table as the example (Data Tables, pp. 239–240). Screen readers move between tables with the `t` key and between cells with arrows, announcing "column 3 of 4" and the header (Data Tables, p. 241). `summary` is deprecated; `caption` is visible and read on entering the table; a heading may sit inside the caption, giving "three ways to discover the table"; a table inside a `figure` with a `figcaption` needs no caption (Data Tables, pp. 241–242). A React `Table` component takes `headers` and `rows` arrays so the markup is always well formed, with prop types catching bad input; TypeScript is "a bit much" for small projects (Data Tables, pp. 243–246). Responsive tables: as Adrian Roselli noted, changing `display` on table elements removes table semantics, so the answer is a horizontally scrolling parent, `tabindex="0"` only when it overflows (otherwise a WCAG 2.4.3 failure), `role="group"` labeled by the caption, and a "scroll to see more" note in the caption (Data Tables, pp. 247–252). For very narrow viewports the data takes "a different structure": `caption` becomes `h2`, a row header `h3`, a column header `dt`, a cell `dd`, generated from the same arrays and shown or hidden at a width, with the two trees in the DOM at once as the cheaper option (Data Tables, pp. 253–256). Sorting is a button in each `th`, `aria-sort` on the header with an explicit `role="columnheader"`, a label of "sort by [column]", and three SVG arrow states; the arrow shows current state rather than the state pressing achieves, which the author flags as a Toggle-buttons violation accepted here (Data Tables, pp. 256–260). The `grid` role is for keyboard cell navigation such as a date picker, "not needed to make most tables accessible" (Data Tables, p. 260). Sorting copies the array so the mobile structure is not rebuilt (Data Tables, p. 261). Checklist: only tabular data in tables, always headers, sorting "only if needed", clear cell divisions, optional zebra striping (Data Tables, pp. 262–263).

### Modal Dialogs (pp. 264–282)

The proliferation of dialogs is "something of a scourge" (Modal Dialogs, p. 264). Quoting Therese Fessenden of Nielsen Norman Group on the cat that meows at 7am, the author accepts the analogy and adds the condition it assumes: an uninvited dialog (Modal Dialogs, pp. 265–266). A dialog opens only as "the direct result" of a user action or a critical change of system state, and only where "immediate further action" is needed, from which there is "never any need" for a non-modal dialog (Modal Dialogs, p. 267). Draggable panels are "positionable sidebars", not dialogs (Modal Dialogs, pp. 267–268). `confirm()` has every behavior of an accessible modal: focus moves in, content is announced, Escape and Cancel close, focus returns, and the page is neither identifiable nor focusable while it is open; the todo list's deletion gets one, with focus sent to the heading because the invoking button is gone (Modal Dialogs, pp. 268–270). "Questions, not statements": OK and Cancel imply a question, so text plus a close button "probably shouldn't be a dialog", and a dialog with OK and Cancel needs no close button (Modal Dialogs, pp. 270–271). Whole forms and 10,000-word terms in a modal: "Just don't"; long or complex content gets "its own page or screen"; in a single-page application routing between screens is trivial, and Bulb solved it with a timeline of steps: a `nav` with a hidden heading, an ordered list, and "(you are here)" as visually hidden text because `aria-current` was "less well supported" (Modal Dialogs, pp. 271–273). The custom modal: `role="dialog"`, `aria-labelledby` from its text, buttons that are `button` elements, created on demand (Modal Dialogs, p. 274). Modality means the rest of the page is undetectable and unclickable: `aria-hidden="true"` on a wrapper handles the first, and disabling focus by hand, a click overlay, or a focus trap (which makes the address bar unreachable by Tab) are cludges; `inert` does it all, supported only in Chrome "at the time of writing", with a polyfill (Modal Dialogs, pp. 275–278). The OK button takes focus on open, the invoker is saved and refocused on close, and the dialog is centered with `transform`, capped at the viewport with `max-height` and `overflow`, and given a `max-width` in `ch` for measure (Modal Dialogs, pp. 278–281). Usability testing taught the author that freedom to explore an interface is "not actually very popular"; a needed dialog is "as straightforward and bold as possible" (Modal Dialogs, pp. 281–282).

### Cards (pp. 283–315)

Cards have no element and no ARIA pattern, so they "require the most invention" (Cards, p. 283). A card lives in a list item, because cards rarely appear alone, and screen readers enumerate list items (Cards, p. 284). Each card has a heading of the same level; a decorative image gets `alt=""` (Cards, p. 285). Wrapping the whole card in an `a` makes the entire content the link's label, verbose and, once an author link is added, confusing; some screen readers read only the first element of a block link (Cards, p. 286). The tension is between document structure, visual layout and intuitive interaction, and the approach is structure first, CSS for layout, JavaScript "if beneficial"; the heading text becomes the primary link so every link is unique in a links list (Cards, pp. 287–288). Two ways to make the whole card clickable: the pseudo-content trick (`position: relative` on the card, an `::after` on the link stretched over it), which blocks text selection but keeps the link's context menu, or a redundant click handler on the container with a 200ms threshold to spare text selection (Cards, pp. 288–291). Affordance: `cursor: pointer` added by script so a failed script is not deceptive, `box-shadow` on hover because it follows rounded corners, and `:focus-within` to give keyboard users the card-sized style, layered so older browsers keep a basic style, with a transparent outline for High Contrast Mode and a warning not to mix `:focus-within` into a block with `:hover` (Cards, pp. 292–295). "Content tolerance": Flexbox columns, `flex-grow` on the text, `margin-top: auto` on the attribution, and the owl selector for spacing so any length of title and description holds (Cards, pp. 295–298). Cards share a height in Grid, enhanced with `@supports`, with a `max-width` of about 60 characters on the text as the single-column fallback (Cards, pp. 298–300). `object-fit: cover` handles image dimensions at the cost of cropping (Cards, pp. 300–302). An author link inside the card is a second tab stop, raised with `position: relative`, given padding for a larger hit area; on small screens the gap between cards grows so scrolling does not activate one, for people "including those with Parkinson's disease and rheumatism" (Cards, pp. 302–304). An explicit "read more" is `aria-hidden` decoration that takes the focus style through a sibling combinator and is attached to the link as a description through `aria-describedby`, which still works on a hidden element (Cards, pp. 305–308). Unique ids come from a random string, `+new Date`, or a slugify of the title, the last preferred because snapshots stay stable (Cards, pp. 309–310). A meaningful image placed before the heading is skipped by a heading-navigating screen reader, so the source puts the text first and Flexbox `order` moves the image up, which is safe because an image is not focusable (Cards, pp. 310–313). The closing checklist: list markup, tolerance of wrapping and aspect ratios, "Cards shouldn't be miniature web pages", and headings that begin sections (Cards, p. 314). "That's it. Go make a better web." (Cards, p. 315).

## 5. The book's own exceptions

These are the places the author limits his own claim, admits a counter-case, or says a rule does not apply.

- **Checkboxes as toggles.** A checkbox is "a perfectly serviceable on/off switch", and the checklist allows it where the user will not think she is "submitting data"; for done items in a list, checkboxes are "the semantically correct way" (Toggle buttons, pp. 9, 33; A Todo List, p. 53).
- **Changing the label instead of the state.** The rule to keep a consistent label and change state reverses for voice-control users, for whom changing the label is "more robust" (Toggle buttons, p. 24). The data-table sort arrow shows current state, not the state pressing achieves, which the author calls "a mistake" in many circumstances and keeps anyway because the change of direction is what communicates (Data Tables, p. 259).
- **The box-shadow toggle style.** "Offered just as one idea"; explicit on/off labels may be "better understood by more users" (Toggle buttons, p. 19).
- **Invisible labels.** A visible label is the rule "in almost all cases", but an input/submit pair or a search region can do without one when the button label is descriptive (A Todo List, pp. 45–46).
- **Disabled submit buttons.** Disabling until valid is used in the demo and then qualified: the author is "wary" of it, and finds it "usually better" to let the person press the button and then hear about errors (A Todo List, p. 49). Disabling slider buttons at the ends is left undecided: only testing "in context and with real content" answers it (A Content Slider, p. 210).
- **Live regions.** They are "a relatively new technology" and some users think focus moved; the author asks for care over where live regions and focus management are used (A Todo List, p. 53; Notifications, p. 233). Visually hidden live regions are for "a little extra aural information", and most content is to be "seen and heard" (Notifications, pp. 219, 233). A live region added and populated in the same moment "is not reliable" (Notifications, p. 219).
- **Confirmation dialogs.** Accidental deletion of a todo "is not really a critical mistake", so no dialog; a critical deletion gets a confirmation dialog (A Todo List, p. 57). The todo list "doesn't really need it" (Modal Dialogs, p. 282).
- **Focusing non-interactive elements.** Never by the user, a WCAG 2.4.3 failure; by script with `tabindex="-1"`, yes, and then without a focus style (A Todo List, pp. 59–60). Same-page link targets get `tabindex="-1"` for browsers that do not move focus (Menus & Menu Buttons, p. 72).
- **ARIA menus.** Not for navigation; only for an application that "closely imitate[s] a desktop application" (Menus & Menu Buttons, pp. 66, 81). The navigation button is a deliberate "hybrid component" with `aria-expanded` and no menu roles (Menus & Menu Buttons, p. 80). `aria-controls` "doesn't really do much harm", and "some JAWS users may expect it" (Menus & Menu Buttons, p. 78).
- **JavaScript-free solutions.** The checkbox hack is "about as close as you can get" and "may be a suitable option" for a navigation menu of links (Menus & Menu Buttons, pp. 88–89), against the checklist's rule never to trade usability for a JavaScript-free build, which is "vanity" (Menus & Menu Buttons, p. 94). Not every component can be built well without JavaScript (Menus & Menu Buttons, p. 86).
- **Tooltips.** "A last resort" where space is at a premium, the example being a WYSIWYG toolbar (Tooltips & Toggletips, p. 98). Neither tooltips nor toggletips may be "beneficial" at all (Tooltips & Toggletips, p. 113). The `title` attribute does work on form elements in screen readers, though not for touch or keyboard (Tooltips & Toggletips, p. 96).
- **Theme switching.** A nice-to-have, built only where it can be done "efficiently"; a low-light theme is the one type that "adds real value" (A Theme Switcher, pp. 115–116). The component is hidden where `filter` is unsupported, since absent beats present and broken (A Theme Switcher, p. 124).
- **Tabbed interfaces.** The WAI-ARIA keyboard pattern is "the prescribed behavior" and ergonomic only for a user who already knows "the interaction paradigm"; after testing, the author suggests letting tabs take Tab focus and focusing the panel on click, "against standardized authoring advice" (Tabbed Interfaces, pp. 141–143). No tabbed interface at all with more than four tabs (Tabbed Interfaces, p. 143). The author asks whether users need a tabbed interface "at any viewport width" (Tabbed Interfaces, p. 146). Accordions are "a safe bet" where tabs are many or unknown (Tabbed Interfaces, p. 144).
- **Web components.** Limited in "data binding and state"; the case is for "at least your functional components" (Collapsible Sections, p. 167). Automatic enhancement of prose trades control for convenience (Collapsible Sections, pp. 165–166).
- **Carousels.** "Not literally all bad"; "when used judiciously and with care" a content slider "can be quite compelling", given "a good, well-researched reason" (A Content Slider, pp. 181, 214). Stopping at the scroll-only MVP is an option the author names (A Content Slider, p. 194). Hidden slides are not `aria-hidden`, "in the interest of multimodality" (A Content Slider, p. 212). The region's `tabindex="0"` may be "an obstructive extra tab stop" once buttons exist, kept anyway (A Content Slider, p. 207).
- **Notifications.** Some screen reader and browser pairs already silence hidden tabs, but not every user has "these setups" (Notifications, p. 222). Appending the word "message" to each message is "arguably" right (Notifications, p. 224). A dialog, not a notification, is for a message that asks for action (Notifications, p. 216).
- **Tables.** Row headers are never "strictly necessary" for any data the author can think of (Data Tables, p. 239). A caption is not always needed: a preceding heading or a `figcaption` will do (Data Tables, p. 242). `role="presentation"` on a layout table is the exception to adding rather than removing semantics (Data Tables, p. 236). Keeping both table and list structures in the DOM "will bloat an already large DOM tree" for extremely large data sets (Data Tables, p. 256). Sorting is switched off by a prop where the data is small (Data Tables, pp. 256, 263). The `grid` role applies only where keyboard users must reach each cell (Data Tables, p. 260).
- **Dialogs.** The author expects a design system will need a modal dialog, and limits it to no more than "it should have to handle" (Modal Dialogs, p. 273). He hopes an interface never has to "resort to a dialog" (Modal Dialogs, p. 282). `confirm()` sacrifices "a branding opportunity", posed as a question (Modal Dialogs, p. 268).
- **Cards.** Some of the chapter's ideas may not apply to "your particular card designs" (Cards, p. 313). Whether the author link belongs in the card at all comes first: tab stops only "where beneficial" (Cards, p. 302). Text selection versus the context menu is a trade the reader makes (Cards, p. 291). The `order` trick is "unlikely to cause major comprehension problems" only because the image is not focusable (Cards, p. 313).
- **The whole book.** Rules "beget conventions", "some conventions are stronger than others", and research that shows a pattern failing users licenses departing from it (Tabbed Interfaces, p. 143). Inclusive design has "no right or wrong" (Tabbed Interfaces, p. 151).

Record: `organisms/DataTable.svelte` carries no sort control and no `aria-sort`; list pagination is open on [#446](https://github.com/markgoho/doula-cloud/issues/446).

## 7. What has changed since publication

Each browser fact, tool, figure or company the book leans on, checked in September 2026 against a later source. "Unchecked" means no source could be reached that confirms or refutes the claim, with the reason. The session's web-search allowance was exhausted before this section began, so every check below is a direct fetch of a named page.

- **`inert` is supported only in Chrome "at the time of writing", with a polyfill (Modal Dialogs, p. 278).** Changed. MDN's Baseline badge for the `inert` attribute gives April 2023 as the date it became available across browsers (developer.mozilla.org, Global attributes: inert).
- **The native modal is `confirm()`, which "is not styleable" (Modal Dialogs, pp. 268–269); the custom modal is built with `role="dialog"` because nothing else exists (p. 274).** Changed. The `<dialog>` element with `showModal()` is Baseline "since March 2022" per MDN (developer.mozilla.org, `<dialog>`); the behaviors the book lists for `confirm()` on pp. 268–269 are what `showModal()` provides, with the page behind made inert by the browser.
- **Windows High Contrast Mode is detected with the `-ms-high-contrast` media query (A Theme Switcher, p. 127).** Changed. Microsoft's Edge blog of September 17, 2020 ("Styling for Windows high contrast with new standards for forced colors") introduces `@media (forced-colors: active)` as the standard replacement and says the `-ms-` alias is kept "temporarily"; MDN lists `forced-colors` as Baseline "since September 2022". The transparent-outline and `currentColor` tricks the book gives (pp. 21, 127, 161, 294) address the same mode under its new name.
- **Vue removes attributes bound to false, "magically (?)", so `aria-pressed` needs a stringified value (Toggle buttons, p. 16).** Changed for Vue 3. The Vue 3 migration guide, "Attribute Coercion Behavior", says Vue 3 stops removing a non-boolean attribute bound to `false` and writes the string `"false"` instead, with `aria-checked` as its own example (v3-migration.vuejs.org).
- **`aria-label` is not translated by Google's and Microsoft's translation services (Toggle buttons, p. 25; Tooltips & Toggletips, p. 100; Notifications, p. 229).** Still holds for Google Translate. Adrian Roselli's "aria-label Does Not Translate" (November 2019, updated through July 2025) reports that Google Translate still misses "the same examples", and that Chrome's built-in translation translated `aria-label` for a period and then became unreliable (adrianroselli.com/2019/11/aria-label-does-not-translate.html). Microsoft's service was not re-tested by that source and is unchecked.
- **Reach Router "comes highly recommended" for focus management; React Router 4's `withRouter` is the alternative (Tabbed Interfaces, p. 150).** Changed. React Router v6, announced November 3, 2021, "is also the successor to Reach Router" (remix.run/blog/react-router-v6). The reach.tech site returned an error on fetch (HTTP 526), so its own deprecation notice is unchecked.
- **Bulb, the author's client, for the live-region testing, the fuel-price table and the step timeline (A Todo List, p. 53; Data Tables, p. 239; Modal Dialogs, p. 272).** The company is gone: Bulb Energy entered special administration on November 24, 2021, the first UK energy company to do so, and Octopus Energy completed its acquisition on December 21, 2022 (en.wikipedia.org, Bulb Energy). The findings stand as the author's account of that work.
- **TodoMVC's delete control "only appears on hover" (A Todo List, pp. 35–36).** Still holds. The current `todomvc-app-css` stylesheet on GitHub carries `.todo-list li .destroy { display: none }` and `.todo-list li:hover .destroy { display: block }`.
- **shouldiuseacarousel.com: 1% clicked a feature, and 89% of those were on "the first position" (A Content Slider, p. 198).** Still holds as stated. The site is live and cites the same figures from Erik Runyon's 2013 Notre Dame statistics (erikrunyon.com/2013/07/carousel-interaction-stats). The figures are from one university's homepage in 2013 and were not re-measured.
- **Changing `display` on table elements removes table semantics, per Adrian Roselli (Data Tables, pp. 247–248).** Changed. Roselli's post carries dated updates: Chrome 80 and Chromium Edge stopped dropping semantics on February 19, 2020; Firefox closed its last bug in 2022; and an update of October 7, 2023 reports tables with display properties working across Chromium, Gecko and "(finally)" WebKit, Safari 17 having taken "5¾ years" (adrianroselli.com/2018/02/tables-css-display-properties-and-aria.html).- **Safari "doesn't support `scroll-behavior`", so CSS snap points are the fallback (A Content Slider, p. 206).** Changed. MDN lists `scroll-behavior` as Baseline since March 2022 (developer.mozilla.org, scroll-behavior). Scroll snap is standard rather than a mix of proprietary and standard properties.
- **Lazy loading needs `IntersectionObserver` and a `data-src` swap (A Content Slider, pp. 198–200).** Changed in part. The `img` element now takes `loading="lazy"`, which defers the load until the image nears the viewport and only while JavaScript is enabled (developer.mozilla.org, `<img>`); a Baseline date for the attribute specifically was not on the page fetched and is unchecked.
- **The collapsible section had no consistent native implementation across browsers (Collapsible Sections, p. 152).** Changed. MDN lists `<details>` as Baseline since January 2020 (developer.mozilla.org, `<details>`).
- **The `switch` role "is not quite as well supported as `aria-pressed`" and ChromeVox does not recognize it (Toggle buttons, p. 32).** Partly changed. `switch` is a defined widget role in WAI-ARIA 1.2, a W3C Recommendation of June 6, 2023 (w3.org/TR/wai-aria-1.2). HTML has since gained a native `switch` attribute on `input type="checkbox"`, which MDN marks experimental and caniuse lists as Safari 17.4 and later only (caniuse.com, mdn-html_elements_input_switch). ChromeVox's current handling is unchecked.
- **WAI-ARIA Authoring Practices 1.1 as the source of the menu and tab keyboard patterns (Menus & Menu Buttons, p. 83; Tabbed Interfaces, p. 141).** The Authoring Practices Guide is now a living document; its tabs pattern still prescribes arrow keys within the tab list and recommends automatic activation where the panels display "without noticeable latency" (w3.org/WAI/ARIA/apg/patterns/tabs). It carries no reference to the user-testing caveat the book raises.
- **BBC GEL tabs mix ARIA semantics with "same-page link-like behavior" after user testing (Tabbed Interfaces, p. 143).** Still holds. The live GEL tabs page states that unselected tabs are focusable, that Enter and Space activate them, and that clicking a tab moves focus "to the visible tab panel" (bbc.github.io/gel/components/tabs).
- **"Danger! ARIA tabs" on Simply Accessible (Tabbed Interfaces, p. 141).** Unchecked: simplyaccessible.com did not resolve on 2026-09-10 (DNS failure), so the article is unreachable at its original address.
- **Hidde de Vries's workshop finding, quoted from Twitter, 4 November 2018 (Tabbed Interfaces, p. 142).** Unchecked: the tweet was not fetched, and the service has since been renamed X. The author's own contact handles on p. 7 name Twitter and Mastodon.
- **The Paciello Group's verdict on the `title` attribute (Tooltips & Toggletips, p. 96).** Unchecked: The Paciello Group is now TPGi, and its "Using the HTML title attribute" page returned HTTP 403 on fetch.
- **`aria-controls` is supported only in JAWS (Menus & Menu Buttons, pp. 77–78; Tabbed Interfaces, pp. 142–143; Collapsible Sections, p. 157).** Unchecked: the later support note by Adrian Roselli that was looked for returned 404 at the URL tried, and no other source was reached.
- **`aria-current` was "less well supported" than hidden "(you are here)" text (Modal Dialogs, p. 273).** Unchecked: MDN's `aria-current` page carries no assistive-technology support table.- **Léonie Watson's report that text inputs are non-functional in Firefox plus JAWS without a `form` (A Todo List, p. 45).** Unchecked: no source reached; the browser and screen reader versions concerned are not named in the book.
- **Internet Explorer and early Edge put SVGs in focus order, hence `focusable="false"` (A Todo List, p. 55; Collapsible Sections, p. 160); Edge does not accept Booleans from a sort comparator (Data Tables, p. 260).** Changed. Internet Explorer 11 support on the Windows 10 Semi-Annual Channel ended on June 15, 2022 (en.wikipedia.org, Internet Explorer); the date Chromium replaced EdgeHTML was not on the page fetched and is unchecked.- **WCAG 2.0 as the reference standard (Toggle buttons, pp. 20, 34; A Todo List, p. 48).** Superseded. WCAG 2.2 is a W3C Recommendation whose current edition is dated December 12, 2024, and it adds 2.5.8 Target Size (Minimum) and 2.4.11 Focus Not Obscured (Minimum) at Level AA (w3.org/TR/WCAG22), the first of which speaks to the book's touch-target advice on pp. 204 and 304. The success criteria the book cites (1.4.1, 1.4.3, 2.2.2, 2.4.3, 3.2.2) keep their numbers in 2.2.
- **inclusive-menu-button with Hugo Giraudel, built on a11y-dialog (Menus & Menu Buttons, p. 94); Xiao, the author's router (Tabbed Interfaces, p. 147).** All three repositories are live on GitHub and not archived; a11y-dialog is maintained under the name KittyGiraudel. Last-commit dates were not on the pages fetched and are unchecked.
- **The blog inclusive-components.design (Introduction, p. 6).** Live, listing the eleven component articles and a note that the book carries "updated and improved" content and demos; the site gives no publication date for the book.
- **Nielsen Norman Group's modal-dialog article by Therese Fessenden (Modal Dialogs, p. 265), mutable.gallery (A Content Slider, p. 213), the "Writing Less Damned Code" talk (A Theme Switcher, p. 115; A Content Slider, p. 214), the BBC carousel and sortable table (A Content Slider, p. 214; Data Tables, p. 262), Rik Schennink's `noscript` technique (A Content Slider, p. 202), and the "41.9KB" carousel plugin (A Content Slider, p. 213).** Unchecked: not fetched, and the last is unnamed in the book.

## 8. Where the book is weakest

- **Evidence that is the author's own testing, unquantified.** The Bulb finding that users hearing a live region thought their focus had moved (A Todo List, p. 53), the usability lesson that freedom to explore is "not actually very popular" (Modal Dialogs, p. 281), and the BBC "extensive user testing" behind the tabs departure (Tabbed Interfaces, p. 143) are reported without participant counts, tasks or dates. The one outside test cited against the tab pattern is a single tweet about one user (Tabbed Interfaces, p. 142).
- **Browser facts frozen in 2018.** `inert` in Chrome only, `-ms-high-contrast`, Safari without `scroll-behavior`, no consistent native collapsible, `confirm()` as the only native modal, and the `display` table-semantics bug are each stated as present tense and each has since changed (section 7). A reader applying the book's workarounds today ships code for a bug that is fixed.
- **Screen reader claims stated as general.** JAWS-only support for `aria-controls` (Menus & Menu Buttons, p. 77), `aria-current` "less well supported" (Modal Dialogs, p. 273), and the ChromeVox note on `switch` (Toggle buttons, p. 32) carry no version or test date, and section 7 could confirm none of them.
- **A rule stated and then broken inside the book.** "Never change label and state together" and keep the label constant (Toggle buttons, pp. 22–25) is reversed for voice control on p. 24 and set aside for sort arrows on p. 259; the author names the second departure himself. Focusable non-interactive elements are a WCAG 2.4.3 failure (A Todo List, p. 59) and the content slider region then takes `tabindex="0"` with the admission that it may be "an obstructive extra tab stop" (A Content Slider, p. 207).
- **Tone that dates the text.** The carousel chapter opens by likening carousels to men and closes with a checklist item addressed to men who were not offended (A Content Slider, pp. 181, 214); the introduction's aside on silicon (Introduction, p. 4) and the "Places to get drunk" heading example (A Todo List, p. 38) are of a piece. None of it bears on the arguments, and it is the part a reader quoting the book is likeliest to trim.
- **Code the reader cannot see in this copy.** The text extraction loses every code sample and figure, and the book's argument is often in the code: the keyboard tables on pp. 83–84 and p. 141 survive as prose, but the collapsible web component (pp. 166–176), the slider script (pp. 199–213) and the sortable table (pp. 243–261) do not. A claim about what the code does was checked against the prose around it, not the code.
- **Performance claims without measurement.** "153 bytes uncompressed" for the dark theme (A Theme Switcher, p. 118), "about 100 bytes of JavaScript" (A Content Slider, p. 194), "less than 2KB minified" against a plugin at "41.9KB" (A Content Slider, p. 213), and the claim that a bloated DOM slows many users' experience (A Todo List, p. 57) are asserted; no page load, task time or assistive-technology latency is measured anywhere in the book.
- **Framework churn as evidence.** React Router 4, Reach Router (Tabbed Interfaces, p. 150), Vue's attribute removal (Toggle buttons, p. 16), Modernizr (A Theme Switcher, p. 125) and the "React-like Web Components" debate (Collapsible Sections, p. 167) are treated as the state of play; each has moved, and the chapters that rest on them (A Theme Switcher, Collapsible Sections, Data Tables) are the ones whose code is least reusable as written.
- **The card chapter's central tension is left to the reader.** Two clickable-card techniques are given with a trade on text selection and context menus (Cards, pp. 288–291), and the author's recommendation is conditional on "If it's not seemingly important" (p. 291), with no user evidence on either side.
