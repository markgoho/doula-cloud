## 3. The claim

The book's thesis, in the author's frame, is that inclusive design is a mindset rather than a skill set: the potential audience of a website is anyone human, people always differ in ability, preference, and circumstance, and an interface that makes allowances for that difference is a robust interface (Introduction, pp. 11, 13–14). The author illustrates it with a data-schema analogy, an address property that cannot be forced into one fixed shape, and says that swapping "addresses" for "people" gives inclusive interface design "in a nutshell" (Introduction, pp. 12–13). The method is to reason about each interface pattern from the imagined point of view of many kinds of user, and to reach first for what the platform already provides, the worked example being a `<button>` element against a `<div>` styled with a background image (Introduction, pp. 14–18). Inclusive design, the author says, need not be harder than exclusive design; it is "just different" (Introduction, p. 14). Four principles are set out: the web is made of code and is best designed in code; content comes first and every other decision serves it; pages are not immutable artifacts and should tolerate changing content managed as reusable components; and inclusivity of ability, preference, and circumstance is paramount (Introduction, p. 11). The patterns that follow are offered as exemplars but "mostly they're for practice" in that way of thinking (Introduction, p. 19).

The author says what the claim is not. It is not a book about developer ergonomics, frameworks, preprocessors, or task runners; tools appear only where they affect the user's experience, and the lessons apply within any framework flexible enough to permit good interfaces (The Document, pp. 44–45). It is not a book organized by accessibility principle: an early draft was structured by keyboard, color, and writing, and the author abandoned it because a pattern has to be inclusive in every regard at once (Evaluation By Pattern, pp. 108–109). It is not a compliance manual: WCAG is what the author defers to in an audit, but the book's object is whether a person can get things done, and a fully compliant interface can still be unusable (Evaluation By Pattern, p. 110; A List Of Products, pp. 214–215). It is not a treatise on responsive design or image performance, both of which it says are out of scope beyond the principles that support inclusion (The Document, p. 25; A List Of Products, p. 205). And its patterns are not a fixed library: the navigation pattern may be reused as presented, but the rest are examples for formulating one's own (Inclusive Prototyping, p. 180).

## 4. The argument, chapter by chapter

### Introduction (pp. 8–19)

The chapter opens on a party anecdote about the word "designer" and argues that the industry's most persistent error has been to apply print design's fixed, pixel-perfect assumptions to a medium that is none of those things (Introduction, pp. 8–10). Design is "deliberation", the pursuit of the best solution to a problem, and relegating it to visual aesthetics leaves most of the web undesigned (Introduction, p. 10). The four principles follow (Introduction, p. 11), then the address-schema analogy: one string cannot be split into a country reliably, a fixed object cannot fit every country's address, and the inclusive answer is the one that tolerates variety (Introduction, pp. 12–13). The button example runs through three designers. The graphic designer draws a button; the designer who codes ships a `<div class="button">` with a background image and a click listener; the inclusive designer sees that the image blurs under zoom and does not scale with a user's font size, vanishes when images are switched off or under Windows high contrast mode, is not focusable or keyboard-operable, has no role for a screen reader, and carries its label in CSS where it cannot be translated (Introduction, pp. 14–17). The answer is `<button>Start</button>`, which the platform already made resizable, translatable, focusable, and stylable (Introduction, p. 18). An Adam Morse quotation on the 140 trillion hex-code combinations closes the point that constraint leaves ample room for expression (Introduction, p. 18).

### The Document (pp. 20–45)

The chapter configures a parent page for inclusive patterns. The doctype comes first, because without it browsers fall into quirks mode and the author checks for it before anything else when a page misbehaves (The Document, pp. 21–22). The `lang` attribute on `<html>` improves indexing and translation, switches Firefox's spellcheck dictionary, picks the right screen reader voice profile, and selects system fonts with the right character set; it can be set per element and targeted with `:lang()` (The Document, pp. 22–24). Responsive design is treated as part of inclusive design, with device breakpoints called futile: build a flexible design and add "content breakpoints" only where content breaks the layout, found by resizing in Firefox's responsive mode until something collides (The Document, pp. 25–26). As a rule of thumb, never set a fixed width or height on an element (The Document, p. 26). Pinch-zoom must never be disabled; the author's informal Twitter poll named it the most-cited inclusion mistake, and Adrian Roselli's list of reasons is reproduced; positioned elements, especially `position: fixed`, become blind spots when content is enlarged (The Document, pp. 27–28). Font size: browsers default to 16px for a reason, the root is set at `100%` rather than `16px` so a user's own setting survives, sizing uses `rem` and `em` so padding and margin scale with text, media queries use `em` because `rem` misbehaves in Safari, and a preprocessor must not convert rems to pixels (The Document, pp. 29–31). Viewport units cannot be zoomed on their own, so `calc(1em + 1vw)` restores zoom and a minimum size, and where a browser does not understand it (Opera Mini at the time) it falls back to the default (The Document, pp. 31–32). Progressive enhancement is defined broadly, as resilience to when and how CSS and JavaScript fail, not only to their absence; every pattern in the book is semantic HTML enhanced by CSS and JavaScript, and scripts go at the end of the body (The Document, pp. 32–34). Web fonts are an enhancement, FOIT is to be avoided with a base64 font stylesheet loaded on `onload` behind a `<noscript>` fallback or with Bram Stein's Font Face Observer, and the resulting FOUT is softened by choosing fallback fonts with similar metrics (The Document, pp. 34–36). Fonts are subsetted with Google Fonts' `text=` parameter or Font Squirrel's generator, with a system font filling the missing glyphs (The Document, pp. 37–38). The `<title>` is the document's accessible name, is announced on load, and follows the convention of page description then site name, with a search page carrying the search term (The Document, pp. 38–39). `<main>` gives screen readers a landmark and a shortcut, holds a single-page application's views, and makes a print stylesheet a one-liner that hides its siblings (The Document, pp. 39–40). Skip links are for sighted keyboard users more than screen reader users, hidden until focused (The Document, pp. 41–42). The assembled page is shown (The Document, p. 43), then a note that the book is about the audience, not developer ergonomics, with a points system: one point if it benefits the author, ten if it benefits users like the author, a hundred if it benefits users unlike the author (The Document, pp. 44–45).

### A Paragraph (pp. 46–69)

Text is primary and a paragraph is an atom in Brad Frost's terms (A Paragraph, p. 47). On typefaces, the author distrusts the "well-supported" claim that sans serif is more readable and offers four questions instead, about ornament, consistent metrics, distinct letterforms, and character coverage; the British Dyslexia Association's findings on ascenders, mirrored letters, and I/l/1 are cited (A Paragraph, pp. 48–49). A typeface chosen for people who struggle to read is pleasant for everyone, which is offered as the efficient form of inclusive design, with "Designing for the extremes" quoted on the fiction of the average user (A Paragraph, pp. 49–50). A Spanish study found a typeface designed for dyslexic readers performed very poorly, and Chuck Bigelow's research agrees; the lesson is not to target a group in isolation (A Paragraph, pp. 50–51). Typesetting: measure of 45–75 characters per Bringhurst, set indirectly with a `max-width` in `rem` on the container so it scales with font size (A Paragraph, pp. 51–53); justified text is bad practice, CSS hyphenation was poorly implemented and absent in Chrome, and left alignment is preferred (A Paragraph, pp. 53–55); leading of one-and-a-half per WCAG 1.4.8, set as a unitless `line-height` (A Paragraph, pp. 55–56); contrast designed in from the outset with tools such as Contrast-A and Color Safe, but tempered slightly because stark black on white harms readers with Irlen syndrome and triggers the author's migraines (A Paragraph, pp. 56–57). Inline links stay underlined because color alone fails color-blind readers; a gradient-and-text-shadow underline that skips descenders is shown, adapted from Medium (A Paragraph, pp. 58–60). Focus: an element must be focusable, visible, and visibly focused; default focus styles may be replaced but never removed; a filled background color, as on GOV.UK, is clearer than a dotted outline (A Paragraph, pp. 60–62). External links get an automated icon and hidden "(external link)" text via an attribute selector and pseudo-content, so editors never touch code (A Paragraph, pp. 63–66). Writing: short words and sentences, few passives, no redundancy, varied length; "everything but content is an enhancement", so prototypes carry real copy (A Paragraph, pp. 66–67). The things-to-avoid list ends the chapter (A Paragraph, p. 68).

### A Blog Post (pp. 70–107)

Spartan designs are held to be the most effective because there is less to break when a reader adjusts something (A Blog Post, p. 71). `<main>` returns, with a warning against third-party grid systems whose `<div>` scaffolding bloats the DOM and once made a screen reader misbehave in the author's testing; simple interfaces are usable, accessible, maintainable, and performant (A Blog Post, pp. 72–74). Headings carry the document's structure: one `<h1>`, the article title, which NVDA and JAWS reach with the 1 key; the author's informal survey found most screen reader users navigate by headings, some by landmarks, some by reading element by element, which is why source order matters and the title precedes the publish date (A Blog Post, pp. 74–76). An automated tool would not flag the wrong order, and inclusive design is about how people really use interfaces (A Blog Post, p. 76). Only `<h1>`–`<h6>` describe depth, because the HTML5 outline algorithm was never implemented; skipping a level to get a smaller font breaks the structure, and styling an `<h2>` as an `<h3>` is tolerated with caution because it segregates seeing and non-seeing readers (A Blog Post, pp. 77–79). Subtitles: not a second heading, and not `<hgroup>`, which had been removed from the specification; either a `<span>` inside the `<h1>` or a paragraph prefixed with a visually hidden "Subtitle:" (A Blog Post, pp. 80–82). The `.visually-hidden` utility class is given, with the note that `display: none` and its relatives silence screen readers too, and the accessibility tree is introduced (A Blog Post, pp. 82–83). `<article>` is judged "probably not, but maybe": no landmark, no outline effect, and only JAWS announces it, which helps on a listing page (A Blog Post, pp. 84–85). Alice Bartlett's GDS research is cited as compelling evidence to avoid `<select>` wherever possible (A Blog Post, p. 86). Sound structure survives a missing stylesheet and works in feed readers; the test is to switch CSS off (A Blog Post, pp. 86–87). Static content rendered by client-side JavaScript is underperforming and unreliable; Tantek Çelik's "js;dr" line is quoted, and curl is the test (A Blog Post, pp. 87–88). Flesch reading ease and Flesch-Kincaid grade are explained, with a Chrome extension, the author's Node CLI, and Tenon named, and a caveat that readability is subjective and only an early warning (A Blog Post, pp. 88–91). Headings and links must make sense out of context because screen readers list them: not "Free, you say?" but "Free flapjacks", and not a run of "a lot of support" links but the works named (A Blog Post, pp. 91–93). Video: captions serve many circumstances, not only deafness, and a transcript is always provided; a player is tested by tabbing into it and, with NVDA on Windows with Firefox or VoiceOver on Safari, listening for "Play button"; YouTube, Able Player, PayPal's, and Laura Kalbag's players are recommended; caption conventions identify speakers and sounds, per the BBC guidelines (A Blog Post, pp. 94–101). A flow system spaces successive elements with the owl selector `* + *` in units of the paragraph line height, uses `em` on headings so they sit closer to their own content, doubles the margin around non-paragraph elements, and hides empty elements left by WYSIWYG editors with `:empty`; Markdown is preferred to WYSIWYG (A Blog Post, pp. 101–106).

### Evaluation By Pattern (pp. 108–123)

The author explains why the book is organized by pattern: an audit organized by WCAG principle is easy to reassure oneself with, but development teams do not find it actionable, and one bad idea becomes several tickets (Evaluation By Pattern, pp. 109–111). The upvote-button example shows three developers each fixing one ticket, adding `aria-label`, then `tabindex` and a keydown script, then `role="button"`, and ending with a bloated `<div>` when the pattern-level answer was a `<button>` with an SVG (Evaluation By Pattern, pp. 111–115). Reporting by pattern feeds the organization's pattern library, and Joe Dolson's wish to be hired less is endorsed (Evaluation By Pattern, pp. 115–116). Custom elements: a `<toggle-button>` is only an `HTMLElement`, so it needs `tabindex`, `role`, a keydown handler, and `aria-pressed` added in its lifecycle callback, or it can extend `HTMLButtonElement` with `extends: 'button'` and inherit them; both the v0 `registerElement` and v1 `customElements.define` syntaxes are shown (Evaluation By Pattern, pp. 117–121). Shadow DOM severs `aria-labelledby`, `aria-describedby`, and `aria-controls` across the boundary, custom elements and Shadow DOM are independent technologies, and positive `tabindex` is discouraged everywhere in favor of source order (Evaluation By Pattern, pp. 122–123).

### Navigation Regions (pp. 124–153)

Navigation is content that helps with content, present even on the first web page (Navigation Regions, p. 125). `<main>` and `role="main"` are equivalent; navigation landmarks may be several per page and should be consistent across pages (Navigation Regions, pp. 126–127). Site navigation is an unordered list of links inside `<nav>`, which reads as a list even without CSS and announces its item count to screen readers, and landmarks are listed as a menu in NVDA, JAWS, and VoiceOver (Navigation Regions, pp. 127–129). Familiar form matters because schemata are a cognitive cache: navigation goes at the top of the page in the expected shape, and source order should match reading order; a Léonie Watson clinic story has navigation reachable only after thirty or forty Tab presses because it sat last in the source (Navigation Regions, pp. 129–131). Positioning is to be avoided in all but the rarest cases, with modal dialogs singled out for extreme caution (Navigation Regions, pp. 131–132). The current page is marked with more than color, per WCAG 1.4.1: an underline or a pointer, checked in macOS grayscale (Navigation Regions, pp. 132–134). Non-visually, a hidden "Current page" span or an `aria-describedby` to a `hidden` element does the job (Navigation Regions, pp. 135–137). The self-referential link is not removed, because it is the "You are here" marker and keyboard users tab through links; the author's favorite fix points it at `#main` so it doubles as a skip link and is announced as a same-page link, with a caveat for single-page applications where that announcement would lie (Navigation Regions, pp. 137–140). The logo link and the Home link are merged so two things that look different do not do the same thing (Navigation Regions, pp. 140–142). A table of contents is preferred to drop-down submenus, which hide content, encourage fragmentary pages, need absolute positioning, and degrade badly; NN/g's "use sparingly" is cited and drop-downs get no pattern of their own (Navigation Regions, pp. 143–144). In-page links rely on sequential focus navigation, once broken in Chrome and needing `tabindex="-1"` in Internet Explorer; smooth-scroll scripts that hijack links must restore focus and the URL hash (Navigation Regions, pp. 145–149). Multiple navigation landmarks are told apart with `aria-labelledby` on a heading or `aria-label` (Navigation Regions, pp. 149–152).

### A Menu Button (pp. 154–179)

The rule of thumb comes first: a menu with fewer than five items is laid out, not hidden; at desktop widths there is rarely a reason to hide navigation; hiding functionality behind an action is "always a last resort" (A Menu Button, p. 155). Icons speed comprehension, cross languages, and help low literacy, with a study on medication icons cited (A Menu Button, p. 156). The three-line icon works because it is a co-opted list icon, so the menu it reveals should look like a list, and the symbol is not to be extrapolated (A Menu Button, p. 157). James Foster's A/B test found the icon plus the word "menu", inside a bordered button shape, better understood; all buttons should look like buttons for perceived affordance, and the word gives voice-control users a term to say (A Menu Button, p. 158). Rendering: background images vanish in Windows high contrast mode; a PNG becomes black on black; icon fonts fail when a user substitutes their own font or a font is blocked, and Opera Mini loads no web fonts; the Unicode trigram U+2630 may be announced aloud and needs `aria-hidden`; SVG sprites, embedded with `<symbol>` and `<use>`, scale, take `currentColor`, and are judged the most robust (A Menu Button, pp. 159–165). Labeling: a visible text node is simplest, a visually hidden span or `aria-label` covers an icon-only control, and the same technique fixes play and close buttons (A Menu Button, pp. 165–167). Older browsers get a `<switch>`/`<foreignObject>` PNG fallback with `alt=""` (A Menu Button, pp. 167–168). Operation: the button sits inside the `<nav>` landmark, the menu follows it in source order and is hidden with the `hidden` attribute so its links are unfocusable when closed; `aria-controls` is "poop" because only JAWS exposes it, so a link to the landmark with `tabindex="-1"` and `:target` is offered where proximity is impossible (A Menu Button, pp. 169–171). State is `aria-expanded`, toggled by a small inline vanilla script, and the disclosure uses no positioning or animation so it works without CSS, stays in document flow, and keeps hidden links unfocusable (A Menu Button, pp. 172–175). Animation is warned against as something only other designers admire, with Goran Peuc quoted on people not wanting to use products (A Menu Button, pp. 175–176). Touch targets: Apple's 44 points and Android's 48 pixels are named as the point at which a finger no longer hides the focus feedback; Patrick Lauke's W3C research is cited; the BBC's inactive-space advice is set aside for navigation in favor of one link per line with generous vertical padding (A Menu Button, pp. 176–178).

### Inclusive Prototyping (pp. 180–189)

Inclusive thinking belongs in the earliest stage: after discovery, stockpile verbs and prototype for usability before aesthetics (Inclusive Prototyping, p. 180). Paper prototyping is credited with almost every successful project the author has worked on, the Great British Public Toilet Map among them; anyone can work with paper, it iterates fast with sticky tack, and its roughness keeps feedback honest (Inclusive Prototyping, pp. 181–182). Equipment, the scenario, the person playing the computer, think-aloud instructions, and Lily Dart's "Test usability, not users" are set out, with a seating diagram (Inclusive Prototyping, pp. 183–187). From paper to code: Charlotte Jackson's exercise of everyone coding a component in HTML and CSS against a time limit, with the author's two stipulations that several people take the same component and that a solution that is not keyboard-accessible or screen-reader explicable is out; standard elements such as `<input>`, `<select>`, `<a>`, and `<button>` are the fastest way to prototype (Inclusive Prototyping, pp. 188–189).

### A List Of Products (pp. 190–223)

Marketing targets an audience; inclusive design does not second-guess how anyone operates the interface, because ability and circumstance have nothing to do with interest (A List Of Products, pp. 191–192). OXO is cited for designing for extremes first, and "Sandra", a photographer who lost her sight, stands for the user a business would write off; the features she wants benefit others, and keyboard accessibility helps everyone eating with their mouse hand, per Adrian Roselli (A List Of Products, pp. 192–194). Using standard elements is less work than a `<div class="heading-3">` patched with ARIA (A List Of Products, p. 194). Products are list items, each with an `<h3>` at the same level, a featured item marked with text rather than a promoted heading, navigable by heading or by JAWS's list-item key; Henny Swan's four BBC principles appear (A List Of Products, pp. 195–197). Key facts go in a `<dl>`, with the multiplication sign so "times" is announced, and star images given `alt=""` beside a spelled-out rating (A List Of Products, pp. 198–200). The thumbnail shows the product plainly, and its alt text adds what the title does not, decided with the WAI decision tree (A List Of Products, pp. 200–203). Image weight is demonstrated with Chrome's 3G throttle and What Does My Site Cost; compression, lazy loading via a `data-src` swap, and `<picture>` are the three techniques (A List Of Products, pp. 204–206). "Buy Now" is a link, so it must not get `role="button"`; links that act as calls to action get an emphatic style that still does not resemble a button, all three controls share one interactive color, the class is qualified with the element name so it cannot be misapplied, and buttons keep the default cursor per Adam Silver (A List Of Products, pp. 207–210). Standard link behavior is kept rather than replaced by JavaScript, and each link carries the product name in visually hidden text so a links list makes sense and search relevance improves (A List Of Products, pp. 210–212). Block-level links are valid but rejected: no dedicated label, VoiceOver heading navigation breaks, the readout is verbose, and touch users follow them by accident; Karl Groves' "To Hell With Compliance" underwrites the point that compliance is the minimum (A List Of Products, pp. 212–215). For search results, the `<title>` is the link text, and schema.org Product microdata is added to the permalink page, tested with Google's tool (A List Of Products, pp. 215–221).

### A Filter Widget (pp. 224–259)

Filtering puts users in control, Henny Swan's second principle (A Filter Widget, p. 225). The first rule of ARIA use is quoted: prefer a native element with the semantics built in, because standard interactivity is more performant and robust (A Filter Widget, pp. 226–227). The sorter is a `<form method="get">` with `role="form"` to make it a navigable region, one `<fieldset>` with a "Sort by" `<legend>`, radio buttons, and a submit button; the browser supplies arrow-key selection, and the legend is read with every option (A Filter Widget, pp. 227–229). CSS enhancement hides the radio and styles the `<label>` as a proxy through `:focus` and `:checked` sibling selectors, giving a larger hit area; "never fix with JavaScript and WAI-ARIA" what HTML and CSS can do (A Filter Widget, pp. 230–232). JavaScript enhancement repopulates the list with XHR so focus stays in the widget, announces "Please wait" and "Loading complete" through an assertive live region that is visually hidden because the spinner already speaks to sighted users, and suppresses the submit event (A Filter Widget, pp. 232–236). Dropping the submit button is weighed and left to user testing: firing on `change` usurps control and fires three times under arrow keys, firing on `click` leaves keyboard users to guess Enter, and iOS will not submit a form with no submit button, so it is kept visually hidden with `tabindex="-1"`; GDS's advice to include disabled participants in testing is quoted (A Filter Widget, pp. 236–239). Infinite scroll is rejected on Derek Featherstone's account, moving the scrollbar under a mouse user and trapping keyboard users above the footer; a "Load more" `<button>` replaces it, and after loading, focus moves to the first new item's `<h3>`, made focusable with `tabindex="-1"`, with a live region and the button's text changed to "Loading" in between (A Filter Widget, pp. 239–245). Display options give the user a choice of list or grid, each an inline SVG label with hidden text, in a second fieldset (A Filter Widget, pp. 245–249). The grid is self-governing: `flex-basis: 10em`, grow and shrink, wrap, a `max-width` of `20em` to protect the measure, and `justify-content: center`; it reflows with font size and needs no media queries (A Filter Widget, pp. 249–252). Right-to-left: `dir="rtl"` reverses flex rows automatically where floats need manual reversal, and tables are not used for layout (A Filter Widget, pp. 253–254). Static mockups idealize content, so forceFeed.js feeds randomized names and titles into the layout until it stops breaking (A Filter Widget, pp. 255–257).

### A Registration Form (pp. 260–289)

Forms are where the web accepts input, and they are "a 10,000-volt electromagnet" for usability problems (A Registration Form, p. 261). Context first: a tiny "Don't have an account?" link under a login form is missed by screen reader users reading top to bottom, which is what bypass blocks exist for (WCAG 2.4.1), and a clearer answer is a Login/Register choice up front, built as a `role="toolbar"` of two `aria-pressed` buttons rather than a full tab interface, with the chosen form following in source order (A Registration Form, pp. 262–266). Labeling: every control needs an accessible label, a `<label for>` matched to a unique `id` (duplicates fail WCAG 4.1.1), because screen readers jump field to field and would skip an unassociated label; a proposed ARIA `password` role is noted as inferior to `type="password"`, which pairs semantics with behavior (A Registration Form, pp. 267–268). The placeholder is a hint, never a label; its default gray fails contrast, so it is styled dark and italic; it vanishes on typing and under autofill, with Lea Verou quoted; the float-label pattern is noted with the caveat that it forfeits the hint (A Registration Form, pp. 268–271). A `<fieldset>` around the whole form adds "Registration:" to every label for no gain, so three rules decide when a fieldset is warranted: more than one distinct set, more than one field in the set, and a legend that would aid each label (A Registration Form, pp. 272–273). Required fields: an asterisk in a `<strong>` is familiar but fragile, so `aria-required="true"` announces "Required" and the asterisk is `aria-hidden`; the HTML `required` attribute is passed over because support was uneven and it marks empty fields invalid from the outset (A Registration Form, pp. 274–276). Showing the password: a checkbox toggles the input type, replacing the "confirm password" field, and Edge's native eye icon is suppressed (A Registration Form, pp. 276–278). Validation communicates two things separately, that something is broken and what would fix it: the submit event is suppressed, a `role="alert"` live region directly above the submit button, hidden with `:empty` until filled, carries a general message with an SVG warning icon whose `aria-label` reads "error:", and the user is deliberately not moved, because focusing the first invalid field is a disorienting shift (A Registration Form, pp. 278–282). Each invalid field gets `aria-invalid="true"`, which doubles as the styling hook, and an `aria-describedby` hint saying what would make it valid (A Registration Form, pp. 282–284). Validation reruns on `input` only after a failed submit, debounced with Lodash so a screen reader is not put into "80's remix mode" (A Registration Form, pp. 285–287). Microcopy follows Bill Beard's five points and WCAG 2.4.6: brand voice must not get in the way, so a password field is not labeled "Secret incantation" (A Registration Form, pp. 287–289).

### Test-Driven Markup (pp. 290–307)

TDD is introduced with a Mocha and Chai example, and the question is whether declarative HTML can be tested the same way (Test-Driven Markup, pp. 291–292). CSS selectors are condition-based expressions, so a selector can match a malformed pattern and paint a red outline on it (Test-Driven Markup, pp. 292–293). A tab interface is the subject: successive selectors flag a `<ul>` without `role="tablist"`, an `<a>` without `role="tab"`, an `<li>` without `role="presentation"`, a selected tab with `tabindex="-1"`, an unselected tab without it, a panel whose `aria-labelledby` does not start with "tab", a `<div>` after the list that is not a panel, and content between list and panels (Test-Driven Markup, pp. 294–299). Messages: pseudo-content is fragile, as revenge.css showed and a11y.css works around, so the author logs an unrecognized `ERROR:` property that Chrome's inspector flags with a warning sign, with a small extension to restyle the strike-through (Test-Driven Markup, pp. 299–304). The tests live in a `tab-interface.test.css` beside the component and are excluded from production; they cannot fail a build, and they test one's own prescribed structure where generic tools such as a11y.css and Tenon report generic errors (Test-Driven Markup, pp. 304–307).

### Further Reading (p. 308 and unnumbered pages)

The author invites errata and suggestions for a sequel, then lists books (A Web For Everyone, Apps For All, Designing With Web Standards, Adaptive Web Design, The Design Of Everyday Things, Don't Make Me Think, Responsible Responsive Design, Design For Real Life, The Timeless Way Of Building, among others) and blogs (Marco Zehe, The Paciello Group, Léonie Watson, Adrian Roselli, Simply Accessible, WebAIM, Karl Groves, Deque, GOV.UK accessibility, Luke Wroblewski, among others) (Further Reading, p. 308 and the unnumbered pages after it).

## 5. The book's own exceptions

These are the places the author limits his own claim, admits a counter-case, or says a rule does not apply.

- **The patterns are examples, not a library.** They are "reusable as exemplars" but mostly for practice; new problems will need new patterns (Introduction, p. 19; Inclusive Prototyping, p. 180). Only the navigation region pattern is expected to be used as presented (Inclusive Prototyping, p. 180).
- **Frameworks and tools.** Use a framework or preprocessor if you like; only opinionated frameworks that cannot be configured for inclusive techniques are to be avoided (The Document, pp. 44–45).
- **Fixed widths.** The rule is a "rule of thumb", and the book itself sets `max-width` on `<main>` and grid items to protect the measure (The Document, p. 26; A Paragraph, p. 52; A Filter Widget, p. 251).
- **Pinch-zoom.** One of Roselli's reasons for keeping zoom is that the developer did a poor job and the user needs it just to use the page, which the author accepts happens (The Document, p. 28).
- **Viewport units.** `calc(1em + 1vw)` is a progressive enhancement; where unsupported the browser falls back to its default, which is presented as acceptable (The Document, p. 32).
- **Enhancement.** "Enhancement is a great thing, but only where it's really needed" is a caption's whole argument; the filter widget is explicitly left "a bit clunky" until JavaScript arrives and then enhanced with restraint rather than rewritten (The Document, p. 33; A Filter Widget, p. 232).
- **Typeface advice.** Serifs are "generally regarded as overcomplex", yet a purposeful serif that differentiates characters is beneficial; sans serif is more vulnerable to look-alike letterforms (A Paragraph, p. 49). Typesetting probably matters more than the font choice, per Bigelow, unless the font is illegible (A Paragraph, p. 51).
- **Contrast.** High contrast is required, but very high contrast harms readers with Irlen syndrome, so the advice is to temper it slightly (A Paragraph, p. 57). The "Things to avoid" list restates it as reasonably high contrast without stark black on white (A Paragraph, p. 68).
- **Underlines.** Button-like call-to-action links "play by different rules of affordance" and are exempt from the underline convention (A Paragraph, p. 58).
- **Focus styles.** They may be replaced; the prohibition is on removing them (A Paragraph, p. 61).
- **Pseudo-content.** Not every screen reader and browser combination announces it; those that do not give a less informative but not a broken experience (A Paragraph, pp. 65–66).
- **Readability scores.** Flesch-Kincaid is subjective and an early warning system only; real users are the test (A Blog Post, p. 91).
- **Heading classes.** Styling an `<h2>` as an `<h3>` avoids structural errors but is to be used with caution, since in most cases an `<h2>` should look like one (A Blog Post, p. 79).
- **`<article>`.** Probably not, but maybe: on a listing page with several articles, JAWS's announcement is arguably useful (A Blog Post, pp. 84–85).
- **Semantic elements in general.** Sometimes the technically correct element is unsupported and has no impact on anyone, and sometimes its supported behavior is confusing; choose by user experience (A Blog Post, p. 85).
- **Single-page applications.** The argument for server-rendered content is scoped to static content meant for reading; where content changes a lot with interaction, client-side rendering enables an immediacy the server cannot (A Blog Post, p. 87). The same-page-link trick for the current nav item is unsuitable in a single-page application, where `aria-describedby` is better (Navigation Regions, p. 140).
- **Custom elements.** Inclusive web components are mostly ordinary semantic HTML inside a new API; only Custom Elements and, to a lesser extent, Shadow DOM pose problems (Evaluation By Pattern, pp. 117, 122). Positive `tabindex` inside Shadow DOM "may have some useful applications", though explicit ordering is not advised (Evaluation By Pattern, p. 123).
- **Positioning.** Avoid it "in all but the rarest of cases", which admits the cases; modal dialogs are one, to be tested across viewports and magnification (Navigation Regions, p. 132).
- **The current-page marker.** Any method is acceptable so long as the text stays readable and hue is not the only cue (Navigation Regions, p. 134). The wording of the hidden cipher is "open to debate" (Navigation Regions, p. 136).
- **Menu buttons.** Not every application reduces to a handful of views, and menu buttons are near-ubiquitous, so an inclusive implementation is formulated despite the rule against them (A Menu Button, pp. 155–156). Judicious animation "can aid comprehension" if designed with care (A Menu Button, p. 175).
- **Icon rendering.** A background image is not a deal breaker when the "menu" text is also present (A Menu Button, p. 159). `aria-label` is offered as a fix where SVG cannot be used, with SVG preferred "if you are able to" (A Menu Button, p. 167).
- **`aria-controls`.** Where design constraints or company politics prevent placing the menu after the button, the attribute is the fallback, and a link to the landmark is better still (A Menu Button, p. 170).
- **Touch targets.** A universal figure is "near impossible" given device variety; Apple and Android disagree; the BBC's inactive-space advice is set aside for navigation only (A Menu Button, pp. 176–178).
- **Paper prototyping.** Coded prototypes are the fallback when standard HTML elements suffice, and the paper stage is for the early process, not the styleguide (Inclusive Prototyping, pp. 181, 188–189).
- **Block-level links.** Technically valid since HTML5, with a genuine advantage in clickable area; rejected on UX grounds, not conformance (A List Of Products, pp. 212–214).
- **The "Size" label.** "Dimensions" would be more precise, but the simpler word wins because in context it means the same thing (A List Of Products, p. 200).
- **`<picture>` by viewport width.** Not an exact science: a user on a slow network may have a wide viewport (A List Of Products, p. 206).
- **The submit button.** Whether users understand submitting on choice rather than on a button is "a question for user testing" (A Filter Widget, p. 239).
- **Infinite scroll.** Rejected "unless implemented very carefully", and Featherstone's own middle option, a Load more button that later offers to turn auto-loading on, is reproduced (A Filter Widget, pp. 240–241).
- **The flex grid values.** The `10em` and `20em` figures need tweaking per content (A Filter Widget, p. 252).
- **Login/register choice.** There is "no right or wrong way" to present it; a full tab interface is overkill for two options but is available (A Registration Form, p. 264).
- **`<fieldset>`.** Technically valid around a whole form, and rejected only because it adds verbosity; HTML is judged by what helps or hinders, not by right and wrong (A Registration Form, pp. 272–273).
- **The `required` attribute.** Passed over on support and behavior at the time, with the general rule that HTML base semantics beat the ARIA extension when vendor support is acceptable (A Registration Form, pp. 275–276).
- **A live region per field.** Whether to add one for as-you-type feedback "is up to you"; `aria-invalid` alone tells the user on refocus (A Registration Form, p. 287).
- **Test-driven markup.** It cannot fail a build; it only highlights errors for a developer to see, and it is not a substitute for generic automated testing, which matters for WCAG compliance (Test-Driven Markup, pp. 306–307).
- **Errata.** The author expects inconsistencies and errors and asks for them to be reported (Further Reading, p. 308).

## 7. What has changed since publication

Each figure, tool, standard, or example the book leans on, checked in September 2026 against a later source that could be fetched. "Unchecked" means no source could be reached, or the source reached did not contain the figure; the reason is given each time. The web search budget for this session was exhausted before this section began, so every check below is a direct fetch of a named page.

- **WCAG 2.0 as the rule set, with 4.1.1 Parsing for duplicate `id`s (Evaluation By Pattern, p. 110; A Registration Form, p. 267).** WCAG 2.2 is the current W3C Recommendation and states that it removed one success criterion, 4.1.1 Parsing (w3.org/TR/WCAG22). The book's duplicate-`id` argument now rests on 1.3.1 and 4.1.2 rather than on a parsing criterion.
- **Touch targets: Apple 44 points, Android 48 pixels, no universal figure (A Menu Button, p. 177).** WCAG 2.2 added 2.5.8 Target Size (Minimum) at level AA: at least 24 by 24 CSS pixels, with five exceptions for spacing, an equivalent control, inline targets, user-agent-sized controls, and essential sizes (w3.org/WAI/WCAG22/Understanding/target-size-minimum). Apple's and Material's current figures are unchecked: both documentation pages render only their title without JavaScript.
- **Chrome does not support CSS hyphenation (A Paragraph, p. 54).** Changed. caniuse records full `hyphens: auto` support in Chrome from version 88, with partial support from 55, Firefox from 6, Safari from 5.1, and 96.9% global support; hyphenation still depends on the `lang` attribute (caniuse.com/css-hyphens).
- **`<hgroup>` was removed from the specification, and the HTML5 outline algorithm is unimplemented with "no sign it ever will be" (A Blog Post, pp. 77, 81).** Both changed. The current WHATWG standard defines `<hgroup>` as a heading with related content, its content model being zero or more `<p>` elements, one `<h1>`–`<h6>`, and zero or more `<p>` elements, which is the subtitle case the book worked around with a span, and it now defines the outline as all headings in tree order, which is the heading-based structure the book recommended in place of the old algorithm (html.spec.whatwg.org/multipage/sections.html). When the change landed was not confirmed from a fetched page.
- **Custom Elements v0 `registerElement` beside v1, and `extends: 'button'` to inherit `HTMLButtonElement` (Evaluation By Pattern, pp. 117–121).** The v0 APIs were targeted for removal in Chrome 80, around February 2020, per Chrome's own post; whether removal happened on that date is unchecked, since the post predates it (developer.chrome.com/blog/web-components-time-to-upgrade). The customized built-in form the book prefers is opposed by WebKit: its standards-positions issue is labeled "position: oppose", opened 2022-11-28, noting WebKit supports autonomous custom elements and has not implemented this aspect (github.com/WebKit/standards-positions/issues/97). The book's `<toggle-button extends button>` therefore does not work in Safari.
- **Shadow DOM severs `aria-labelledby`, `aria-describedby`, and `aria-controls` across the boundary (Evaluation By Pattern, p. 122).** Still true. The WICG Reference Target explainer describes the same limitation and proposes `shadowrootreferencetarget` and `referenceTargetMap` to forward references; the explainer presents it as a proposal under development, phased, not a shipped feature (github.com/WICG/webcomponents, reference-target-explainer).
- **Windows high contrast mode eliminates background images, so an icon drawn as a background disappears (Introduction, p. 17; A Menu Button, pp. 159–160).** Partly changed. MDN's `forced-colors` page, Baseline since September 2022, states that `background-image` is forced to `none` only for values that are not URL-based, that `box-shadow` and `text-shadow` are forced to `none`, that `color` and `background-color` are forced to system colors, and that browsers draw backplates behind text; `forced-color-adjust: none` opts an element out (developer.mozilla.org, forced-colors). A URL background image now survives; the book's advice to prefer SVG with `currentColor` still holds for the color inversion.
- **Screen reader users mostly navigate by headings; run NVDA with Firefox for maximum compatibility; test with NVDA or VoiceOver (A Blog Post, pp. 75, 96).** WebAIM's Screen Reader User Survey #10, December 2023 to January 2024, 1,539 responses: JAWS 40.5% and NVDA 37.7% as primary desktop reader, VoiceOver 9.7%; Chrome 52.3% as the browser, Edge 19.3%, Firefox 16.0%; the most common pairings JAWS with Chrome at 24.7% and NVDA with Chrome at 21.3%; headings at 71.6% as the way to find information on a long page, the find feature at 13.6%, landmarks at 3.7%; heading levels useful to 88.8% (webaim.org/projects/screenreadersurvey10). The heading claim holds; the Firefox pairing does not describe current use.
- **Alice Bartlett's research and "avoid `<select>` wherever possible" (A Blog Post, p. 86).** Holds in GOV.UK's own system: the Select component page says it should only be used as a last resort in public-facing services because research shows some users find selects very difficult, and points to radios and checkboxes instead (design-system.service.gov.uk/components/select).
- **GOV.UK's background-color focus style as the exemplar (A Paragraph, p. 62).** Changed in form. govuk-frontend v3.0.0, released 2019-07-29, introduced new focus styles to meet WCAG 2.1 AA, and the current guidance describes a yellow background with a black bottom border on links and a yellow outline with a thick black border on inputs, chosen to meet 1.4.11 on any GOV.UK background (github.com/alphagov/govuk-frontend/releases/tag/v3.0.0; design-system.service.gov.uk/get-started/focus-states). The principle, a filled highlight rather than a thin outline, is unchanged.
- **Tenon as an emerging accessibility QA product (A Blog Post, p. 90; Test-Driven Markup, p. 306).** Gone. tenon.io redirects to Level Access, whose FAQ says the API stopped accepting requests on 2023-08-07 and points to the Level Access Platform; the acquisition date is not on that page and is unchecked (levelaccess.com/tenon-retiring-faqs).
- **Lazy loading by swapping a `data-src` attribute with a script (A List Of Products, pp. 205–206).** Superseded by the platform: `loading="lazy"` on `<img>` is supported from Chrome 77, Safari 16.4, and Firefox 121, at 95.8% global support (caniuse.com/loading-lazy-attr).
- **Microdata for product structured data, tested with Google's Structured Data Testing Tool (A List Of Products, pp. 216–220).** Google's current documentation says it recommends JSON-LD where a site's setup allows it, treats microdata and RDFa as valid, and names the Rich Results Test as the validation tool; the retirement of the Structured Data Testing Tool is unchecked, since the 2020 post announcing its update could not be fetched (developers.google.com/search/docs/appearance/structured-data/intro-structured-data). The `<g-review-stars>` markup shown on p. 221 is Google's own results page and is unchecked.
- **Hidden navigation: James Foster's A/B test and Louie A's article (A Menu Button, pp. 155, 158).** Foster's page at exisweb.net no longer resolves, so the test is unchecked. The direction is corroborated by Nielsen Norman Group's 2016 study by Pernice and Budiu: hidden navigation cut discoverability almost in half, desktop users were at least 39% slower and mobile users 15% slower, and perceived difficulty rose (nngroup.com/articles/hamburger-menus).
- **Infinite scroll, on Derek Featherstone's Simply Accessible article (A Filter Widget, pp. 240–241).** simplyaccessible.com no longer resolves, so the article could not be re-read; a Baymard comparison of load-more, pagination, and infinite scroll returned 404 at the address tried, so the later evidence is unchecked.
- **Internet Explorer: `hidden` unsupported, `<switch>`/`<foreignObject>` fallback for inline SVG, the IE10/11 focusable-children flex bug, `::-ms-reveal` (Navigation Regions, p. 137; A Menu Button, pp. 167–168; A Filter Widget, p. 252; A Registration Form, p. 277).** Moot. Microsoft's lifecycle page states the IE11 desktop application ended support on 2022-06-15 and was disabled through an Edge update in February 2023 (learn.microsoft.com/en-us/lifecycle/products/internet-explorer-11).
- **`xlink:href` on `<use>` (A Menu Button, p. 164 and throughout).** MDN records `xlink:href` as deprecated since SVG 2 in favor of `href`, with `href` taking precedence where both appear; the Safari version that first supported plain `href` was not in the fetched content and is unchecked (developer.mozilla.org, SVG use element).
- **Suppressing pinch-zoom with `user-scalable=no` (The Document, p. 27; A Filter Widget, p. 245).** MDN states that browser settings can ignore the rule and that iOS 10 and later ignore it by default, and that WCAG requires at least 2x scaling with 5x as best practice (developer.mozilla.org, Viewport meta element). The advice holds; the switch also no longer works where the book feared it most.
- **Opera Mini as the one modern browser without viewport units (The Document, p. 32).** Unchanged: caniuse lists viewport units as not supported in any Opera Mini version, at 97.3% global support elsewhere (caniuse.com/viewport-units).
- **`::placeholder` needing prefixed twins in separate rules (A Registration Form, pp. 269–270).** Changed. Unprefixed `::placeholder` is supported from Chrome 57, Safari 10.1, Firefox 19, and Edge 79, at 97.0% global support (caniuse.com/css-placeholder).
- **The `required` attribute "not implemented uniformly" (A Registration Form, p. 276).** Changed. caniuse puts HTML5 form validation at 97.3% global support, with Safari fully supporting it from 10.1 (caniuse.com/form-validation). The book's second objection, that it marks empty fields invalid from the outset, is a behavior rather than a support gap and is unchanged.
- **A `password` role mooted for WAI-ARIA (A Registration Form, p. 268).** It did not arrive: the WAI-ARIA 1.1 Recommendation's role list has no `password` role (w3.org/TR/wai-aria-1.1).
- **`role="form"` on a `<form>` to make it a navigable region (A Filter Widget, p. 228).** ARIA in HTML now gives `<form>` an implicit `form` role and notes it is not exposed as a landmark unless it has an accessible name (w3.org/TR/html-aria). The explicit role is redundant; the name is what the book's technique needed.
- **CSS pseudo-content is announced and there is no supported "don't say this" property (A Menu Button, p. 162).** Partly changed. MDN documents alternative text for generated content with the `content: url(...) / "alt text"` syntax, marked Baseline widely available with some parts varying, and still warns that generated content is not in the DOM and some assistive technology will not announce it (developer.mozilla.org, CSS content).
- **FOIT avoided with an `onload` media switch or Font Face Observer (The Document, pp. 34–36).** The `font-display` descriptor, which MDN marks as available across browsers since January 2020, handles the block and swap periods without script; exact first versions were not in the fetched content and are unchecked (developer.mozilla.org, font-display). Font Face Observer's maintenance status is unchecked; its GitHub page showed 260 commits and open issues but no dates in the fetched content.
- **Google Fonts' `text=` parameter (The Document, p. 37).** Still documented: the API returns a file optimized for the characters requested, which can cut file size by up to 90% (developers.google.com/fonts/docs/getting_started).
- **`em` media queries because `rem` misfires in Safari, per Zell Liew (The Document, p. 30).** The 2016 article carries no update, so whether Safari fixed it is unchecked (zellwk.com/blog/media-query-units).
- **Recommended video players: YouTube, Able Player, PayPal's, Laura Kalbag's (A Blog Post, p. 97).** Able Player is maintained: version 5.0.0 was released 2026-06-21 as an npm package with an ES module entry (github.com/ableplayer/ableplayer/releases). PayPal's repository returns 404. Kalbag's player at ind.ie and the YouTube player are unchecked.
- **Tools named as live: a11y.css, revenge.css, forceFeed.js, Deque's live region playground, the Great British Public Toilet Map, Penflip, What Does My Site Cost, Contrast-A, Color Safe (various).** a11y.css is at version 5.3.0 with a 2014–2026 footer (ffoodd.github.io/a11y.css). forceFeed.js is on GitHub with 16 commits and no archive notice, its last commit date not in the fetched content. Deque's playground is live and in beta (dequeuniversity.com/library/aria/liveregion-playground). The toilet map is live at toiletmap.org.uk; who runs it now is unchecked. revenge.css's page returns 404. Penflip's domain does not resolve. whatdoesmysitecost.com loops redirects. Contrast-A failed on a TLS handshake and Color Safe's certificate does not match its host, so both are unchecked; the book already noted Contrast-A required Flash (A Paragraph, p. 56).
- **The Paciello Group as the author's consultancy and the source of the Color Contrast Analyser (front matter; A Paragraph, p. 57).** The group's site returned 403 to a fetch, so the rename and the analyser's status are unchecked.
- **Studies the book cites: the Spanish dyslexia font study, Chuck Bigelow's corroboration, the British Dyslexia Association's characteristics, the medication-icon study (A Paragraph, pp. 48–51; A Menu Button, p. 156).** All unchecked: the BDA style guide pages tried return 404, a later OpenDyslexic study could not be reached through PubMed or ERIC, and the other two were not fetched.
- **Readability tools: the TRAY Chrome extension and the author's readability-checker CLI (A Blog Post, pp. 89–90).** Unchecked; neither was fetched.
- **The author's informal Twitter poll on pinch-zoom and informal screen reader survey (The Document, p. 27; A Blog Post, p. 75).** Unchecked as sources; the survey's headline claim is corroborated by WebAIM above.

## 8. Where the book is weakest

- **Evidence is mostly the author's own experience and informal polls.** The pinch-zoom claim rests on "an informal poll" of the author's Twitter followers (The Document, p. 27); the heading-navigation claim on "my informal research" among screen reader users (A Blog Post, p. 75); the danger of grid systems on one screen reader misbehaving "in testing" (A Blog Post, p. 73); paper prototyping's value on the projects the author has worked on (Inclusive Prototyping, p. 181). Section 7 finds the heading claim corroborated by WebAIM; the others stand on the author's word.
- **Claims presented as established with one or no citation.** That sans serif is more readable is called "one well-supported claim" and then set aside without a source either way (A Paragraph, p. 48). That icons improve comprehension is "well established" on the strength of one medication-label study (A Menu Button, p. 156). The case against `<select>` is "compelling evidence" from a single talk (A Blog Post, p. 86). The hand-cursor rule rests on one blog post (A List Of Products, pp. 209–210). The average-user argument is a quotation from an article and an OXO marketing page (A Paragraph, p. 50; A List Of Products, p. 192).
- **Vendor behavior observed at one moment and stated as fact.** `aria-controls` is exposed only in JAWS (A Menu Button, p. 170); only JAWS announces `<article>` (A Blog Post, p. 85); Chrome does not hyphenate (A Paragraph, p. 54); Opera Mini alone lacks viewport units (The Document, p. 32); `required` is uneven and `::placeholder` needs prefixes (A Registration Form, pp. 269–270, 276); `<hgroup>` is gone and the outline algorithm will never come (A Blog Post, pp. 77, 81). Section 7 shows several of these reversed within a few years, and the book itself has no dates on its support claims beyond "at the time of writing".
- **Internal tensions.** Fixed widths are never to be set (The Document, p. 26), and the book sets `max-width` on `<main>` and on grid items (A Paragraph, p. 52; A Filter Widget, p. 251). Breakpoints are to come from content (The Document, p. 25), and the examples use `60em`, `120rem`, and `20em` media queries with no content named (The Document, p. 31; A Paragraph, p. 53; Navigation Regions, p. 143). Hidden navigation is "always a last resort" (A Menu Button, p. 155), and the chapter then builds one. Positioning is avoided "in all but the rarest of cases" (Navigation Regions, p. 132), and the skip link, the visually hidden class, and the current-page pointer all use it (The Document, p. 42; A Blog Post, p. 83; Navigation Regions, p. 134).
- **Slips the author invited reports of.** The "Things to avoid" list for paragraphs names tempered contrast, the chapter's own advice, as a thing to avoid (A Paragraph, p. 68). The utility class is `.visibility-hidden` on one page and `.visually-hidden` everywhere else (A Menu Button, p. 166; A Blog Post, p. 83). The readout for "90cm × 30cm" is given as thirty by ninety (A List Of Products, p. 199). The asterisk markup has a broken opening tag, `<strong class="red"*`, in the quiz example (A Registration Form, p. 274). The table-of-contents examples give two links the same `#endorsements` target (Navigation Regions, pp. 145, 151). The forceFeed script calls `cite.addAttribute`, which is not a DOM method (A Filter Widget, p. 256). The smooth-scroll code's fragment pattern, `/#._$/`, does not strip a fragment from a URL as its comment says (Navigation Regions, p. 148). The debounced validator binds `this` outside any handler (A Registration Form, pp. 286–287).
- **Examples that do not reach the claim.** "Sandra" is a constructed persona, not a research participant, and carries the argument that no user group can be written off (A List Of Products, pp. 192–193). The GOV.UK focus style is cited as an exemplar of inclusive service design without a study behind it (A Paragraph, p. 62). The points system, one, ten, or a hundred points by who benefits, is offered as the book's aim and cannot be measured (The Document, p. 45). The claim that a spinner "already say[s] what needs to be said" to sighted users leaves the live region unseen by a sighted user who cannot interpret the spinner (A Filter Widget, pp. 235–236).
- **Web-form advice is about one small form.** The registration pattern has three fields, all required, no server round-trip shown, and no error-summary list; the two-message validation model is stated for a form where a general "make sure your information is correct" message can stand in for a list of errors (A Registration Form, pp. 274, 280). The book does not say how the pattern scales to a long form, and its own toolbar for login versus register relies on how each screen reader happens to announce `aria-pressed` (A Registration Form, p. 265).
- **Test-driven markup cannot fail.** The chapter's own closing admits none of it can technically fail a build, and the mechanism depends on a browser's rendering of an unrecognized CSS property (Test-Driven Markup, pp. 302, 306). It is a visual lint, not a test in the sense the chapter opens with.
- **Deferred to other books.** Tab interfaces are handled by pointing at the author's earlier *Apps For All* twice (A Registration Form, p. 264; Test-Driven Markup, p. 294), so the one complex ARIA widget the book tests is one it does not explain. Responsive design and image performance are each declared out of scope after a page (The Document, p. 25; A List Of Products, p. 205).
- **A single-page-application reader gets a caveat, not a pattern.** The book's answers assume a document per page: the current-page link as a skip link, `role="form"` to survive a page refresh, the `get` form that rebuilds the page from the server (Navigation Regions, pp. 139–140; A Filter Widget, pp. 228–229). Each is followed by a note that a single-page application differs, and none is worked through for one.
