# Theme synthesis: offline and resilience

## What this file is for

This is one of the five theme syntheses for the reference track that [#1684](https://github.com/markgoho/doula-cloud/issues/1684) adds, on the path that [the forms synthesis](forms.md), [the inclusive components synthesis](inclusive-components.md), [the design system synthesis](the-design-system.md) and [the visual craft and type synthesis](visual-craft-and-type.md) took first. ADR-0041 gives the reference track a read-back and then an adopt-or-not decision in the shape of ADR-0021; #1684 puts a synthesis between the two, so that the founder's grilling session and the adopt-or-not ADR for this theme start from one page. The file lays out what each of the twelve reference-track books claims about what a product does when the network is slow, drops, or is not there at all: what still works, what a person sees while she waits, what she sees when a request fails, and what is kept for her; where the books agree; where they conflict; and what the repo has already decided. It contains no ruling. Every book on the track is named below, with "no position" where the book has none, so that a reader can tell an omission from an absence. #1684's table names one book with a position on this theme, *Going Offline*; the books show that eight more have one, *Form Design Patterns* and *Inclusive Design Patterns* at length and *Inclusive Components*, *Atomic Design*, *Flexible Typesetting*, *Laying the Foundations*, *Designing User Interfaces* and *Design Systems* narrowly, and each is given a full entry. Three books, *Refactoring UI*, *Expressive Design Systems* and *Giving a Damn About Accessibility*, have none.

Three neighbors share ground with this theme, and this file does not repeat them. The task list and "check before you start" patterns for a long form are [the forms synthesis](forms.md)'s; this file takes only what *Form Design Patterns* says about an interrupted task and saved progress. Where focus goes after a Load more press, and the live region as a control, are [the inclusive components synthesis](inclusive-components.md)'s; this file takes the wait itself and the performance reason for loading in pages. The metric-compatible fallback font and the type scale are [the visual craft and type synthesis](visual-craft-and-type.md)'s; this file takes only the slow-network reason the books give for treating a web font as an enhancement.

Page citations follow each read-back's own page rule, stated in its source line. *Inclusive Components* cites the PDF index, because the book prints no numbers. Every other book cites its printed page: equal to the PDF index for *Laying the Foundations*, *Refactoring UI*, *Designing User Interfaces* and *Giving a Damn About Accessibility*; the PDF index less one for *Inclusive Design Patterns* and *Design Systems*; less two for *Form Design Patterns*; less five for *Going Offline*, *Flexible Typesetting* and *Expressive Design Systems*; and, for *Atomic Design*, an offset that changes at two missing pages, as its read-back sets out. *Going Offline*'s Foreword carries no printed number and is cited by name. The read-backs are in `docs/research/books/`. Where a citation below differs from the one a read-back gives, it was taken from the book itself. Heydon Pickering wrote two books on the track, and each is named by its title wherever the two differ; Keith means *Going Offline*, Silver *Form Design Patterns*, Frost *Atomic Design*, Brown *Flexible Typesetting*, Couldwell *Laying the Foundations*, the Malewiczes *Designing User Interfaces*, and Kholmatova *Design Systems*. A sentence a book quotes from someone else is attributed to the person who said it. GOV.UK and MDN are not books on the track; where they appear below, each is either a source a book cites or a record the repo adopted. The repo records were read on 2026-10-03.

## The question

What does the product do when the network does not: what still works when a script, a font or a request fails to arrive; what a person sees while she waits and when a request fails; what is kept on her device or on the server so that an interruption costs her nothing; and how the product is built and checked for a slow or absent connection?

## What each book claims

**Going Offline** (Keith, 2018). The whole book is on this theme. Aaron Gustafson's foreword calls network connectivity the web's "Achilles' heel" and says that with no network at all "the web ceases to exist" (Foreword). Keith's own frame: networks "go bad", mobile networks get flaky on a train and Wi-Fi in a hotel room, and "When the network fails, the web fails" (Ch. 1, pp. 1–2); native apps outshine the web partly by working with no connection, and a website can now "continue working" when the network is not there (pp. 2–3).

*The enhancement.* A service worker is installed only on a first visit, so it "can only be deployed as an enhancement", which the author calls "a brilliant piece of design": supporting browsers are rewarded and others are not punished (Ch. 2, pp. 10–11). The fetch logic is look in the cache, otherwise fetch from the network, otherwise show a fallback, because a server down for maintenance and a person who "has lost their internet connection" end the same way (Ch. 5, p. 62). The fallback is an offline page cached at install, served in place of the page asked for without a redirect, and treated like a 404 page as a chance to show off the brand, with Trivago's maze as the example (pp. 63–65). The fetch code is designed "on a case-by-case basis" (p. 67), and there is "no one-size-fits-all service worker" (Ch. 9, p. 135).

*Freshness against speed.* Pages are fetched network first and copied into a cache as the person browses, so a person who loses her connection may "never even notice" for pages she has seen (Ch. 6, p. 86). Article pages can be served from the cache first, one version behind, a "small tradeoff" for speed, while a homepage where freshness is the priority is not (p. 87). A returning visitor then gets content almost at once whether online, offline or on an intermittent connection, and "a flaky connection" can be worse than none (pp. 92–93). The cache-first pattern goes by the name Offline First, a "somewhat misleading" name because a first visit still needs the network, and it treats "the network itself as an enhancement"; caching a whole site suits a game or a rarely changing book, but is "somewhat presumptuous" because a device has finite room (Ch. 6, p. 93). Storage is shared and not limitless, "sometimes gigabytes", and the HTTP cache is cleared before a service worker's cache (Ch. 7, p. 94).

*What the person sees offline.* The offline page can list the pages already cached, so she has "something to do while they're offline", and a Save for Offline button lets her choose what is kept, like Instapaper or Pocket (Ch. 8, pp. 108–110). Background Sync and Notifications let a service worker act "even when the browser isn't open", so data "can be synced", named as a direction beyond the book's recipes (p. 119). The recipes the book builds cache the responses to page and image requests, in the install, fetch and Save for Offline code of Chapters 4 to 8 (read-back section 4); syncing data is the frontier p. 119 names, not a recipe.

*The progressive web app.* Frances Berriman, who coined the term, said the name is "for your boss, for your investor, for your marketeer" (Ch. 9, p. 120). For Keith, "progressive" echoes progressive enhancement, which he calls "the most sensible way" to build anything for the web (p. 120), and a progressive web app is HTTPS, offline support through a service worker, and a Web App Manifest (p. 121). Early examples that worked only on mobile were a step backwards, and such an app is responsive "as a minimum baseline" (p. 131); a new one starts from the core task, then the simplest technology, "Not the best. The simplest", and only then layers service workers on (p. 133). Too many websites are "bloated, buggy, and slow" (p. 134). Remy Sharp is quoted that people will come to expect a progressive web app on the home screen to work (p. 135).

The read-back records that the book never names iOS Safari, that its install criteria were one vendor's and have since changed, that it says nothing about testing a service worker, and that its storage figure carries no source (read-back sections 7 and 8). It also records that service workers now have about 97% global support, against the book's "not exactly a field of green" (read-back section 7).

**Form Design Patterns** (Silver, 2018). A full position, spread across the book. Progressive enhancement is "about users": a reasonable experience "no matter their browser, device, or quality of connection", because a style sheet or script can fail to load (Ch. 1, pp. 35–36). The content works in HTML, "the basic experience is the best and most performant one", and an enhancement that adds no value is not added (p. 37); the approach builds "resilience baked in" (p. 38). A person with a network or JavaScript failure and no native date input gets a bare text box, and a well-written error message "may have to suffice" (Ch. 3, p. 177). Designs made for each device width add code that gives "slow-loading pages" (Ch. 5, p. 243). A filter works without JavaScript by a GET form that rebuilds the page on the server (Ch. 7, p. 288). Once Ajax is added, the page owes the person the loading indicator the browser used to give: a spinner, which does not say how long is left "or if the connection is slow", plus an announcement in a live region (pp. 295–297). Ajax costs data and battery (p. 301) and is "not necessarily faster" than a page load, because it gives up progressive rendering; Silver quotes Jake Archibald on how a page renders while it downloads (pp. 301–302). Ajax is kept for small updates, and the answer is found by research on "varying connection speeds"; screen size "shouldn't be used to infer" connection speed (p. 302). An upload shows a progress bar per file, because files are slow on a slow connection, and states for success and error (Ch. 8, pp. 332–336). Each expense in a one-thing-per-page flow is a trip to the server, "which is slow", so the add-another pattern sends them all in one trip, with the same flow working without JavaScript by building the fields on the server (Ch. 9, pp. 354–355). For a long task, people work on the go and are interrupted, so being able to "jump back into the middle" is crucial, and parts of the process happen offline (Ch. 10, p. 376); previous information is saved so they can return to it (p. 378), and the checklist asks to let users "save their progress" and return later (p. 381). Silver quotes Don Norman that checklists matter most "where there are interruptions" (p. 376).

**Inclusive Design Patterns** (Pickering, 2016). A full position, made in the first chapter and carried through its patterns. Progressive enhancement is "a cornerstone of inclusive design", and a strong foundation of content is "resilient to a multitude of network and scripting failures", a matter of when and for how long JavaScript or CSS is unavailable and not only whether (The Document, pp. 32–33). On slow networks the content arrives first, and a web font is an enhancement: a stalled font with invisible text is "uninclusive of users on temperamental networks", answered with Keith Clark's load-then-font technique (pp. 34–35). Printing a page, or printing it to PDF, is "currently the easiest offline solution" (p. 40). The article "Designing for the extremes", by Susana Gonzalez Ruiz, is cited for the point that a web app that performs on the most unreliable mobile network performs everywhere (A Paragraph, p. 50). A menu button's script is inline so that it is "less likely to fail", and the menu is usable where JavaScript fails (A Menu Button, p. 173). Alt text describes an image where the image request returns a 403, 404, 500 or 503 (A List of Products, p. 193), and serves a person on a slow network who has turned images off (p. 203). Developers' fast broadband is "a privileged and an unrepresentative" experience, so the chapter throttles to "Regular 3G", counts what a page costs in data, and compresses, lazy-loads and sizes images (pp. 204–206), while warning that a large screen can still be on a slow mobile network, "not an exact science" (p. 206). A filter is repopulated with XHR "where possible", with the loading symbol and a live region saying "Loading products." and then the count (A Filter Widget, pp. 232–234). Loading every result at once is "a serious performance bottleneck", so results come in pages; Derek Featherstone is quoted against infinite scroll, and the Load more button announces its loading and its result (pp. 239–244). The read-back records that the evidence is mostly the author's experience and informal polls (read-back section 8).

**Inclusive Components** (Pickering, 2018 on its copyright page, 2019 in the book table). A narrow position, in asides. A menu is first considered without JavaScript (Menus & Menu Buttons, p. 74), and a tabbed interface starts as a table of contents with same-page links, where an enhancement may turn out to be "a step you needn't take" (Tabbed Interfaces, p. 132). The author's mantra is "if it can't be done efficiently, don't do it at all", and a feature that costs a significant performance hit is abandoned, "how critical performance is on the web" (A Theme Switcher, p. 115; p. 129). An inclusive component is, among other things, "Performant" (A Content Slider, p. 182). A slider loads only its first image and the rest as they scroll into view, because most readers see only the first; the demo is to be watched with the network throttled to a low-end mobile setting; a loading indicator stands where an image will be; and the "no JavaScript" case is rare while "broken/failed JavaScript" is "distressingly common" (pp. 198–202). A card's pointer cursor is added by script, because if JavaScript fails the style "would be deceptive" (Cards, p. 292).

**Atomic Design** (Frost, 2016). A narrow position, in the workflow chapter. The web is a range of devices and "network speeds" (ch. 4, pp. 112–113), and a design system is to be "resilient", to "Treat performance as an essential design principle" with "fast-loading experiences", and to "Progressively enhance" from core experiences (p. 114). The "impact of the network" is one of the things a design shows only in the browser, not in a static comp (p. 119). A framework's unused CSS and JavaScript still downloads, "resulting in slower page loads" (ch. 1, p. 22).

**Flexible Typesetting** (Brown, 2018). A narrow position, on type over a slow connection. Performance is "the speed, loading sequence, and smoothness" of an experience, in part the result of typographic decisions, and "A lot of people have spotty and/or slow internet connections", so leaving performance aside leaves design work undone (Ch. 1, pp. 20–21). Many readers see a fallback font while the web font loads, and the change between the two has to be "as smooth as possible" (Ch. 4, p. 115). A composition is evaluated "without a network connection" and under network throttling (Ch. 6, p. 179), and every fix is weighed against "your performance budget" (p. 182).

**Laying the Foundations** (Couldwell, 2019). A narrow position, in its documentation chapter. More typefaces and weights make a page load slower, "particularly for users on mobile phone/cellular networks", so the choice between semi-bold and bold is "Pick one" (Chapter 9, p. 196). BBC GEL is praised for documenting edge cases, among them "What happens if JavaScript is turned off?" (pp. 205–206). Loading spinners are named among the small things to document, and IBM's Carbon is praised for its "Loading" guidance, with skeleton states, progressive loading and spinners (pp. 206, 208).

**Designing User Interfaces** (Malewicz and Malewicz, 2020). A narrow position, on the wait. A progress bar makes it "easier to wait without fear that something went wrong"; it is designed empty, half-filled and full, with a success state and a state for when progress "is interrupted"; and a spinner is for a process whose length cannot be predicted (Animation, p. 305). A button can turn into a progress bar, the worked example reading "SAVE", "SAVING..." and "SAVED" (p. 308).

**Design Systems** (Kholmatova, 2017). A narrow position, on performance as a principle; the book never names a network connection, a failed request or a wait. A principle is expressed through "the performance of the site" as well as its patterns (ch. 1, p. 42); qualities such as useful are givens, along with "accessibility and performance" (ch. 2, p. 49); and TED's purpose means "prioritizing performance and accessibility over flashy features" (p. 58). Dan Saffer is quoted for "signature moments", "an elegant 'loading' animation" among them (ch. 4, p. 99).

**Refactoring UI** (Wathan and Schoger, 2018). No position. The book says nothing about networks, loading, failure or offline use. The nearest is that an empty state, a screen with no data yet, is "a priority, not an afterthought" (Finishing Touches, pp. 203–205), which is about a new account, not a failed request.

**Expressive Design Systems** (Perez-Cruz, 2019). No position. The nearest is that color conveys the urgency of notifications, "success, warning, and error colors" (Ch. 3, p. 71).

**Giving a Damn About Accessibility** (Byrne-Haber, 2021). No position. The nearest is that accessibility testing belongs in the software process as usability and "performance" testing already do (Ch. 3, p. 38).

## Where the books agree

- **The core works first, and the rest is layered on so that its failure costs little.** Keith's service worker that "can only be deployed as an enhancement" and his build order of core task, simplest technology, then enhancement (Ch. 2, p. 11; Ch. 9, pp. 120, 133); Silver's progressive enhancement against "quality of connection" and a script that fails to load (Ch. 1, pp. 35–38); *Inclusive Design Patterns*' foundation "resilient to a multitude of network and scripting failures" (The Document, pp. 32–33); *Inclusive Components*' table of contents before tabs and its "broken/failed JavaScript" (Tabbed Interfaces, p. 132; A Content Slider, p. 202); Frost's "Progressively enhance" (ch. 4, p. 114); and Couldwell's praise for BBC GEL's "What happens if JavaScript is turned off?" (Chapter 9, pp. 205–206).
- **A slow connection is the common case, not an edge case, and the person building it is the one who does not see it.** Keith's flaky train and hotel networks (Ch. 1, pp. 1–2); *Inclusive Design Patterns*' "privileged and an unrepresentative" broadband and its "Regular 3G" throttle (A List of Products, pp. 204–205); Brown's "spotty and/or slow internet connections" (Ch. 1, p. 21); Frost's range of "network speeds" (ch. 4, pp. 112–113); Silver's research on "varying connection speeds" (Ch. 7, p. 302).
- **Check it without the network, or with a throttled one.** Brown evaluates "without a network connection" and under throttling (Ch. 6, p. 179); *Inclusive Design Patterns* throttles to "Regular 3G" (A List of Products, p. 204); *Inclusive Components* asks the reader to throttle to a low-end mobile setting (A Content Slider, p. 201); Keith tests his offline page by ticking the browser's Offline box (Ch. 5, p. 65); Frost names the "impact of the network" as something only the browser shows (ch. 4, p. 119).
- **Performance is a design decision, not a later fix.** Frost's "essential design principle" (ch. 4, p. 114); *Inclusive Components*' feature abandoned if it costs a significant performance hit (A Theme Switcher, p. 115); Kholmatova's performance as a given and TED's "performance and accessibility over flashy features" (ch. 2, pp. 49, 58); Brown's performance budget and typographic decisions as a cause of performance (Ch. 1, pp. 20–21; Ch. 6, p. 182); Silver's basic experience as "the best and most performant" (Ch. 1, p. 37); Keith's "bloated, buggy, and slow" websites (Ch. 9, p. 134).
- **A web font is an enhancement, and what loads first is what a slow connection shows.** *Inclusive Design Patterns*' stalled font and "temperamental networks" (The Document, pp. 34–35); Brown's fallback font seen while the web font loads (Ch. 4, p. 115); Couldwell's fewer weights for "cellular networks" (Chapter 9, p. 196). The fallback's metrics are [the visual craft and type synthesis](visual-craft-and-type.md)'s.
- **A wait is shown, and said.** Silver's spinner and live region once Ajax takes the browser's indicator away, and a progress bar per upload (Ch. 7, pp. 295–297; Ch. 8, pp. 332–334); *Inclusive Design Patterns*' loading symbol with "Loading products." and the result count (A Filter Widget, pp. 233–234, 244); the Malewiczes' progress bar that makes it easier to wait "without fear that something went wrong" (Animation, p. 305); *Inclusive Components*' loading indicator in an image's place (A Content Slider, p. 200); Couldwell's Carbon "Loading" guidance (Chapter 9, p. 208). How each is shown is a conflict, below.
- **Fewer and smaller requests.** Silver's one trip to the server for many expenses and Ajax kept for small updates (Ch. 9, pp. 354–355; Ch. 7, p. 302); *Inclusive Design Patterns*' results in pages and lazy-loaded, compressed images (A Filter Widget, p. 239; A List of Products, pp. 205–206); *Inclusive Components*' slider that loads only what is seen (A Content Slider, p. 198); Frost's unused framework code that still downloads (ch. 1, p. 22); Keith's cache, which skips the network for what is already held (Ch. 6, pp. 86–87).
- **An interruption is planned for.** Silver's "jump back into the middle" and saved progress (Ch. 10, pp. 376, 378, 381); the Malewiczes' progress bar state for when progress "is interrupted" (Animation, p. 305); Keith's reader who loses her connection and may "never even notice" (Ch. 6, p. 86).

## Where the books conflict

- **Update in place, or load a page.** Silver: Ajax is "not necessarily faster" than a page load, costs data and battery, and is kept for small updates, the answer coming from research on varying connections (Form Design Patterns, Ch. 7, pp. 301–302). *Inclusive Design Patterns*: a filter is repopulated with XHR "where possible", so a keyboard user is not sent back through the page (A Filter Widget, pp. 232–233). Keith's cache-first pages make a repeat visit near instant without either (Ch. 6, pp. 92–93).
- **Whether screen size says anything about the connection.** Silver: screen size "shouldn't be used to infer" connection speed, since most of his own mobile time is on Wi-Fi (Ch. 7, p. 302). *Inclusive Design Patterns*: a smaller viewport is "more likely" on a mobile network, so `<picture>` serves it a smaller image, while a large screen on a slow network is the case that makes it "not an exact science" (A List of Products, p. 206).
- **How a wait is shown.** Silver and *Inclusive Design Patterns* use a spinner or loading symbol with a live region, and Silver notes the spinner says neither how long is left nor whether the connection is slow (Ch. 7, p. 296; A Filter Widget, pp. 233–234). The Malewiczes: a progress bar where progress can be measured, a spinner only where it cannot, and a button that becomes the progress bar (Animation, pp. 305, 308). *Inclusive Components*: a placeholder that stands where the content will be (A Content Slider, p. 200). Couldwell names Carbon's skeleton states, progressive loading and spinners as things to document, without ranking them (Chapter 9, p. 208).
- **What the person keeps when the network goes.** Keith: pages already visited, kept by the service worker, an offline page that lists them, and a Save for Offline button for pages she chooses (Ch. 6, p. 86; Ch. 8, pp. 108–110). *Inclusive Design Patterns*: a print style sheet, because printing to PDF is "the easiest offline solution" (The Document, p. 40). Silver: progress saved on the server, so she can return to a long task (Ch. 10, pp. 378, 381).
- **What the failure page is for.** Keith: the offline page is a chance to show off the brand, a "witty message of sympathy" or Trivago's maze (Ch. 5, p. 65). Silver: where a script or the network fails, a well-written error message "may have to suffice" (Ch. 3, p. 177). No other book on the track designs a page for a failed request.
- **Evidence.** Keith's debugging walk-throughs are Chrome's tools only, and his storage figure carries no source (Going Offline read-back section 8). Silver's Ajax case rests on Jake Archibald's account of progressive rendering (Ch. 7, pp. 301–302). *Inclusive Design Patterns* rests on the author's experience and a cited article (read-back section 8; A Paragraph, p. 50). Brown's, Frost's, Couldwell's and Kholmatova's lines on performance and the network are stated without data.

## What the repo already decided

- **The standing expectation.** `CLAUDE.md`'s cross-cutting Performance line reads "What is built stays quick under a real Practice's data, not only a fixture's." It names data volume and no network condition.
- **The brief's smoothness commitments.** [`docs/design/brief.md`](../../../design/brief.md) makes smoothness "a requirement" that "gets checked, not hoped for", with six lines, among them "Nothing shifts after it paints", "Every action acknowledges itself within 100ms, even when the work behind it takes longer", and "Loading is skeletal, not spinning ... A spinner covering a whole page is a failure"; the same section says a form "remembers what was typed". Its Doherty Threshold row sets "under 400ms, end to end" for routine acts, with 100ms as the feedback floor, and "Over 400ms, the work is done optimistically or with skeletal loading, never with a spinner over the page". Its Zeigarnik Effect row reads "Nothing in this product loses work: an intake form partially filled at 3am survives the tab closing", and its conflicts section holds the Motion rule over Goal-Gradient and Zeigarnik: "progress is *shown*, never animated at somebody".
- **What is not checked, and why.** [ADR-0020](../../../adr/0020-smoothness-is-gated-on-causes-because-the-outcome-is-not-measurable-where-the-gate-lives.md), decided on [#418](https://github.com/markgoho/doula-cloud/issues/418) (closed 2026-08-29), gates smoothness on its causes and names "The 100ms acknowledgment floor and the 400ms Doherty completion budget" as not checked, because "Both are dominated by network and BFF latency" and "neither can be read honestly on a shared runner". It measures one outcome, that a `Skeleton` reserves the space of what it stands in for. It names "The blank first frame" as not checked: the app is "a client-rendered SPA", so "every route paints blank before JS boots", and "The intended answer is a service-worker precache rather than server rendering ... It is fog on #405". [#405](https://github.com/markgoho/doula-cloud/issues/405) (open) carries that as "A service-worker precache, for an instant first paint", pre-v1 and "not before the shell and Templates land". [`docs/test-plans/README.md`](../../../test-plans/README.md) makes every Time step `manual` on ADR-0020's reasoning, and the Budget's Time line in [`docs/journeys/README.md`](../../../journeys/README.md), from [#1683](https://github.com/markgoho/doula-cloud/issues/1683) (closed 2026-10-03), holds each routine act to 400 ms and 100 ms with "never under a spinner"; a test plan's Time step is timed "on the stage's device", with no network condition named.
- **Offline affordances are outside the layout commitment.** [ADR-0024](../../../adr/0024-layout-is-intrinsic-and-320px-is-a-conformance-commitment.md) covers "works" at 320px and not "refined", naming "install prompts, camera or offline affordances" as "a separate effort" about which it "deliberately promises nothing". #405's body records the same line under "Refining the mobile experience, as distinct from working at 320px".
- **The PWA layer is push only.** [ADR-0002](../../../adr/0002-message-transport-push-triggered-fetch.md) planned the frontend "as a PWA with a service worker" and chose push-triggered fetch: a content-free Web Push wakes the service worker, which fetches the Message from the BFF. [ADR-0026](../../../adr/0026-two-populations-two-sign-in-methods-and-one-token-table.md) states "Doula Cloud is a PWA". [#61](https://github.com/markgoho/doula-cloud/issues/61) (closed 2026-08-16) asked for "a minimal PWA layer: web app manifest + service worker registered on load, scoped only to push events (no offline caching/precaching)". `app/src/service-worker/index.ts` handles `activate`, `push` and `notificationclick` and has no `fetch` handler; its header reads "no offline caching, no asset precaching, per the ticket's explicit scope". `app/static/manifest.webmanifest`, linked from `app/src/app.html`, sets `name`, `short_name`, `start_url`, `display: "standalone"`, `background_color`, `theme_color` and one SVG icon, and has no `lang` or `description`; its two colors are held to the tokens by `tokens.spec.ts`, as [the visual craft and type synthesis](visual-craft-and-type.md) records. Of Keith's three parts of a progressive web app, the repo has HTTPS and a manifest, and the service worker does no offline work. #405's body records that the portal's quick exit, [#472](https://github.com/markgoho/doula-cloud/issues/472) (closed as not planned on 2026-08-30), counted "the service worker caches nothing per #61" among what was already true.
- **The app does not render without JavaScript.** `app/vite.config.ts` builds with `adapter-static` and a `200.html` fallback, and `app/src/routes/+layout.ts` sets `ssr = false`. [`docs/design/govuk-alignment.md`](../../../design/govuk-alignment.md)'s Dialog departure gives GOV.UK's progressive-enhancement reason for having no modal and answers it: "That requirement does not bind here -- Doula Cloud is `ssr = false` and client-rendered end to end, so every screen already depends on JavaScript to render at all, not only this one; adopting their no-JS floor would mean rebuilding the whole app, not this component." Its Tabs row reads "the app has no no-JS baseline to keep, since every route here already needs Svelte to render".
- **What a failed request shows.** The alignment table's *Service unavailable* and *There is a problem with the service* rows are Aligned on `templates/ErrorPage.svelte`'s `unavailable` (503) and `problem` (500 and any other unexpected status) states, built on [#471](https://github.com/markgoho/doula-cloud/issues/471) (closed 2026-08-30). Inside a form, `app/src/lib/formErrors.ts`'s `SERVICE_PROBLEM` is what a reader is told for "a 5xx, a dropped connection, a response we could not read": "There is a problem with the service. Try again in a few minutes." Its three Identity Platform mappers answer `auth/network-request-failed` with "We could not reach the service. - **A send that outlives an outage.** [ADR-0010](../../../adr/0010-notification-email-delivery-is-an-outbox-not-in-request.md) makes notification email an outbox so that "the send survives a crash between commit and delivery, and a Mailgun outage delays delivery instead of losing it", with retry "bounded, not infinite", about five attempts over a day and then dead-lettered; `api/internal/outbox`'s `BackoffSchedule` runs from 5 minutes to 18 hours. [ADR-0013](../../../adr/0013-outbox-delivery-gets-a-cloud-tasks-nudge.md) adds a Cloud Tasks nudge to the outbox's scheduled drain. These are the server's resilience to a vendor's outage, not the browser's to its own connection.
