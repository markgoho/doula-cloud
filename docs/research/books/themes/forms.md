# Theme synthesis: forms

## What this file is for

This is one of the five theme syntheses for the reference track that [#1684](https://github.com/markgoho/doula-cloud/issues/1684) adds. ADR-0041 gives the reference track a read-back and then an adopt-or-not decision in the shape of ADR-0021; #1684 puts a synthesis between the two, on the path the values track took, so that the founder's grilling session and the adopt-or-not ADR for this theme start from one page. The file lays out what each of the twelve reference-track books claims about how a screen asks a person a question, checks the answer, and helps the person recover from a refusal; where the books agree; where they conflict; and what the repo has already decided. It contains no ruling. Every book on the track is named below, with "no position" where the book has none, so that a reader can tell an omission from an absence. #1684's table names three books with a position on this theme; the read-backs show that two more, *Inclusive Components* and *Refactoring UI*, also have one, and both are given a full entry.

Page citations follow each read-back's own page rule, stated in its source line: *Form Design Patterns* and *Inclusive Design Patterns* cite the printed page, *Inclusive Components* cites the PDF index because the book prints no numbers, and *Designing User Interfaces* and *Refactoring UI* cite a printed page that equals the PDF index. The read-backs are in `docs/research/books/`. Heydon Pickering wrote two books on the track, and each is named by its title wherever the two differ; a bare Silver means *Form Design Patterns*, and the Malewiczes means *Designing User Interfaces*. GOV.UK is not a book on the track; where it appears below, it is either a source a book cites or the record that ADR-0021 adopted.

## The question

How is a question asked on a screen, how is the answer checked, and how does a person recover when the answer is refused?

## What each book claims

**Form Design Patterns** (Silver, 2018). The whole book is on this theme: ten chapters, each one form, measured against the Paciello Group's seven inclusive design principles and built by progressive enhancement from the native control (Introduction, pp. x, xv–xvi; Ch. 1, pp. 35–38).

*Asking.* The question protocol asks why each field exists, and first and last name are dropped from the registration form (Ch. 1, pp. 27–28). Every control has a `<label>` above it, closest to its own field, because a label directly above is read in "a single eye movement" (Ch. 1, pp. 20–21, 31). A hint sits above the control, inside the label or joined by `aria-describedby`, and a placeholder is not a hint because it disappears on typing and is mistaken for a value (Ch. 1, pp. 22–25); float labels save no space and lose the hint (pp. 25–27). Optional fields carry "(optional)" in the label and required fields carry no asterisk, since most fields are required once the question protocol has run, and each field's hint says why it is asked (Ch. 2, pp. 75–79). The form starts as one thing per page and groups questions only where research shows it helps, on Jarrett's finding that users "weren't bothered" by separate pages (Ch. 2, pp. 70–73). The common option comes first and is selected by default, which "stops users from ever seeing an error" (Ch. 2, p. 86; Ch. 3, p. 192). A field's width tells the length of the answer (Ch. 2, pp. 79–82). Select boxes are a last resort, radio buttons expose the options, and a long list becomes an autocomplete built on a hidden select (Ch. 3, pp. 124–131). The kind of date decides the control: three text boxes for a memorable date, the document's format for a date from a document, a picker for a chosen near-future date (Ch. 3, pp. 154–160). `type="number"` is for amounts only (Ch. 2, pp. 99–103), `autocomplete` tokens turn on autofill (pp. 97–98), auto-tabbing between split boxes is rejected because it takes control away (Ch. 4, pp. 206–207), and a password gets a reveal button in place of a confirm field (Ch. 1, pp. 38–45). Login and registration are separate pages with a link between them (Ch. 4, pp. 212–213). A "Check your answers" page adds a step and still reduces effort (Ch. 2, pp. 107–109). A progress bar is left out until research shows one helps, after the Carer's Allowance team removed a 12-step bar with no effect on completion, and "Step 3 of 4" in the heading is the first thing to try (Ch. 2, pp. 113–117). A long process that takes days gets "check before you start" and a task list (Ch. 10, pp. 373–380).

*Checking.* HTML5 validation is turned off with `novalidate` so that client and server errors look the same, and the script listens to the form's `submit` event so that Enter still submits (Ch. 1, pp. 49–51). Live inline validation interrupts too early or too late, although the author concedes "some evidence" that it helps in long forms; a checklist that ticks off each rule is the gentler variant (Ch. 1, pp. 61–62). A disabled submit button leaves the person wondering what is wrong and cannot be focused (pp. 62–63). Frequent errors point to a problem elsewhere, in the form's length or its guidance (p. 62). Rules forgive trivial mistakes such as surrounding whitespace (p. 60), and input is accepted under Postel's law (Ch. 2, pp. 103–106). A text area with a limit uses a character countdown in a polite live region and not `maxlength`, which truncates silently (Ch. 2, pp. 88–93).

*Recovering.* A refused submit changes three things: the document title is prefixed with the error count; an error summary headed "There's a problem", never "Error", appears at the top, takes focus, and links each error to its field; and an inline message in red with an icon sits above the field inside its label, with `aria-invalid` on the control (Ch. 1, pp. 51–58). A group's error goes in its legend, and the summary links to the first option (Ch. 3, pp. 186–190). One message is written to work in both places, and error copy is concise, specific, human, plain, active and blameless, with "Please", "invalid", "forbidden" and "mandatory" named as words to avoid, on a study that put custom error messages at a 0.5% conversion gain (Ch. 1, pp. 63–66). For a frequent task, undo beside a success message replaces a confirmation dialog, and a success message is a panel in the document flow, not a toast (Ch. 5, pp. 255–259). Removing a repeated item moves focus to the page heading, and no animation is added, because "needless animation is jarring" (Ch. 9, pp. 367–369).

The author limits all of this himself: rules can be broken "occasionally", a move away from convention waits for "thorough and diverse" research, and the expense chapter ends with no right or wrong pattern, only the one that fits (Introduction, p. x; Ch. 1, pp. 29–30; Ch. 9, p. 370). The read-back records that the headline evidence for one thing per page, Just Eat's 5% gain, came from a whole-checkout redesign with no control (Ch. 2, p. 69), that the one study the book names on live validation found forms 42% faster and is set aside on reasoning (Ch. 1, p. 61), and that GOV.UK has since moved the hint and the error out of the `<label>` into separate elements joined by `aria-describedby` (read-back section 7).

**Inclusive Design Patterns** (Pickering, 2016). The registration-form chapter calls forms "a 10,000-volt electromagnet" for usability problems (A Registration Form, p. 261). A login and a register form are offered as a choice up front, a `role="toolbar"` of two `aria-pressed` buttons with the chosen form following in source order, because a small "Don't have an account?" link under a login form is missed by a screen reader user reading top to bottom; the author says there is "no right or wrong way" to present it (pp. 262–266). Every control has a `<label for>` on a unique `id` (pp. 267–268). The placeholder is a hint and never a label, restyled dark and italic because its default gray fails contrast (pp. 268–271). A `<fieldset>` is warranted only when there is more than one distinct set, more than one field in the set, and a legend that would help each label (pp. 272–273). A required field keeps a familiar asterisk, hidden from screen readers, with `aria-required="true"` announcing "Required"; the HTML `required` attribute is passed over because support was uneven and it marks empty fields invalid from the outset (pp. 274–276). A checkbox reveals the password in place of a confirm field (pp. 276–278). On a refused submit, one general message goes into a `role="alert"` live region directly above the submit button, with a warning icon labeled "error:", and the person is deliberately not moved, because focusing the first invalid field is an "unexpected and unsolicited shift" (pp. 278–282). Each invalid field gets `aria-invalid="true"` and an `aria-describedby` hint saying what would make it valid (pp. 282–284). Validation reruns on `input` only after a failed submit, debounced so a screen reader is not put into "80's remix mode"; whether to add a live region per field "is up to you" (pp. 285–287). Labels describe purpose and brand voice does not get in the way, so a password field is not labeled "Secret incantation" (pp. 287–289). Outside that chapter, `<select>` is avoided wherever possible on GDS research (A Blog Post, p. 86); a sorting form is a `fieldset` of radio buttons with a submit button, and HTML and CSS are never replaced by JavaScript and ARIA where they suffice (A Filter Widget, pp. 227–232); and submitting on `change` without a button is left to user testing because it "usurps" control and iOS will not submit a form with no submit button (pp. 236–239). The read-back records the limit of the evidence: the registration pattern has three fields, all required, no server round-trip and no list of errors, and the book does not say how it scales to a long form (read-back section 8; A Registration Form, pp. 274, 280).

**Inclusive Components** (Pickering, 2018 on its copyright page, 2019 in the book table). The to-do list chapter is a small form, and it carries most of the book's position. A `<form>` element is needed so that Enter submits (A Todo List, pp. 44–45). A placeholder is not a label, because it disappears on focus and under autocomplete; a visible label sits above or to the left of the input "in almost all cases", the exception being an input and submit pair whose button label is descriptive enough; a placeholder prefixed "E.g." stops it reading as a value; and the default placeholder gray fails WCAG 1.4.3 (pp. 45–48). Disabling the submit button until the input is valid leaves an unfocusable button that is often missed, and it is "usually better" to let the person press the button and then report the errors (p. 49). Feedback after adding an item goes to a visually hidden `role="status"` live region rather than a focus move (pp. 50–52), and in testing at Bulb some users who heard an announcement thought their focus had moved (p. 53). Where a deletion is critical, a confirmation dialog is provided, and after a deletion focus goes to the list heading with a polite announcement (pp. 57–62). The toggle-button chapter adds that form controls carry a "longstanding association" with data collection, so a setting that takes effect at once is better as a button with `aria-pressed`, and a checkbox is used for a toggle only where the person will not think she is "submitting data" (Toggle buttons, pp. 13–15, 33). A settings screen is "just headings, subheadings, and form controls", grouped by `fieldset` and `legend` under descriptive names rather than "General" and "Content", and messages are told apart by content, with a bold "Error:" prefix at minimum (Notifications, pp. 225–229). A modal dialog is for urgent input that the person asked for or that is critical, a dialog asks a question, and long or complex content needs "its own page or screen" (Modal Dialogs, pp. 267–271). The read-back records that the book's own rule on labels, keep the label and change the state, reverses for voice-control users (Toggle buttons, p. 24).

**Designing User Interfaces** (Malewicz and Malewicz, 2020). The Forms chapter frames a form by conversion, the share of entries completed, and tells the designer to test every form with real users because target markets differ (Forms, p. 230). Every field has five designed states: normal, active, completed, unsuccessful and disabled, with a check mark inside a field for a successfully validated entry (p. 233). An error is a short description "directly under each field", in red, and validations are never all displayed under the entire form or in popups; the description can show the proper way to fill the field as an example, and the book's own example reads "The entered text is not a valid e-mail address" (p. 233). A password field gets "a little eye-icon" to preview the entry (p. 234). A label in Title Case is processed faster than one in uppercase (p. 234). Material-style inputs with a label that moves up are "OK", and the only rule is not to mix the two styles in one product (p. 237). A subtle inner shadow on a text field is said to slightly increase conversion, on "many studies" that are not named (p. 238). A left-aligned label directly above a left-aligned field is "always the best choice" on desktop and mobile; a placeholder serving as a label can work "in rare cases" such as a search bar (p. 241). Forms are single-column and narrow, about 320 to 500 points wide, and a form of six fields or more is divided into pages that say which step the person is on (p. 242). A field's length shows the amount of data it wants, a placeholder or a short example such as "XX-YYY" can suggest a format, a field can move the cursor past a hyphen for the person, and a longer description goes into the label or, less well, behind a tooltip icon (p. 244). A dropdown of five options or fewer becomes radio buttons, and a very long one gets a search box (pp. 245–247). Checkboxes and radio buttons act after the whole form is submitted, a switch acts at once, the most popular radio option can be selected by default, and the label is clickable (pp. 250–253). Optional fields are marked and required ones carry no red asterisk, and the best forms have one button (p. 256). A long form is split into steps with progress shown as a percentage, a step count or a slider, so the person knows where they are "at all times"; subtle animation and microinteractions give a form a "memorable feel", up to an animated character that follows the active field (p. 259). Pop-up sign-up forms are the product of "statistics meeting" poor experience, and an on-page form is recommended instead (Modals, popups, p. 268). The read-back records that the inner-shadow claim carries no citation and that the book's examples are mostly one invented product (read-back section 8).

**Refactoring UI** (Wathan and Schoger, 2018). A narrow position, on how a form looks rather than how it asks. A label 20px below the previous input and 20px above its own does not read as connected, and the rule is more space around a group than within it (Layout and Spacing, pp. 83–86). A text input and a checkbox are inset wells, lit from above with a lighter bottom edge and a dark inset shadow at the top (Creating Depth, pp. 155–156). Radio buttons can become selectable cards and a dropdown can be sectioned with icons (Finishing Touches, pp. 210–214), and a button inside an input is named as one of the moves a reader would not have thought of (Leveling Up, pp. 216–217). The chapter that calls labels "a last resort" is about displaying data, and it says in its first lines that it is not about forms (Hierarchy is Everything, p. 41). The read-back records that the selectable cards and the sectioned dropdown carry no note on keyboard or assistive use (read-back section 8).

**Atomic Design** (Frost, 2016). No position on how a question is asked or checked. The nearest is the taxonomy itself: form labels, inputs and buttons are its example atoms, and a label, a search input and a button joined together are its example molecule (ch. 2, pp. 43–45); and a custom dropdown found to underperform the native one is fixed once, in the system, so the fix reaches every instance (ch. 5, pp. 144–146).

**Laying the Foundations** (Couldwell, 2019). No position on how a question is asked beyond one line of its accessibility foundations: a form input always has a label, because an input on its own is most likely meaningless to a screen reader (Chapter 3, p. 62). The nearest beyond that is that a component is documented in every state, a text input's placeholder and value states among them, with hover, error and disabled (Chapter 8, pp. 159–162).

**Design Systems** (Kholmatova, 2017). No position. The nearest are that "button" can mean an outlined clickable area, a link or a form submit, so a team needs a shared use of language (ch. 1, pp. 28–30), and that a module named "Binary radio button" was precise and nobody remembered it (ch. 5, p. 114).

**Expressive Design Systems** (Perez-Cruz, 2019). No position. The nearest is that text fields are basic components, with buttons and links, where color and typography stay functional rather than expressive (Ch. 3, pp. 51–59).

**Flexible Typesetting** (Brown, 2018). No position. The nearest is that labels belong to the small-text job, one of the typographic jobs a text block is classified by (Ch. 3, p. 62).

**Giving a Damn About Accessibility** (Byrne-Haber, 2021). No position; the book has no section on forms. The nearest is that core adjacent services, surveys among them, are held to the same accessibility bar as the product (Ch. 4, pp. 42–43).

**Going Offline** (Keith, 2018). No position on a form, a submission, or what happens to an answer sent without a network; its recipes cache pages and images. The nearest is one line that Background Sync lets a service worker act "even when the browser isn't open", so that data can be synced, named as a frontier beyond the book's own recipes (Ch. 8, p. 119).

## Where the books agree

- **Every control has a visible label, and a placeholder is not one.** Silver (Ch. 1, pp. 20–25), *Inclusive Design Patterns* (A Registration Form, pp. 267–271), *Inclusive Components* (A Todo List, pp. 45–48) and the Malewiczes (Forms, p. 241) all say it, and *Laying the Foundations* says the first half in one line (Chapter 3, p. 62). Each names an exception: Silver a placeholder as the lesser "of two evils" for a date-format hint when neither the native date input nor JavaScript is there (Ch. 3, p. 178), *Inclusive Components* an input and submit pair with a descriptive button (A Todo List, pp. 45–46), and the Malewiczes a search bar (Forms, p. 241).
- **The label sits above the field.** Silver, on Penzo's eye-tracking (Ch. 1, p. 31), and the Malewiczes, as "always the best choice" on desktop and mobile (Forms, p. 241); *Inclusive Components* allows above or to the left (A Todo List, pp. 45–48). Refactoring UI reaches the same grouping from spacing: more space around a group than within it, so a label reads as its own field's (Layout and Spacing, pp. 83–86).
- **Mark the optional field, not the required one.** Silver (Ch. 2, pp. 78–79) and the Malewiczes (Forms, p. 256) agree, each on the ground that most of a form is required; *Inclusive Design Patterns* is the exception, below.
- **Show the password instead of asking for it twice.** Silver's reveal button (Ch. 1, pp. 38–45), *Inclusive Design Patterns*' checkbox (A Registration Form, pp. 276–278) and the Malewiczes' eye icon (Forms, p. 234) each replace a confirm field; the three disagree only on the control.
- **Do not disable the submit button to stop a submit.** Silver (Ch. 1, pp. 62–63) and *Inclusive Components* (A Todo List, p. 49) both say a disabled button cannot be focused and hides what is wrong, and both prefer letting the person press it and then saying why it refused. *Inclusive Design Patterns* keeps the button enabled and suppresses the submit event (A Registration Form, pp. 278–282). The Malewiczes design a disabled state for every field and do not discuss the submit button (Forms, p. 233).
- **Few options are shown, not hidden.** Silver calls a select box a last resort and exposes options as radio buttons (Ch. 3, pp. 124–131); *Inclusive Design Patterns* avoids `<select>` on the same GDS research (A Blog Post, p. 86); the Malewiczes turn a dropdown of five options or fewer into radio buttons (Forms, pp. 245–247).
- **A group of related controls gets a fieldset and a legend, but not every field does.** Silver (Ch. 2, p. 85; Ch. 3, pp. 191–192), *Inclusive Design Patterns*' three rules (A Registration Form, pp. 272–273) and *Inclusive Components*' settings screen (Notifications, pp. 225–227).
- **Mark the problem with more than color.** Silver's inline message carries an icon beside the red (Ch. 1, pp. 56–58); *Inclusive Design Patterns*' warning icon is labeled "error:" (A Registration Form, pp. 279–282); *Inclusive Components* asks for a bold "Error:" prefix at minimum (Notifications, pp. 228–229). The Malewiczes color the message red "for increased urgency" and name no second cue (Forms, p. 233).
- **Test the form with people.** Silver puts every departure from convention behind research (Ch. 1, pp. 29–30), *Inclusive Design Patterns* leaves submit-on-change to user testing (A Filter Widget, pp. 236–239), and the Malewiczes tell the designer to test every form with real users (Forms, p. 230).

## Where the books conflict

- **Where the message for one field goes.** Silver puts it above the field, inside the `<label>`, so it is part of the control's name (Ch. 1, pp. 56–58). *Inclusive Design Patterns* joins it to the control with `aria-describedby`, read after the label (A Registration Form, pp. 282–284). The Malewiczes put it "directly under each field" (Forms, p. 233). The Silver read-back records that GOV.UK has since moved both the hint and the message out of the label into separate elements joined by `aria-describedby`, with the message between the hint and the input (read-back section 7).
- **What a refused submit says, and where.** Silver lists every error in a summary at the top of the page, each a link to its field, and repeats each message beside its field (Ch. 1, pp. 51–58). *Inclusive Design Patterns* puts one general message in a live region above the submit button and marks the fields, with no list (A Registration Form, pp. 278–284). The Malewiczes put each message under its field and say to avoid showing all validations under the entire form (Forms, p. 233). The three are a list, one sentence, and no summary at all.
- **Where focus goes after a refused submit.** Silver moves focus to the error summary (Ch. 1, pp. 53–55). *Inclusive Design Patterns* deliberately leaves focus on the submit button, because moving it to the first invalid field is an "unexpected and unsolicited shift" (A Registration Form, pp. 281–282). *Inclusive Components* sends feedback to a live region rather than a focus move, and records Bulb testers who thought a live announcement had moved their focus (A Todo List, pp. 50–53). Neither of Pickering's books tests a form long enough to need a summary, which the *Inclusive Design Patterns* read-back names as that book's limit (read-back section 8).
- **When the check runs.** Silver checks on submit and calls live validation premature, while conceding "some evidence" for it in long forms; the Silver read-back records that the study he names found forms 42% faster with live validation (Ch. 1, pp. 61–62; read-back section 7). *Inclusive Design Patterns* checks on submit and then rechecks on every keystroke once a submit has failed, debounced (A Registration Form, pp. 285–287). The Malewiczes design a "completed" state with a check mark for a successfully validated field, which shows a result before the submit (Forms, p. 233).
- **How a required field is marked.** Silver and the Malewiczes mark the optional field and leave the required one bare (Ch. 2, pp. 78–79; Forms, p. 256). *Inclusive Design Patterns* marks the required field with an asterisk hidden from screen readers and `aria-required="true"` (A Registration Form, pp. 274–276).
- **What a placeholder may carry.** Silver: no hint, because it vanishes and reads as a value (Ch. 1, pp. 22–25). *Inclusive Design Patterns*: a hint, never a label, restyled to pass contrast (A Registration Form, pp. 268–271). *Inclusive Components*: an example, prefixed "E.g." (A Todo List, pp. 45–48). The Malewiczes: a format such as "XX-YYY" (Forms, p. 244), and the book's own example placeholder reads "Please enter your e-mail…" (Forms, p. 256).
- **The words of an error.** Silver names "Please", "invalid", "forbidden" and "mandatory" as words to avoid (Ch. 1, pp. 63–66). The Malewiczes' worked example is "The entered text is not a valid e-mail address" (Forms, p. 233). *Inclusive Design Patterns* asks only that labels describe purpose and that brand voice stay out of the way (A Registration Form, pp. 287–289).
- **Choosing an answer for the person.** Silver selects the most common option by default, so that the person never meets an error (Ch. 2, p. 86; Ch. 3, p. 192), and the Malewiczes allow the most popular radio option to be selected by default (Forms, p. 252). No other book on the track addresses a default answer. The repo record on the other side is GOV.UK's own rule against pre-selecting an answer to a question, quoted in the alignment table (below).
- **Steps and progress.** Silver starts with one thing per page and no progress indicator, adds "Step 3 of 4" to the heading first, and adds a bar only on research (Ch. 2, pp. 70–73, 113–117). The Malewiczes split a form only at six fields or more and always show progress, as a percentage, a step count or a slider (Forms, pp. 242, 259).
- **Login and registration.** Silver keeps them on separate pages, linked (Ch. 4, pp. 212–213). *Inclusive Design Patterns* puts both behind a two-button toolbar on one page, with the chosen form following, and says there is "no right or wrong way" (A Registration Form, pp. 262–266).
- **Revealing the password.** Silver's toggle is a `<button>` whose label changes between Show and Hide, with `aria-pressed` as the alternative if research finds the changing label confusing (Ch. 1, pp. 40–45). *Inclusive Design Patterns* uses a checkbox (A Registration Form, pp. 276–278). *Inclusive Components* argues against a checkbox for anything that takes effect at once, since a checkbox reads as data to submit (Toggle buttons, pp. 13–15, 33). The Malewiczes name an eye icon (Forms, p. 234).
- **Motion in a form.** The Malewiczes recommend subtle animation and microinteractions to make a form memorable and fun, up to an animated character that follows the active field (Forms, p. 259). Silver adds no animation to a form, because "needless animation is jarring" and can harm users with ADHD or autism (Ch. 9, pp. 368–369).
- **Moving the cursor for the person.** Silver rejects auto-tabbing between split boxes, on Léonie Watson's account that correcting its mistakes costs more than moving focus herself (Ch. 4, pp. 206–207). The Malewiczes describe a field that jumps past the hyphen after the first two digits so the person does not type it (Forms, p. 244).
- **Evidence.** Silver's figures are his own clients' redesigns with no control (Just Eat's 5%, Boots) and GDS findings reported from talks and posts (read-back section 8). *Inclusive Design Patterns* rests on the author's experience and informal polls (read-back section 8). The Malewiczes cite unnamed "studies" for the inner shadow and none for most rules (Forms, p. 238; read-back section 8). The one controlled study any of the three cites on a contested point, Wroblewski's on live validation, is the one Silver argues against (Ch. 1, p. 61).

## What the repo already decided

- [ADR-0021](../../../adr/0021-govuk-is-the-reference-for-service-patterns.md): when a screen asks a person for something or tells a person something went wrong, GOV.UK is the default reference; the decision is taken and the markup and the look are not; a departure needs a recorded reason on the same commit; and GOV.UK's content rules hold for what a person reads, "no 'please', no 'valid' or 'invalid', no 'required' in an error message". Its amendment of 2026-09-01 sets the order of sources where GOV.UK has no pattern: GOV.UK, then NHS.UK and ONS, then *Inclusive Components* and Adrian Roselli's writing, then Every Layout, then original work with a recorded reason. *Inclusive Components* is the one book on the reference track that a repo record already names as a source. That amendment is dated 2026-09-01, ADR-0041 was decided on 2026-09-10, and the book table in `docs/agents/literature.md` lists *Inclusive Components* at **read-back**.
- [`docs/design/govuk-alignment.md`](../../../design/govuk-alignment.md), the living half of ADR-0021, as it reads on 2026-10-02. *Recover from validation errors*: every form that submits renders `ErrorSummary` above the `<h1>` and the same string beside the field, with `novalidate` so the page refuses rather than the browser; the Engagement detail page's section-local operation outcomes stay a `Notice`. *Error summary*: it takes focus on appear and each entry's link focuses its control by the browser's own fragment steps. *Error message*: `LabeledField`'s message sits between the hint and the control, moved there from below the control on `198953e`, and `formErrors.usage.spec.ts` fails a commit on "please", "valid", "invalid" or "required". *Question pages*: the `QuestionPage` Template, one thing per page, legend or label as the `<h1>`. *Check answers*: `CheckAnswers`, with a Change link per row. *Dates* and *Date input*: a memorable date is three boxes, never a picker, and a chosen date is the native `type="date"`. *Text input*: the atom fills its container and a caller narrows a field. *Fieldset*: the Templates own the fieldset and the legend. *Radios* and *Select*: aligned, with `RadioGroup` unable to carry a hint per option. The *Autocomplete* section: a token names whose data it is, `off` on a field about someone else.
- The same table's departures. *Names*: given, family and preferred, split, against GOV.UK's single field. *Confirmation pages*: an outcome is a `Notice` in place, not a page of its own. *Complete multiple tasks* and *Task list*: not adopted. Three questions open with an answer chosen, against GOV.UK's Select rule that "you should not pre-select any of the options" on a question: *Who is this Visit for?* ([#909](https://github.com/markgoho/doula-cloud/issues/909)), the Practice timezone at signup ([#1166](https://github.com/markgoho/doula-cloud/issues/1166)), and *Who is the Doula?* on the Start work form ([#1515](https://github.com/markgoho/doula-cloud/issues/1515), [#1596](https://github.com/markgoho/doula-cloud/issues/1596)), each with its reason recorded there. The Radios row also records that a question with one answer left is not asked ([#1432](https://github.com/markgoho/doula-cloud/issues/1432)).
- Three rows of that table read differently from the tickets they name, as of 2026-10-02.
