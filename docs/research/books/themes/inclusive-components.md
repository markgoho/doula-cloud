# Theme synthesis: inclusive components

## What this file is for

This is one of the five theme syntheses for the reference track that [#1684](https://github.com/markgoho/doula-cloud/issues/1684) adds, on the path that [the forms synthesis](forms.md) took first. ADR-0041 gives the reference track a read-back and then an adopt-or-not decision in the shape of ADR-0021; #1684 puts a synthesis between the two, so that the founder's grilling session and the adopt-or-not ADR for this theme start from one page. The file lays out what each of the twelve reference-track books claims about how a control is built so that every person can operate it, whatever the input, the output, the eyesight or the screen; where the books agree; where they conflict; and what the repo has already decided. It contains no ruling. Every book on the track is named below, with "no position" where the book has none, so that a reader can tell an omission from an absence. #1684's table names three books with a position on this theme; the read-backs and the books show that seven more have one, *Form Design Patterns* at length and *Refactoring UI*, *Designing User Interfaces*, *Laying the Foundations*, *Flexible Typesetting*, *Design Systems* and *Expressive Design Systems* narrowly, and each is given a full entry.

How a form asks a question, checks the answer and reports a refusal is the forms synthesis's ground, and this file does not repeat it: labels and placeholders, the disabled submit button, the error summary and where focus goes after a refused submit, the password reveal, and select boxes against radios are all laid out there. Where a point below meets one of those, it names it in a clause and links to the forms synthesis.

Page citations follow each read-back's own page rule, stated in its source line. *Inclusive Components* cites the PDF index, because the book prints no numbers. Every other book cites its printed page: equal to the PDF index for *Giving a Damn About Accessibility*, *Refactoring UI*, *Designing User Interfaces* and *Laying the Foundations*; the PDF index less one for *Inclusive Design Patterns* and *Design Systems*; less two for *Form Design Patterns*; less five for *Flexible Typesetting*, *Expressive Design Systems* and *Going Offline*; and, for *Atomic Design*, an offset that changes at two missing pages, as its read-back sets out. The read-backs are in `docs/research/books/`. Heydon Pickering wrote two books on the track, and each is named by its title wherever the two differ; a bare Silver means *Form Design Patterns*, Byrne-Haber means *Giving a Damn About Accessibility*, and the Malewiczes means *Designing User Interfaces*. WCAG, GOV.UK and the WAI-ARIA Authoring Practices are not books on the track; where they appear below, each is either a source a book cites or a record the repo adopted. The repo records were read on 2026-10-02.

## The question

How is a control built so that a person can find it, tell what it is and what state it is in, and operate it, by keyboard, screen reader, voice, touch or pointer, at any zoom and without relying on color, and how is that checked?

## What each book claims

**Inclusive Components** (Pickering, 2018 on its copyright page, 2019 in the book table). The whole book is on this theme: twelve components, each built from the standard HTML element first, with WAI-ARIA added "as a progressive enhancement" only for a state HTML lacks, so that an interface works for "more and different people" (Introduction, p. 6; Toggle buttons, p. 15). Accessibility is "only a part of inclusive design": a control also has to make sense to a person and play "an unambiguous role" (Toggle buttons, p. 13), and inclusion is an "equivalent experience", not the same one (A Todo List, p. 52). An inclusive component is clear, interoperable across inputs and outputs, device agnostic, performant, and "Under the user's control" (A Content Slider, p. 182).

*State and toggles.* A checkbox is a serviceable on/off switch, but form controls carry a "longstanding association" with data collection, so a setting that takes effect at once is a `button` with `aria-pressed`, and a list of settings can use the `switch` role (Toggle buttons, pp. 9–15, 27–32). A state needs an explicit true or false (p. 15), and the styling hangs off the state attribute itself, so that "form should follow function" (p. 17). Pressed state and label never change together, except that a voice-control user is better served by a changing label (pp. 22–24). Color is never the only signal, which fails WCAG 1.4.1 (p. 20). Every interactive component has a focus style that does not affect layout, with a transparent outline that becomes visible in Windows High Contrast Mode (pp. 20–21). `aria-label` is not translated by translation services, and a visually hidden text node is (pp. 25–26).

*Structure and names.* Heading level "is actually a question of belonging", and a region is labeled by its own heading (A Todo List, pp. 37–40). TodoMVC's delete control appears only on hover, "an entirely inaccessible feature by keyboard" (pp. 35–36). An icon-only button gets a visually hidden label and its icon is hidden from assistive technology (pp. 55–57). Text beside an icon is the answer to a tooltip "most of the time"; the `title` attribute hides its content from touch, keyboard and most screen reader users; a toggletip announces through a live region and holds no interactive content (Tooltips & Toggletips, pp. 96–114).

*Menus, tabs and disclosure.* Navigation is lists of links, and ARIA menu roles are for "application behavior", in a project that closely imitates a desktop application (Menus & Menu Buttons, pp. 65–67, 81–85). A button that reveals content carries `aria-expanded` on the control and not on the content, and a collapsible section's button sits inside its heading (Menus & Menu Buttons, pp. 73–78; Collapsible Sections, pp. 154–157). A table of contents is "a superior way" to navigate than a hover submenu, and touch cannot be detected from screen size (Menus & Menu Buttons, pp. 69–72). The tab pattern moves focus with arrow keys and a roving `tabindex` (Tabbed Interfaces, pp. 135–141); testing found users who did not know to use the arrow keys, so the author tells clients to let the tabs take focus by Tab, to focus the panel on click, and to use no tabbed interface at all with more than four tabs, and he calls it fine to go "against standardized authoring advice" where research shows a pattern failing users (pp. 141–143). "Responsive design is inclusive design", because full-page zoom triggers the same breakpoints as a narrow window (pp. 143–144). A single-page application's views are reached by links, with focus moved to the new view and the `title` updated (pp. 146–150).

*Motion, messages and dialogs.* A content slider never moves "without the user's say-so" (A Content Slider, p. 183); a scrolling region that takes focus needs a role, a label, a focus style and instructions (pp. 185–192); a disabled previous or next button drops out of the focus order, so disabling them at the ends is left open (pp. 207–210). A notification only informs, and focus is not moved to it; message types differ by content, a bold "Error:" prefix at minimum; dismissing a notification by hand is "not something worth encountering", the messages leave on a timer, and a notification refers only to things discoverable elsewhere in the interface (Notifications, pp. 216–233). A modal dialog opens only on a person's action or a critical change of state, asks a question, keeps the page behind it undetectable, and returns focus to the control that opened it; long or complex content gets "its own page or screen" (Modal Dialogs, pp. 267–281).

*Tables, cards and themes.* Column headers are `th` with `scope`; a wide table scrolls in a parent that is focusable only when it overflows and is labeled by its caption; at very narrow widths the data takes a different structure, a definition list generated from the same arrays (Data Tables, pp. 237–256). A sort control is a button in the header, with `aria-sort` (pp. 256–260). A card's heading is its link, a block link is avoided, and the gap between cards grows on small screens for people with Parkinson's disease (Cards, pp. 286–304). A theme switcher honors the operating system's `prefers-color-scheme`, and a low-light theme is one that "adds real value" (A Theme Switcher, pp. 116, 128).

The author limits all of it: there is "no one way" to build any component (Toggle buttons, p. 8), none is a "just-copy-and-paste" exemplar (Cards, p. 313), and there is "no right or wrong in inclusive design" (Tabbed Interfaces, p. 151). The read-back records that much of the evidence is the author's own unquantified testing, at Bulb among others, and that many of the browser facts the book states as present, `inert` in Chrome only, `-ms-high-contrast`, no consistent native collapsible, have changed since 2018 (read-back sections 7 and 8).

**Inclusive Design Patterns** (Pickering, 2016). Inclusive design is a mindset rather than a skill set, and it is not harder than exclusive design, "just different" (Introduction, pp. 11–14). The worked example is a button: a styled `<div>` with a background image cannot take focus, has no role, vanishes in Windows high contrast mode, does not scale with the person's font size and cannot be translated, where `<button>` already does all of it (Introduction, pp. 14–18). The first rule of ARIA is quoted, and the chapter's summary is "never fix with JavaScript and WAI-ARIA" what HTML and CSS can do (A Filter Widget, pp. 226–232). An audit is reported by pattern and not by WCAG principle, because three developers fixing three tickets for one bad pattern end with a bloated `<div>` (Evaluation By Pattern, pp. 109–115). A custom element is only an `HTMLElement` until given focus, a role and behavior, and Shadow DOM severs ARIA references across its boundary (pp. 117–122). The document declares `lang`, never disables pinch-zoom, sets the root font size as a percentage and sizes in `rem` and `em`, takes its breakpoints from content rather than devices, and has a `<title>`, a `<main>` landmark and a skip link (The Document, pp. 22–42). Focus styles may be replaced but never removed, and a filled background is clearer than a dotted outline (A Paragraph, pp. 60–62); inline links stay underlined, because color alone fails color-blind readers (pp. 58–60); contrast is designed in from the outset and tempered, not stark black on white (pp. 56–57). Headings carry the structure, with one `<h1>` and no level skipped for size, and links and headings make sense out of context because a screen reader lists them (A Blog Post, pp. 74–79, 91–93). Navigation is a list in a `<nav>`, the current page is marked with more than color, and a table of contents is preferred to a drop-down submenu (Navigation Regions, pp. 127–144). A menu with few items is laid out, not hidden, because hiding functionality is "always a last resort"; a menu button says "menu" beside its icon, draws the icon as SVG, sits inside the `<nav>`, carries `aria-expanded`, and hides the closed menu so its links cannot take focus; `aria-controls` is passed over because only JAWS exposed it (A Menu Button, pp. 155–175). Touch targets are Apple's 44 points or Android's 48 pixels, with no universal figure (pp. 176–178). A link is a link and never takes `role="button"`, and a block-level link is valid but verbose and accident-prone, with Karl Groves's "To Hell With Compliance" cited for compliance as the minimum (A List Of Products, pp. 207–215). A Load more button replaces infinite scroll and moves focus to the first new item (A Filter Widget, pp. 239–245). Inclusive prototyping rules out any coded solution that is not keyboard-accessible or explicable to a screen reader (Inclusive Prototyping, pp. 188–189), and markup is tested against the pattern's own structure with CSS selectors that flag a malformed tab interface, though such a test cannot fail a build (Test-Driven Markup, pp. 294–307). The read-back records that much of the evidence is the author's own informal polls and that several vendor facts the book states as present have since reversed (read-back sections 7 and 8).

**Giving a Damn About Accessibility** (Byrne-Haber, 2021). The book is not about how a control is built; its position is on who builds it and how an organization decides. Technology does not make accessibility hard, people who do not "give a damn" do (Ch. 1, pp. 8–9), and demanding a business case for accessibility is "ableist", because access is a civil-rights question (pp. 11–12). WCAG does not prescribe a mechanism: a moving carousel needs a way to stop it, and that way need not be a button (p. 15). Overlays and widgets do not make a product accessible, and 10% of the accessibility lawsuits filed by the end of 2020 were against companies that had installed one (pp. 22–24). A first attempt "will be awful", "perfect" is undefined because WCAG is not prescriptive, and accessibility is a continuous process and not a project (Ch. 2, pp. 26–33). Good accessibility becomes great by going past the targeted level, the example being AAA touch-target size; by checking contrast in color-blindness modes and on focus indicators; by holding employee-facing tools to the same bar as public ones (Ch. 4, pp. 41–42); by testing with people who have disabilities, since testers simulating a disability is "never sufficient" and a congenital and an acquired disability give different perspectives (pp. 43–44); by making the design system accessible, because one defect in it "will show up in every single component" (p. 45); and by making accessibility a release gate, with an exceptions process for a team that wants to ship around it (p. 46). The read-back records that most of its figures carry no source and that two of its four example design systems have since been archived (read-back sections 7 and 8).

**Form Design Patterns** (Silver, 2018). The form patterns are the forms synthesis's; what the book says about a control in general is given here. Its measure is the Paciello Group's seven inclusive design principles, and its method is the native control first, "fully accessible out of the box", enhanced only where it is not good enough (Introduction, pp. xv–xvi; Ch. 3, p. 124). A label serves sighted users, screen reader users, and motor-impaired users, for whom it enlarges the hit area, on Laura Kalbag's visual, auditory, motor and cognitive parameters (Ch. 1, pp. 20–21). Focus outlines are restyled, never removed (Ch. 1, p. 33). A custom component meets Steve Faulkner's punch list, working without JavaScript, focusable, operable and usable with assistive technology, and the destination autocomplete is built against it as a `combobox` with one tab stop and a live region for the count of results (Ch. 3, pp. 129–153); the custom date picker is a `grid` with a roving `tabindex` and arrow keys, built only for browsers without the native one (pp. 161–178). Disabling is right for an unavailable seat, "one of the few" such cases (Ch. 3, p. 194). Menus open on click and never on hover, because a hover tunnel is hard to operate with a motor impairment, and a feature is never inferred "from screen size" (Ch. 5, pp. 245–246); a select box is not a menu, because WCAG forbids a change of setting from causing a change of context on its own (Ch. 5, pp. 238–239), and submitting a filter on `change` fails WCAG 3.2.2 by number (Ch. 7, p. 294); a true menu takes `role="menu"`, `aria-haspopup`, `aria-expanded`, and the arrow, Escape, Home and End keys, though the role is uncommon on the web and belongs to applications that mimic desktop ones (Ch. 5, pp. 246–253). "Select all" is a button that toggles, not a checkbox, because a control looks like "what it does", and the book repeats Pickering's line that accessibility is only a part of inclusive design (Ch. 5, pp. 253–254). Drag and drop sits beside a file picker and never replaces it, because a person with tremors may not be able to drag (Ch. 8, pp. 324–325). After a removal, focus goes to a heading, and no animation is added, because it can harm users with ADHD or autism (Ch. 9, pp. 367–369). The read-back records that several of the book's markup reasons rested on Internet Explorer 11 (read-back section 8).

**Refactoring UI** (Wathan and Schoger, 2018). A narrow position, on how a control looks to a person with low vision or color blindness. WCAG's 4.5:1 for normal text and 3:1 for larger text is the book's one outside rule, and "Accessible doesn't have to mean ugly": dark colored text on a light tint of the same hue passes where white text on a colored fill needs a dark fill that draws attention (Working with Color, pp. 142–145). Color is never the only channel: a red-green colorblind reader cannot tell a rising metric from a falling one without an icon, and chart series are told apart by lightness rather than hue (pp. 146–148). Decorative backgrounds stay at low contrast so that they do not interfere with content (Finishing Touches, pp. 200–202). The labels chapter opens by putting down "the accessibility pitchfork" and saying that it is not about forms (Hierarchy is Everything, p. 41), and a section title may be in the markup for accessibility and hidden visually (p. 47). The read-back records that the book's selectable-card radios and sectioned dropdown carry no note on keyboard or assistive use (read-back section 8).

**Designing User Interfaces** (Malewicz and Malewicz, 2020). A narrow position, mostly on contrast. Accessibility is making a product suitable for older users, visually impaired and color-blind users, and people on low-contrast, low-quality displays; every essential element, buttons, forms and essential text, meets at least AA contrast, 4.5:1, checked with a plugin, while decoration can be ignored (Colors, p. 98). A pie or bar chart is not told apart by color alone, and a pattern over the color is the fallback, tested by removing the color (Tables and Graphs, p. 227). A link is never shown by color alone, because people with color blindness may not see the difference (Navigation, p. 296). A side-scrolling table raises "accessibility issues" and is "the lesser of two evils" against a mini table per row (Tables and Graphs, p. 224). Neumorphism is "terrible for buttons" because of shallow edge contrast (Design Styles, p. 344). The meaning of an icon is not universal: in the authors' client research, 67% read a heart as "the product is healthy" (Icons, p. 168). The UI audit's accessibility test checks contrast with a plugin, flags every element below the WCAG rules, lets purely decorative objects fail, and checks alt text on images and labels on form elements (UI Audit, pp. 388–389). The read-back records that several of the book's figures carry no citation and that its contrast guidance is written against WCAG 2.0 (read-back sections 7 and 8).

**Laying the Foundations** (Couldwell, 2019). A narrow position, inside its Digital Foundations, where accessibility and inclusivity guidelines come before a design system. A form input always has a label, since an input on its own is most likely meaningless to a screen reader; an icon used without a text label is as much a question of experience and culture as of accessibility; and people navigate with a screen reader or a keyboard, not only a mouse (Chapter 3, pp. 62–63). Accessibility is framed broadly, quoting Don Norman, to include "a young, athletic parent" carrying a baby (p. 63). A component is documented in every state, hover, disabled, error and placeholder among them (Chapter 8, pp. 159–162), and Salesforce Lightning's documentation is praised for its accessibility notes (Chapter 10, pp. 228–229).

**Flexible Typesetting** (Brown, 2018). A narrow position, on text a person can resize and links a person can see. The root font size is set in a relative unit, because pixel sizes and viewport units do not respect a reader's own font-size preference (Ch. 2, pp. 44–46). `text-size-adjust` is avoided entirely: its `none` value stops type being resized, "a big problem" for readers with impaired vision, and the property "can cause serious accessibility problems" (Ch. 2, pp. 46–47). Links "should be underlined", as a familiar convention and "an accessibility boon" (Ch. 4, p. 136).

**Design Systems** (Kholmatova, 2017). A narrow position, which its read-back calls "present but thin" (read-back section 8). Qualities such as simple and useful are givens, "done by design", along with accessibility and performance (ch. 2, p. 49). Imagining an interface read aloud, with volume and intonation, also makes it more accessible to screen readers (ch. 3, p. 78). Buttons and links keep "a consistent expression of purpose" for people who see the interface and people who use a screen reader, on Pickering's split between links and calls to action, which also keeps the code "simple and accessible" (ch. 8, pp. 206–208). Contrast is tested against WCAG with a checker, and a palette built for accessibility from the start would need no rebalancing (ch. 9, pp. 229–231). Léonie Watson, a screen reader user, is reported as meeting a product through its "style of writing" (ch. 9, p. 238).

**Atomic Design** (Frost, 2016). No position on how a control is built; its read-back records that accessibility is "named but not treated" (read-back section 8). The nearest are that accessibility treated as a costly extra line item is "a fallacy" (ch. 1, p. 35); that baked-in accessibility is pitched to stakeholders as reaching more users and reducing the risk of a lawsuit (ch. 4, pp. 96–97); and that a custom dropdown found to underperform the native one is fixed once, in the system, so that the fix reaches every instance (ch. 5, pp. 144–146).

**Expressive Design Systems** (Perez-Cruz, 2019). A narrow position, in one example. Basic components, buttons, links and text fields, keep color and typography functional (Ch. 3, p. 53). Atlassian's toggle shows a change of state with both color and an icon, "which also makes it more accessible", and its documentation says when a toggle is right and when a checkbox is: a toggle never waits for a submit button, and where a submit is needed, checkboxes are used instead (Ch. 3, pp. 53–54). The conclusion adds that "systems aren't neutral" and that building accessibility into components from the outset needs "a heterogeneous group of people" contributing to the system (Conclusion, pp. 117–118).

**Going Offline** (Keith, 2018). No position. The nearest is one sentence that chooses a `<button>` as the control that saves a page for offline reading, "an accessible, all-purpose trigger", with a checkbox named as an alternative (Ch. 8, p. 110).

## Where the books agree

- **Start from the native element, and add ARIA only for what it lacks.** *Inclusive Components* adds WAI-ARIA "as a progressive enhancement" (Toggle buttons, p. 15); *Inclusive Design Patterns* quotes the first rule of ARIA and says "never fix with JavaScript and WAI-ARIA" what HTML and CSS can do (A Filter Widget, pp. 226–232), with a `<button>` against a styled `<div>` as its opening example (Introduction, pp. 14–18); Silver builds on native controls, "fully accessible out of the box", and goes custom only in four named places (Ch. 3, pp. 124, 198). *Atomic Design* comes nearest from the system side, with a custom dropdown that underperformed the native one (ch. 5, pp. 144–146), and *Going Offline* picks a `<button>` as "an accessible, all-purpose trigger" (Ch. 8, p. 110).
- **Accessibility is not the whole of it.** *Inclusive Components* says accessibility is "only a part of inclusive design" and that a control must also play "an unambiguous role" (Toggle buttons, p. 13); Silver repeats the line and makes "Select all" a button because a control looks like "what it does" (Ch. 5, pp. 253–254); *Inclusive Design Patterns* says a fully compliant interface can still be unusable and cites "To Hell With Compliance" (A List Of Products, pp. 214–215); Byrne-Haber separates compliance from empathy (Ch. 4, pp. 41–42).
- **Color is never the only signal.** *Inclusive Components* (Toggle buttons, p. 20; Notifications, pp. 228–229), *Inclusive Design Patterns* for links and the current page (A Paragraph, pp. 58–60; Navigation Regions, pp. 132–134), *Refactoring UI* for metrics and charts (Working with Color, pp. 146–148), the Malewiczes for charts and links (Tables and Graphs, p. 227; Navigation, p. 296), *Flexible Typesetting* for links (Ch. 4, p. 136), and *Expressive Design Systems* for Atlassian's toggle, color and an icon together (Ch. 3, p. 53). The second cue differs: a word, an icon, an underline, a lightness step, or a pattern.
- **Contrast is measured, not judged by eye.** *Refactoring UI* states WCAG's 4.5:1 and 3:1 (Working with Color, p. 142); the Malewiczes ask for AA on every essential element, checked with a plugin, and audit for it (Colors, p. 98; UI Audit, p. 388); *Design Systems* tests against WCAG with a checker (ch. 9, pp. 229–231); *Inclusive Design Patterns* designs contrast in from the outset (A Paragraph, pp. 56–57); Byrne-Haber extends the check to color-blindness modes and focus indicators (Ch. 4, p. 42). *Refactoring UI* and the Malewiczes both let purely decorative elements sit at low contrast (Finishing Touches, pp. 200–202; UI Audit, pp. 388–389).
- **Focus is always visible, and a default focus style is restyled, never removed.** *Inclusive Components* (Toggle buttons, pp. 20–21), *Inclusive Design Patterns* (A Paragraph, pp. 60–62) and Silver (Ch. 1, p. 33).
- **A control that appears only on hover, or only at one screen size, fails someone.** *Inclusive Components* on TodoMVC's hover-only delete and on touch not being detectable from screen size (A Todo List, pp. 35–36; Menus & Menu Buttons, p. 69); Silver on menus that open on hover and features inferred "from screen size" (Ch. 5, pp. 245–246); *Inclusive Design Patterns* on device breakpoints as futile and hidden functionality as "always a last resort" (The Document, pp. 25–26; A Menu Button, p. 155).
- **A table of contents, or a list laid out, beats a hidden submenu.** *Inclusive Components* (Menus & Menu Buttons, pp. 69–72) and *Inclusive Design Patterns* (Navigation Regions, pp. 143–144; A Menu Button, p. 155).
- **A disclosure carries `aria-expanded` on its button, and closed content cannot take focus.** *Inclusive Components* (Menus & Menu Buttons, pp. 73–78; Collapsible Sections, pp. 156–157), *Inclusive Design Patterns* (A Menu Button, pp. 169–175) and Silver's filter categories (Ch. 7, pp. 302–307).
- **A disabled control drops out of the focus order, so disabling is the exception.** *Inclusive Components* leaves disabled slider buttons open for that reason (A Content Slider, pp. 207–210) and Silver allows disabling only for an unavailable option (Ch. 3, p. 194). The disabled submit button is the forms synthesis's.
- **A hit area is large enough for an imprecise finger or hand.** *Inclusive Design Patterns* names 44 points and 48 pixels (A Menu Button, pp. 177–178), Silver 44px and a larger area for motor-impaired users (Ch. 1, pp. 20–21, 32; Ch. 8, p. 325), *Inclusive Components* a wider gap between cards for people with Parkinson's disease (Cards, p. 304), and Byrne-Haber AAA touch-target size as the step from good to great (Ch. 4, p. 41).
- **Text resizes with the person's own setting.** *Inclusive Design Patterns* (The Document, pp. 29–32) and *Flexible Typesetting* (Ch. 2, pp. 44–47) both set the root font size as a percentage and size in relative units, and both say why a fixed or viewport-only size defeats the reader's preference.
- **A design system carries accessibility to every instance, for good or ill.** Byrne-Haber's one defect that shows up in "every single component" (Ch. 4, p. 45), *Atomic Design*'s fix made once in the system (ch. 5, pp. 144–146), *Laying the Foundations*' accessibility guidelines placed before the system (Chapter 3, pp. 62–63), *Expressive Design Systems*' "heterogeneous group" of contributors (Conclusion, pp. 117–118), and *Inclusive Design Patterns*' audit by pattern, so the fix is the pattern (Evaluation By Pattern, pp. 113–116).
- **Test with people, and with disabled people.** Byrne-Haber says simulating a disability is "never sufficient" (Ch. 4, p. 44); *Inclusive Design Patterns* quotes GDS's advice to include disabled participants (A Filter Widget, pp. 238–239) and rules out a prototype that is not keyboard-accessible (Inclusive Prototyping, pp. 188–189); *Inclusive Components* departs from the tab pattern on testing (Tabbed Interfaces, pp. 141–143); Silver puts a move away from convention behind "thorough and diverse" research (Ch. 1, pp. 29–30).

## Where the books conflict

- **When `role="menu"` is right.** *Inclusive Components* keeps ARIA menu roles off navigation and reserves them for an application that closely imitates a desktop one, and makes the navigation button "a kind of hybrid" with `aria-expanded` and no menu roles (Menus & Menu Buttons, pp. 65–67, 79–85). Silver builds a true `role="menu"` with arrow, Escape, Home and End keys for an inbox's actions when the buttons do not fit, while calling the role uncommon on the web (Ch. 5, pp. 246–253). *Inclusive Design Patterns* gives a menu button that is a plain disclosure and offers no menu-role pattern at all (A Menu Button, pp. 169–175).
- **How tabs take focus.** *Inclusive Components* builds the WAI-ARIA pattern, arrow keys and a roving `tabindex`, and then, on testing, advises letting each tab take focus by Tab and focusing the panel on click, with no tabbed interface beyond four tabs (Tabbed Interfaces, pp. 135–143). *Inclusive Design Patterns* writes CSS tests that require the WAI-ARIA structure, `tabindex="-1"` on every unselected tab, and defers the behavior to the author's earlier book (Test-Driven Markup, pp. 294–299). The *Inclusive Components* read-back records that the current Authoring Practices still prescribe arrow keys and carry no note of the testing caveat, and that BBC GEL's tabs follow the book's alternative (read-back section 7).
- **What an on/off control is.** *Inclusive Components* makes a setting that takes effect at once a `button` with `aria-pressed`, or a `switch`, because a checkbox reads as data to submit, and allows a checkbox only where the person will not think she is "submitting data" (Toggle buttons, pp. 13–15, 27–33). Silver agrees for "Select all" (Ch. 5, pp. 253–255). *Inclusive Design Patterns* toggles the password's visibility with a checkbox (A Registration Form, pp. 276–278), *Going Offline* names a checkbox as an alternative to its save-for-offline button (Ch. 8, p. 110), and the Malewiczes say a switch acts at once while a checkbox acts on submit (Forms, pp. 250–253), the same line Atlassian's guideline draws in *Expressive Design Systems*, where a toggle never waits for a submit button and a checkbox is used where one is needed (Ch. 3, pp. 53–54). The password control is the forms synthesis's.
- **Whether a message can be dismissed, and whether it can leave on its own.** *Inclusive Components* drops dismiss buttons and lets each notification leave on a timer, since a notification refers only to things discoverable elsewhere (Notifications, pp. 230–232). Silver puts a success message in a panel in the document flow, rejects toasts because they vanish before they are read, and adds a Dismiss button only if research shows it is wanted (Ch. 5, pp. 255–258).
- **Focus move or announcement, after an item is added or loaded.** *Inclusive Components* announces an added item in a live region and does not move focus, and records Bulb testers who thought a live announcement had moved their focus (A Todo List, pp. 50–53). *Inclusive Design Patterns* moves focus to the first newly loaded item and uses a live region for the wait (A Filter Widget, pp. 240–245). Silver moves focus to the first new field on add and adds no notification, because the focus move is itself the feedback (Ch. 9, pp. 354–369). *Inclusive Components* and Silver both send focus to a heading when the focused item is removed (A Todo List, pp. 58–62; Ch. 9, pp. 367–368). Focus after a refused submit is the forms synthesis's.
- **How much depends on JavaScript.** *Inclusive Design Patterns* and Silver build every pattern as HTML first, enhanced by CSS and JavaScript that may fail (The Document, pp. 32–34; Ch. 1, pp. 35–38), and *Inclusive Design Patterns* says a page that needs client-side JavaScript to show static content underperforms (A Blog Post, pp. 87–88). *Inclusive Components* also enhances progressively, but says never to trade usability for a JavaScript-free build, which is "vanity" (Menus & Menu Buttons, p. 94).
- **Shadow DOM.** *Inclusive Components* builds its collapsible section as a web component with Shadow DOM and a `slot` (Collapsible Sections, pp. 166–176). *Inclusive Design Patterns* warns that Shadow DOM severs `aria-describedby`, `aria-controls` and their kin across its boundary (Evaluation By Pattern, p. 122).
- **A label that is not seen.** *Inclusive Components* keeps a visible label "in almost all cases" and prefers text beside an icon to a tooltip (A Todo List, pp. 45–46; Tooltips & Toggletips, pp. 97–98), and *Laying the Foundations* asks what an icon means without a label (Chapter 3, p. 62). *Refactoring UI* treats a label as "a last resort" for data, makes a needed one lower in contrast, and lets a section title be hidden visually (Hierarchy is Everything, pp. 41–47). The forms synthesis has the label on a form control.
- **How far past the minimum.** Byrne-Haber treats WCAG AA as the start and names AAA touch-target size and contrast checks beyond text as the step to great (Ch. 4, pp. 41–42). The Malewiczes ask for AA on essential elements and let decoration fail (Colors, p. 98; UI Audit, pp. 388–389), and *Refactoring UI* takes WCAG's ratios as its one outside rule (Working with Color, p. 142). *Inclusive Components* finds WCAG 2.2.2's pause control for a moving carousel "not good enough" and builds a slider that never moves on its own (A Content Slider, pp. 182–183).
- **How much contrast.** *Inclusive Design Patterns* tempers contrast, not stark black on white, because very high contrast troubles readers with Irlen syndrome and gives the author migraines (A Paragraph, pp. 56–57). The other books with a position on contrast set a floor and name no ceiling (Working with Color, p. 142; Colors, p. 98; ch. 9, pp. 229–231).
- **Why an organization does it.** Byrne-Haber calls a demand for a business case "ableist", because access is a civil-rights question (Ch. 1, pp. 11–12). *Atomic Design* pitches baked-in accessibility to stakeholders as reaching more users and reducing the risk of a lawsuit (ch. 4, pp. 96–97). *Design Systems* treats it as a given "done by design" (ch. 2, p. 49).
- **Evidence.** *Inclusive Components* rests on the author's own testing, reported without participant counts, and on a single tweet for the case against the tab pattern (read-back section 8). *Inclusive Design Patterns* rests on informal polls of the author's followers (read-back section 8). Byrne-Haber's figures mostly carry no source (read-back section 8). *Refactoring UI* cites no study and names WCAG as its only outside standard (read-back section 8), and the Malewiczes' icon figure is one client's research (Icons, p. 168). The one survey any read-back brings in, WebAIM's screen reader survey, is the *Inclusive Design Patterns* read-back's, which finds the book's claim that most screen reader users navigate by headings corroborated (read-back section 7).
