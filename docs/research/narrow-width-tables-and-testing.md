# Narrow-width tables, and testing intrinsic layout

Research date: 2026-08-30. Sources are quoted primary docs/specs/repos, not blog summaries, except where explicitly flagged as secondary.

## Question A: what does a wide data table become when there is no room?

### GOV.UK Design System

**They do not publish an answer.** The published component page ([design-system.service.gov.uk/components/table](https://design-system.service.gov.uk/components/table/)) only offers a text-size class for data-heavy tables: "If you have a lot of data, try to organise it into multiple tables or multiple pages. If you cannot split your data, you can use the CSS class `govuk-table--small-text-until-tablet`." That class shrinks text on small screens; it does nothing about columns not fitting. The page has no horizontal-scroll, stacking, or reflow guidance, and links out to an open discussion instead: "take part in the ['Table' discussion on GitHub](https://github.com/alphagov/govuk-design-system-backlog/issues/61)."

That backlog issue ([alphagov/govuk-design-system-backlog#61](https://github.com/alphagov/govuk-design-system-backlog/issues/61)) is **still open, 62 comments, oldest from Feb 2018, most recent Apr 2026** — confirmed live via `gh api`. It is the closest thing to an authoritative record of GOV.UK's actual position, which is: unresolved. Key primary quotes, in order:

- Adam Silver (GOV.UK design lead), 2018-10-05, laid out the three real options and declined to pick one: "There are a number of options to consider such as: (1) In the case of two or three column tables we could decide to use the 'Check your answers' pattern that actually uses a `<dl>` (2) To give the table container its own horizontal scroll bar with appropriate signifiers that this behaviour exists such as a fade out effect on the side (3) Using CSS to change the layout on small screens so that table headings are repeated for every row... I'm not sure there is one size fits all but at the moment, a pretty major component of the Design System is lacking an opinion for a fairly common scenario."
- `murfious` (Environment Agency, WRLS team), 2018-05-24, reported building real `<div>`-based flexible tables because "our tables are not optimised for small screens... We can make changes to the UI to make it respond and show the data in a stack but when we do this the context of the data is lost unless we do more work," and separately that screen-reader users lose header context on long/complex tables.
- `dnyuar` (HMRC), 2025-10-31 — as recently as last year, a service team was still hitting this from scratch and had to reverse-engineer a fix from other departments' design systems: "We currently have an issue displaying our tables in mobile view in which the table goes off the page when the table has 4 or more columns... The current table design pattern does not offer a responsive table pattern out-of-the-box," citing ONS's and NHS's design systems as the working references and porting their SCSS by hand.

No comment in the thread records GOV.UK adopting any of the three options as canon. Seven-plus years on, it remains an acknowledged gap.

### ONS Design System — the pattern GOV.UK never shipped

The Office for National Statistics service manual ([service-manual.ons.gov.uk/design-system/components/table](https://service-manual.ons.gov.uk/design-system/components/table)) did resolve it, and HMRC's 2025 comment above points at it as the reference implementation:

- A `responsive` variant: "Setting `"variants": 'responsive'` will stack the cells of each table row vertically when viewing on devices with a width less than the small breakpoint," with the column header repeated next to every cell so context survives the stack.
- Horizontal scroll is the default for every other case: "Horizontal scrolling is now applied to all table variants by default," with the scrollable wrapper carrying `role="region"` and an `aria-label` — the exact keyboard/ARIA pattern Question A also asks about below.

### WCAG 2.2 — 1.4.10 Reflow (Understanding document)

Fetched and grep-verified against the raw HTML of [w3.org/WAI/WCAG22/Understanding/reflow.html](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) — exact spec text:

> "Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions for: Vertical scrolling content at a width equivalent to 320 CSS pixels; Horizontal scrolling content at a height equivalent to 256 CSS pixels. Except for parts of the content which require two-dimensional layout for usage or meaning."

Where 320px comes from (Note 1, verbatim): "320 CSS pixels is equivalent to a starting viewport width of 1280 CSS pixels wide at 400% zoom." It is not a phone-screen number — it is a low-vision zoom number. (256px is the equivalent for vertical-text/horizontal-scroll content, derived the same way from a 1024px-tall start.)

The two-dimensional carve-out (Note 2, verbatim): "Examples of content which requires two-dimensional layout are images required for understanding (such as maps and diagrams), video, games, presentations, **data tables (not individual cells)**, and interfaces where it is necessary to keep toolbars in view while manipulating content. It is acceptable to provide two-dimensional scrolling for such parts of the content."

So: **yes, a data table explicitly qualifies for the exception** — the table as a whole may keep its two-dimensional (row × column) layout and scroll in both directions if needed. But the parenthetical "(not individual cells)" is load-bearing: each individual cell's *content* still has to reflow normally at 320px; you cannot use the table exception to justify a giant unwrapped paragraph inside one `<td>`. The Understanding doc's "Intent" section restates this: "sections of content within the two-dimensional layout, such as each cell within a table, would still need to meet this success criterion."

One more thing worth knowing before treating "320px, exactly" as gospel: it is contested even inside the WCAG working group. In a live discussion on the WCAG GitHub repo ([w3c/wcag discussion #4364](https://github.com/w3c/wcag/discussions/4364)), Patrick H. Lauke (a WCAG editor) confirmed the criterion is pinned to the literal number and nothing else: "1.4.10 requires that you test at the specified viewport width or height... as written, the SC only applies for those *exact* widths/heights. nothing more." Another commenter (`grifare`) pushed back that this makes "pass at 320px, fail at 321px" a real, legal outcome. This directly supports Question B's premise: even the normative accessibility spec, by its editors' own admission, only obligates testing at named points, not a continuum.

### Responsive table patterns, and what each one costs

**1. Horizontal scroll in an `overflow-x:auto` region.** The specific, documented requirement: the scrollable container needs `tabindex="0"` so it is keyboard-focusable (a `div` with `overflow:auto` is not focusable or operable by keyboard by default, which fails WCAG 2.1.1/2.1.3 Keyboard), plus `role="region"` with an `aria-label`/`aria-labelledby` so a screen-reader user gets an announced, named landmark rather than an anonymous scroll box. This is documented as an axe-core / accessibility-checker rule ("scrollable region must have keyboard access") and is also exactly what Adrian Roselli's own recommended markup does (below) and what ONS ships by default.

**2. CSS-only stacking via `display:block` on table rows/cells.** This is the classic "responsive table" trick (set `table, thead, tbody, th, td, tr { display: block; }` in a small-screen media query) and it is documented as actively harmful to table semantics. Adrian Roselli's primary write-up ([adrianroselli.com/2018/02/tables-css-display-properties-and-aria.html](https://adrianroselli.com/2018/02/tables-css-display-properties-and-aria.html)) states plainly: "using display: block | grid | inline | … on table elements will also override native semantics," and separately that "display: contents on a `<table>`, `<ul>`, `<ol>`, etc. also hides it from screen readers." He tracked this across browsers over time: as of Chrome 80 (Feb 2020) Chrome stopped dropping table semantics for `flex`/`grid`/`inline-block`/`contents`; Firefox still dropped it only for `display:contents`; "Safari dumps table semantics for everything" at that point. By an October 2023 update he notes the situation improved further across Chromium/Gecko/WebKit, though `display:contents` still isn't fully safe. His blunt conclusion: "If you find you want to use CSS flex, grid, block, inline, or other display properties on a table, then maybe consider what the heck you are doing with the table." The CSS-Tricks "Accessible, Simple, Responsive Tables" piece independently corroborates the practical failure mode — testing found "Neither ChromeVox or VoiceOver tells you when you are on a table heading. `<thead>`, `<th>` and even `scope=\"row|col\"` don't seem to do anything!" once the display-block stacking trick is applied, i.e. the semantics you were relying on are simply gone for those users.

**3. A genuinely different layout at narrow widths (cards / description list per record).** Heydon Pickering's Inclusive Components "Data Tables" pattern ([inclusive-components.design/data-tables](https://inclusive-components.design/data-tables/)) recommends exactly this instead of touching the table's own CSS: "for very narrow (one column) viewports, we can present the data using a different structure, with headings and definition lists," mapping `<caption>` → `<h2>`, row `<th scope="row">` → `<h3>`, column `<th scope="col">` → `<dt>`, and `<td>` → `<dd>`. Crucially, both structures (table and list) live in the DOM at once and a media query toggles which is visible — the table is never mangled by CSS display tricks; a second, independently-correct structure is swapped in instead. This is the same shape as GOV.UK's own "Check your answers" `<dl>`-based pattern that Adam Silver floated as option (1) above, and the same shape the WRLS/Environment Agency team built by hand in 2018.

### Adrian Roselli's actual recommendation

Roselli tested a scrolling version against a CSS-reflow ("stacked") version with real users and picked the scroll: "I have tested this with users, along with the version I made that reflows the content, and this one performs better for all users" ([adrianroselli.com/2020/11/under-engineered-responsive-tables.html](https://adrianroselli.com/2020/11/under-engineered-responsive-tables.html)). His build is the unmodified `<table>` wrapped in a parent `<div role="region" aria-labelledby="…" tabindex="0">` with `overflow:auto` and a visible focus outline — i.e., pattern (1) above, done properly, rather than pattern (2) or (3). His stated reasoning against reflow/stacking: it breaks native semantics in some browsers ("some browsers break the semantics" and screen-reader users "will be stranded"), and spanning header cells have no ARIA equivalent to fall back on ("ARIA has no attribute that maps to the HTML `headers` attribute"), so a stacked table with any `colspan`/`rowspan` cannot be fully repaired with ARIA alone. His steady position across both posts: don't change the table's `display`; if you must present something else at narrow widths, build a second, real structure (his scroll wrapper, or Pickering's parallel `<dl>`), never fake one out of a mangled `<table>`.

### Is there a query-free CSS answer?

No — and it's worth being direct about why, rather than hand-waving it. Every real solution above (ONS's stacked variant, Pickering's `<dl>` swap, Roselli's scroll wrapper's visual affordances) is switched on by a **media query or container query** at some named threshold; none of them is triggered by CSS alone reacting continuously to available space. The reason is structural, not a tooling gap: an HTML `<table>`'s rendering algorithm binds every row to the same column grid — there is no CSS sizing keyword (`min-content`, `max-content`, `fit-content()`) that can turn a table into a stacked list, because that isn't a sizing change, it's a structural one (columns becoming rows). `min-content`/`fit-content` column sizing genuinely is useful and query-free, but only for the *narrower* problem of "let each column be as narrow as its content allows" — it buys you some room, it does not solve "there is no room at all," and it never removes the two-dimensional column relationship the way a stack or a `<dl>` swap does.

CSS Grid's `grid-template-columns: repeat(auto-fit, minmax(...))` is the nearest thing to a genuinely intrinsic, query-free reflow, but it only works for a collection of independent items (cards) that don't need to stay aligned to each other's columns — which is precisely why Pickering's and ONS's "narrow" alternative is a card/`<dl>` layout and not a repurposed `<table>`. Container queries (`@container`) are the modern, correct replacement for a *viewport* media query in this exact spot — a table region can switch layout based on its own container's width rather than the window's — but a container query is still a query; it's container-scoped rather than viewport-scoped, not query-free.

## Question B: how do you test an intrinsic layout without enumerating widths?

### There is no established continuous-range technique — everyone samples discrete points, including WCAG itself

Every practitioner tool found here works by testing a **finite list of named widths**, not a range:

- **Percy** (browserstack.com/docs, via search of docs.percy.io): responsive snapshotting takes an explicit `widths` array — `.percy.yml`: `version: 2 / snapshot: / responsiveSnapshotCapture: true / widths: [375, 768, 1020, 1440]` — or per-call, e.g. `cy.percyResponsiveSnapshot('My Page', { widths: [468, 860] })`. Percy resizes and re-renders server-side per listed width; "a snapshot of your homepage at 375px and 1280px will count as 2 screenshots" against your usage quota — i.e. cost scales linearly with how many discrete points you add, not with coverage of the range between them.
- **Playwright**: has no built-in width-sweep primitive. The practitioner pattern is a manual `for` loop calling `page.setViewportSize({width, height})` over a hand-picked list (e.g. `[375, 768, 1280]`) — again discrete sampling, just automated.
- **BackstopJS / Chromatic**: same shape — configured viewport/breakpoint lists, compared to baselines per listed width.

This isn't a tooling shortcoming so much as a reflection of how the accessibility spec itself is written. On the WCAG project's own GitHub Discussions ([w3c/wcag discussion #4364](https://github.com/w3c/wcag/discussions/4364), fetched via `gh api graphql`), a WCAG editor (Patrick H. Lauke) confirmed 1.4.10 Reflow "only applies for those *exact* widths/heights. nothing more" — meaning even the normative test for reflow is a point-sample by design, and a layout that fails at 321px but happens to pass at exactly 320px is, per the editors, conforming. **Nobody in the tools or the standard treats this as a continuum problem with a continuum solution; the practical answer in the wild is "sample more points," not "prove the range."**

Consistent with that: **axe-core has no automated rule for 1.4.10 Reflow at all.** Search results describing axe-core/accessibility-scanner coverage state plainly that "there is no fully automated axe-core rule that confirms 1.4.10 Reflow" — automated tools can flag proxies like fixed-width elements or `overflow` properties, but confirming that a real layout reflows without 2D scrolling still requires a manual or visual check at the specified widths.

### What can be asserted statically from CSS source

This is where real, maintained tooling exists, as opposed to Question B's first half. **stylelint-plugin-defensive-css** ([github.com/yuschick/stylelint-plugin-defensive-css](https://github.com/yuschick/stylelint-plugin-defensive-css)) is a real, actively maintained lint plugin aimed at exactly this class of footgun. Its most relevant rules, confirmed from the repo:

- `no-fixed-sizes` — flags fixed pixel values on sizing properties (width, height, font-size), spacing (margin/padding/gap), typography (line-height/letter-spacing), and even `@media`/`@container` at-rules, pushing toward relative units.
- `require-grid-minmax` — flags loose `1fr` on `grid-template-columns`/`grid-auto-columns` and auto-fixes to `minmax(0, 1fr)`. This is directly the grid sibling of the flexbox footgun below: an unconstrained `1fr` track, like an unconstrained flex item, has an implicit non-zero automatic minimum size and will refuse to shrink, blowing out the container — `minmax(0, 1fr)` is the grid equivalent of `min-width: 0`.
- `require-flex-wrap`, `require-overscroll-behavior`, `require-scrollbar-gutter` — adjacent hygiene rules for flex/scroll containers.

I did not find a maintained lint rule specifically named for `white-space: nowrap` or `overflow: hidden` on text nodes as a standalone check — the closest published tooling is the defensive-css philosophy in general (treat any property that stops content from adapting as suspect), not a dedicated rule I can point to by name. Flagging that honestly rather than inventing a rule that doesn't exist.

**The `min-width: auto` flex-item footgun — primary source, not a summary of a summary.** The behavior is defined normatively in the CSS Flexbox spec itself, §4.5 "Automatic Minimum Size of Flex Items" ([w3.org/TR/css-flexbox-1/#min-size-auto](https://www.w3.org/TR/css-flexbox-1/#min-size-auto)), fetched and grepped directly from the spec source:

> "The auto keyword, representing an automatic minimum size, is the new initial value of the min-width and min-height properties... To provide a more reasonable default minimum size for flex items, the used value of a main axis automatic minimum size on a flex item whose computed overflow value is non-scrollable is its content-based minimum size; for scroll containers the automatic minimum size is zero, as usual."

In plain terms: a flex item's `min-width` defaults to `auto`, and `auto` resolves to the item's **content-based minimum size** (its `min-content` size — e.g. the widest unbreakable word or unbreakable inline run inside it) unless the item itself has `overflow: auto|scroll|hidden` set, in which case the automatic minimum collapses to zero. This is *why* a table cell, a flex child holding a long unbroken string (a URL, an amount with no wrap point), or any text-bearing flex/grid child will refuse to shrink below the width of its longest unbreakable content and will blow out its container — it is not a bug, it is the spec's deliberate default, chosen so ordinary content doesn't get silently crushed to nothing. The fix (`min-width: 0` on the flex item, or `min-height: 0` for a column-direction item) explicitly overrides that default back to zero, at the cost of re-enabling the crush-to-nothing behavior the default exists to prevent — which is exactly why `overflow-x:auto`/`text-overflow:ellipsis` are usually paired with it. CSS Grid items have the identical default and the identical fix, which is what `require-grid-minmax`'s `minmax(0, 1fr)` auto-fix (above) is doing under the hood.

### Detecting "the page scrolls horizontally" generically

The standard DOM measurement (per [MDN's `Element.scrollWidth`](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollWidth) and `clientWidth` definitions):

```js
document.documentElement.scrollWidth > document.documentElement.clientWidth
```

`scrollWidth` is the element's full content width including whatever overflows off-screen; `clientWidth` is the visible viewport width (padding included, border/scrollbar excluded). A positive delta means something is wider than the viewport.

False positives and blind spots, all real and all worth designing around:

- **It only catches document-level overflow.** A legitimate, intentionally scrollable region — exactly the `overflow-x:auto` table wrapper recommended in Question A — has its own internal `scrollWidth`/`clientWidth` delta on that specific element, not on `document.documentElement`. The document-level check will report "no horizontal scroll" even while a table inside the page is scrolling, and conversely will not tell you *which* element is responsible when it does fire — you have to walk descendants and repeat the same comparison per element to localize the culprit.
- **Sub-pixel/rounding noise.** Borders, `box-shadow`, or a fractional layout rounding can trip a 1px delta at the document root that is not a real layout defect worth flagging.
- **Browser scrollbar overlay behavior varies.** Some browsers (and platforms) overlay the scrollbar on top of content rather than reserving track width for it, which can shift the exact `clientWidth` value being compared and make the same page report a different delta across browsers even with identical layout.

This measurement is also, notably, the only thing close to a generic runtime check for 1.4.10 Reflow that the research above turned up — and it still only tells you *whether* scroll happened at the width you tested, not whether it will hold across the untested widths in between (back to Question B's opening finding: nothing tests the continuum).
