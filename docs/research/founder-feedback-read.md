# Where the founder signs in to read a feedback item's full text

Research for [#1499](https://github.com/markgoho/doula-cloud/issues/1499), a child of map [#1497](https://github.com/markgoho/doula-cloud/issues/1497) ("Wayfinder: a feedback mechanism for the pilot").

## Summary

No founder-facing read page exists today. `/api/internal/**` (ADR-0037) is the closest analog and it is not a sign-in surface at all: it is a caller-identity boundary meant for machines and for a human running `curl` with a minted token, never for a browser session. Two real options for a founder-only read page: (1) a new route in the Staff app (`app/`), authenticated by the same Identity Platform session every Staff member already uses, gated by a founder-identity check instead of Practice membership; (2) a direct Cloud SQL read through the Cloud Console, authenticated by the founder's own Google Cloud IAM identity, with no app code at all. Recommendation: Option 1, because it is a clickable link a private GitHub issue can hold, it stays inside the Google Cloud BAA the same way the rest of the signed-in app does, it can require a second factor the same way an Owner's session already does, and it can leave an audit row the way every other operator action in this repo does. Full comparison and reasoning below.

## What exists today

**No route in `app/` reads anything for an operator, founder or otherwise.** Every route the Staff app carries is Practice-scoped: `api/internal/staffauth/middleware.go`'s `Middleware` resolves the caller's Identity Platform token against the `staff` table, then requires a `practice_memberships` row for the `{practiceId}` in the URL before it sets `app.current_practice_id` and lets Postgres RLS enforce anything further. There is a "pre-Practice" family with no `{practiceId}` in the path (`mountSessionRoutes` in `api/internal/staffauth/mount.go`, e.g. `GET /api/staff/session`), so a route that authenticates a Staff person without scoping her to a Practice is an existing, working shape in this codebase — it is just not used today for a founder-only read.

**What exists is the `/api/internal/**` operator boundary (ADR-0037, `api/internal/internalauth/guard.go`, wired in `api/routes_internal.go`).** Nobody signs in to reach it. `internalauth.Guard.Allow` accepts either a Google-signed OIDC ID token whose `email` claim is on the `INTERNAL_OIDC_CALLERS` allowlist, or (local/e2e only) a shared `X-Internal-Secret` header that production never configures. Five endpoints sit behind it today: the outbox workers, `#443`'s page verifier, `billing.RefundHandler`, `billing.DormantPracticesHandler` (`/api/internal/billing/dormant-practices`, ADR-0046's own "internal read," listing Practices holding untouched Credits), `billing.FoundingGrantHandler`, and `staffauth.SupportClearHandler` (the MFA-recovery support-clear path). `docs/runbooks/mfa-recovery-support.md` shows exactly how a person, not a scheduled job, reaches one of these by hand: `gcloud auth print-identity-token --impersonate-service-account=internal-caller@doula-cloud.iam.gserviceaccount.com --audiences=<service base URL> --include-email`, then a `curl` carrying that token as a Bearer header. This is deliberate and recorded as deliberate: `#615`'s support-clear endpoint's own acceptance criterion is "no product surface," and the founding-grant and dormant-practices endpoints are described in `api/routes_internal.go` as "an operator endpoint... not a screen." **A browser cannot follow a link into any of this.** A GET typed into a browser's address bar carries no `Authorization` header, and nothing here mints one for a human session — only `gcloud` impersonation does, and that needs a standing IAM grant (`roles/iam.serviceAccountTokenCreator` on the target service account) that nobody but the Terraform-plan identity holds today per `docs/infrastructure.md`.

**Identity Platform on this project is provisioned for MFA and multi-tenancy but is using neither directly.** `docs/research/identity-platform-tier-and-baa.md` §1 and §5, from a live `GetConfig` call on 2026-09-01, found `"mfa": {"state": "DISABLED"}` and `"multiTenant": {}` (the capability exists, no tenant configured) at the project level. Despite that project-level flag, the Staff app already runs a working per-user TOTP enrollment and challenge flow at the application layer: `api/internal/staffauth/mfaenroll.go`'s `FinishEnrollmentHandler`, the `secondFactor` check in `middleware.go` (`if !secondFactor && (reader.Has(roleOwner) || requireMFA)`), and `docs/runbooks/mfa-recovery-support.md`'s recovery path all assume MFA is live for at least every Owner. Either the project-level `mfa.state` field does not gate the SDK's per-user `multiFactor.enroll()` call the way its name suggests, or it was flipped to `ENABLED` after the 2026-09-01 research ran and the change was never written down. This was not re-verified live in this pass; it does not change the comparison below, because both live options reuse the same mechanism Owners already use.

**Cloud SQL (`doula-cloud-pg`) is reachable by IAM alone, not by a founder-specific read screen.** `docs/infrastructure.md` records the instance as public IP with `TRUSTED_CLIENT_CERTIFICATE_REQUIRED` SSL, and its logins (`app_runtime_login`, `site_builder_login`, `postgres`) as created by hand and excluded from Terraform's ownership. The founder holds `roles/owner` on the `doula-cloud` project (`docs/infrastructure.md`, "`apply` runs from a laptop, by the one person who has `roles/owner`"), which includes Cloud SQL admin rights, but no IAM database authentication is configured — every listed login is password-based. There is no existing feedback schema to read from yet; map #1497 says its build tickets have not landed.

## Option 1: a route in the Staff app, gated to a founder identity

A new pre-Practice route, in the shape `mountSessionRoutes` already uses (`GET /api/staff/session`, no `{practiceId}` in the path): something like `GET /api/staff/feedback/{itemId}`, plus a matching `app/` page such as `/feedback/{itemId}`. It runs through the existing `authn` session verification (ADR-0004's BFF-owned `__session` cookie, minted from an Identity Platform ID token) exactly as every other Staff route does, but instead of `setPracticeAndCheckMembership`'s Practice-membership check, it runs a `FounderOnly` guard: the resolved Staff row's id (or its Identity Platform UID) checked against a single configured value, the same shape `OwnerOnly` (`api/internal/staffauth/gate.go`) already is for a Practice role, just with no Practice in the sentence at all.

**Auth mechanism:** Identity Platform email/password sign-in, the same provider every Staff member uses (ADR-0026), on the already-executed BAA (`docs/research/identity-platform-tier-and-baa.md`). Nothing new is needed from Identity Platform itself: no separate tenant, no new provider. A second factor is required unconditionally for this route the same way it already is for an Owner (`middleware.go`'s `reader.Has(roleOwner) || requireMFA` becomes, for this route, simply "always") — reusing `mfaenroll.go`'s working TOTP flow rather than building a second one. What is new is the allowlist itself: one Staff id (or UID) named in configuration, the same shape `INTERNAL_OIDC_CALLERS` already takes for the internal boundary, just naming a person's Staff row instead of a service account's email.

**What it gives:** a URL a private GitHub issue can hold and the founder can click and sign into, from any device, the same way he already signs into the product; MFA on the same footing as an Owner; and a natural place to write an audit row (`staff_auth_events` already carries this pattern for the MFA-recovery support-clear action) recording that the founder read a given item and when — the audit trail every feature in this repo is expected to answer for. It stays entirely inside `app/`/`api/`, so it never leaves the Google Cloud BAA boundary the rest of PHI-adjacent product data already sits inside.

**What it costs:** a small amount of new code — one route, one guard function, one page — none of it a new mechanism. The founder needs exactly one Staff row that belongs to no real Practice (or a Practice row that exists purely to hold it), which is a modeling decision the build ticket makes, not a blocker found here.

## Option 2: a Cloud SQL / Cloud Console read

The founder opens Cloud SQL Studio (`console.cloud.google.com/sql/instances/doula-cloud-pg/studio`) or connects with `psql` through the Cloud SQL Auth Proxy, signed in as `markgoho@gmail.com`, and runs a query by hand against whichever table holds the feedback item.

**Auth mechanism:** Google Cloud IAM. The founder's own `roles/owner` grant on the `doula-cloud` project (`docs/infrastructure.md`) covers Cloud SQL administration, but Studio and `psql` both still need a database login, and every login on the instance today is a hand-created password (`postgres`, `app_runtime_login`, `site_builder_login`; `docs/infrastructure.md`'s Cloud SQL users table) — IAM database authentication is not configured, so this is IAM to reach the Console plus a separate, unmanaged database password to reach the data, not IAM alone. No MFA, tenant, or allowlist question applies to Identity Platform here at all, because this option never touches Identity Platform — it is outside the app entirely.

**What it gives:** zero new application code, and it uses infrastructure that already exists.

**What it costs:** it fails the ticket's own requirement first. "A link inside each private GitHub issue that the founder can open" means a URL a browser GET can follow; Cloud SQL Studio has no per-row deep link — the founder would have to open Studio and hand-type a query with the item's id every time, which is not something a GitHub issue can link to at all. It also has no audit trail of its own inside the product: a raw Studio or `psql` read leaves only Cloud SQL's own connection logs (a GCP-level record, if enabled, not a Doula Cloud one), where CLAUDE.md's audit-trail expectation wants "how did this thing come to be" answerable inside the product. And it hands the founder a raw-SQL surface onto a table that likely carries other Staff and Client rows nearby, when the actual need is one formatted item.

## Option considered and ruled out: the `/api/internal/**` operator boundary

Reuse the existing operator boundary (ADR-0037) for a sixth endpoint, `GET /api/internal/feedback/{itemId}`, and have the founder mint a token the way `docs/runbooks/mfa-recovery-support.md` already documents for the MFA-recovery support-clear action.

**Auth mechanism:** a Google-signed OIDC ID token, minted by `gcloud auth print-identity-token --impersonate-service-account=<caller> --audiences=<service base URL>`, checked against `INTERNAL_OIDC_CALLERS`. No Identity Platform involvement, no MFA, no tenant, no allowlist of a person — the allowlist here is of service accounts, not humans, and the founder reaches it only by impersonating one.

**Ruled out** because it cannot be the destination of a link at all: a browser following a URL sends no `Authorization` header, and nothing in this boundary mints one for a browser session — only `gcloud` impersonation does, from a terminal, not a click. It would also need a new standing IAM grant (`roles/iam.serviceAccountTokenCreator`) for the founder on whichever service account the new endpoint accepts, which nothing today provides for this purpose. This option answers "how would a machine or a person with a terminal reach it," not "where does the founder sign in," so it does not answer this ticket's question even though it is the closest existing mechanism in the repo to an "internal read."

## Recommendation

**Option 1: a new pre-Practice Staff app route, gated to a founder identity, on the same Identity Platform session every Staff member already uses, with MFA required unconditionally.** It is the only option that is a clickable link a private GitHub issue can hold and the founder can open from any device; it stays inside the Google Cloud BAA the same way the rest of the app's PHI-adjacent data does, rather than opening a second surface (Cloud SQL) or reusing a machine-only boundary that cannot answer a browser at all; it reuses working code (`authn`'s session, `mfaenroll.go`'s TOTP flow, `staffauth`'s pre-Practice route shape and `OwnerOnly`-style gate pattern) instead of inventing a new authentication mechanism; and it can leave an audit row the way every other operator action here already does. A separate Identity Platform tenant for the founder was considered and set aside: the project is provisioned for multi-tenancy but has never configured one, and standing up a second sign-in flow for exactly one person contradicts ADR-0049's own frame — Doula Cloud is one person by design — for a problem a single allowlisted Staff id already solves.

This still leaves one modeling question for the build ticket, not this one: whether the founder's Staff row sits under a real (if minimal) Practice, or a Practice-less shape the schema does not have today. Map #1497's own "Not yet specified" section already flags the founder's read cadence as unsettled; this ticket answers only where he opens the page and what proves it is him.
