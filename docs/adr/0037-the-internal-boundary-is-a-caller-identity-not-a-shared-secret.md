# The `/api/internal/**` boundary is a caller identity, not a shared secret

[#1052](https://github.com/markgoho/doula-cloud/issues/1052) asked what actually stands between the public internet and `POST /api/internal/outboxes/drain`, and where that boundary's key is allowed to live. This records the answer. The route list itself is `api/routes_internal_guardrail_test.go`, read from the router, and the configuration is `docs/environment.md`.

**Twenty-three addresses answer the public internet, and something in the process has to tell an internal caller from anybody else.** `doula-api` carries `allUsers` → `roles/run.invoker` and cannot stop: the same service serves the app, the Stripe webhooks and the Mailgun webhook, none of which arrive with a Google credential. Cloud Run's IAM is per-service, so there is no invoker binding that admits the app and refuses the drain. That is not a gap to be closed by adding a binding — it is the reason the check has to be in the process rather than in front of it.

**So the caller presents a Google-signed OIDC ID token, and the service checks it.** Cloud Scheduler mints one for its own service account against the service's own URL as audience; Cloud Tasks does the same for each nudge it dispatches. `internalauth.Guard` verifies the signature and the audience through `idtoken.Validate`, then checks the token's `email` claim against the service accounts `INTERNAL_OIDC_CALLERS` names. Nothing durable carries a credential: the token is minted at dispatch, expires within the hour, and is bound to one audience. A half-configured service — no audience, or an empty allowlist — refuses rather than waving a valid token through, because an allowlist of nobody is not an allowlist of everybody.

**The shared secret survives only where no token can be minted.** `app/e2e/stack.ts` runs the BFF against a local Postgres with no metadata server and no Google credentials at all, so the end-to-end suite and a local run keep `X-Internal-Secret` and `NOTIFICATION_WORKER_SECRET`. Cloud Run sets neither, and an unset secret refuses the header outright — the behavior `outbox.ProcessHandler` already carried, now in one place. So production holds no shared secret for this boundary, and the fixture value in `stack.ts` guards a database that exists for the length of a test run.

## Considered and rejected

**Keeping the shared secret and treating the Scheduler job spec as a secret store.** Where things stood. The value sat in the clear in three places at once: the job spec, which `cloudscheduler.jobs.get` reads and `roles/viewer` grants; Terraform state, which `docs/infrastructure.md` accepted as its one secret because the header is a field on a job that cannot be owned without it; and — on any drift — a `terraform plan` diff, since `scheduler.tf` had to read it through `nonsensitive()` to plan clean on import. No care in the Terraform removes any of the three, because none of them is a Terraform mistake. It is also a bearer credential with no audience and no expiry, so anything that ever saw it could call every endpoint above, from anywhere, until somebody rotated it — and nothing would report that it had been seen.

**Cloud Run IAM alone, by splitting the internal routes onto a second service.** The honest way to make an invoker binding the boundary: two Cloud Run services from the same image, one public and one `run.invoker` for named service accounts only. It is a real design and a larger team might take it. It is rejected because it doubles the deployment surface — two services, two revisions per merge, two sets of environment variables and secret references to keep in step, a second Terraform resource with the same image-ownership conflict ADR-0034 had to solve once — to buy what one token check buys, on a boundary with three callers.

**Signing the requests ourselves.** An HMAC over the body with a rotating key removes the replay window without depending on Google. It also means owning key rotation, clock skew, a canonicalization rule and the code that gets all three right, for a boundary whose every caller is already a Google service holding a Google identity. Google's own token is the same guarantee with none of the code.

## Consequences

An operator calling `/api/internal/billing/refunds` or `/api/internal/staffauth/mfa-recovery/support-clear` by hand now mints a token rather than pasting a secret: `gcloud auth print-identity-token --impersonate-service-account=<caller> --audiences=<service URL>`. That is a longer command and a real cost, paid so that the runbook stops telling a person to hold a credential that never expires. `docs/runbooks/mfa-recovery-support.md` still gives the header form, and moves to this one in the same change that configures the allowlist on Cloud Run — a runbook must describe the deployment as it stands, not as it is about to stand.

The service now depends on reaching Google's certificate endpoint to admit an internal caller. `idtoken.Validate` caches the certificates, so this is a startup-shaped dependency rather than a per-request one, but a total loss of egress stops the drain as well as everything else it would already have stopped.

The allowlist is configuration, not code, and a service account renamed in Terraform without `INTERNAL_OIDC_CALLERS` following it locks the drain out silently until the next Scheduler tick fails. The Scheduler job's own last-run status is what reports that, which is the same signal #481 built the single drain job to make legible.
