# Notification sending identity is one shared domain, reply-to split by voice

The sending-identity ticket ([#216](https://github.com/markgoho/doula-cloud/issues/216), map [#213](https://github.com/markgoho/doula-cloud/issues/213)) needed to decide who a Notification looks like it came from, now that [#221](https://github.com/markgoho/doula-cloud/issues/221) ruled out naming the Practice in the `From`, subject, or body for v1 — collapsing what would otherwise have been a per-Practice sending identity into one shared identity for both Platform and Practice voice.

**One shared sending domain, no per-tenant subaccounts or subdomains.** Research into Mailgun's own subaccount model and comparable on-behalf-of senders (Calendly, DocuSign) found that reputation isolation requires a separately DNS-verified, separately-warmed domain per tenant regardless of subaccount grouping — cost with no benefit before there's real sending history showing a tenant is a deliverability problem. AWS's own SES tenant-isolation feature is documented as a retrofit once that evidence exists, not a pre-launch default. Doula Cloud has neither the sending history nor, since Practice identity is already hidden from recipients, any product reason to differentiate domains per tenant. Per-Practice custom domains (a Practice's own DNS) stay **deferred**, not ruled out — revisit only if a future Practice bake-off reopens naming the Practice in the `From`.

**`From: {Product Name} <notifications@{domain}>` for every Notification, both voices.** The literal product-name string is a placeholder pending a separate Branding decision (see the Branding map, once charted); the domain itself is #218's to provision.

**Reply-to differs by voice, on the same `From` identity.** Platform voice → `support@{domain}`, a monitored inbox a Staff member reads by hand; it never becomes a Message and never touches the product, the same class as a phone number in a footer. Practice voice (the Client portal invite included) → `noreply@{domain}`, because a Client isn't a platform user yet at invite time and inbound email is out of scope for this whole map — there is nowhere for a reply to usefully go.

**Consequence, accepted deliberately:** Nadia Haddad's loss-client journey map flagged a hard `no-reply@` as hostile at exactly the moment a grieving Client most needs a way to respond. This ADR accepts that trade-off for v1 rather than build reply-by-email to avoid it. Revisit if the Client portal surface map ([#176](https://github.com/markgoho/doula-cloud/issues/176)) surfaces real pain here.

This corrects [ADR-0009](0009-notification-is-one-term-two-voices-keyed-by-recipient.md)'s ¶3, which still states a Practice Notification "may name its own Practice" as its content-rule exception — that assumption no longer holds for v1.
