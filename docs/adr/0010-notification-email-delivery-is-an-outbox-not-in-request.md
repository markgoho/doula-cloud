# Notification email delivers via an outbox, not in-request like push

**Amended by [#481](https://github.com/markgoho/doula-cloud/issues/481): Cloud Scheduler calls one drain endpoint over the registry, not one endpoint per outbox.** This decision said "a separate internal endpoint, invoked by Cloud Scheduler on a fixed cadence", and the codebase read the second half as one job per outbox because the first half gave each outbox its own endpoint. The two do not have to match, and making them match was the whole defect. There is no Terraform in this repository, so a Scheduler job is a person at a console, and the list drifted the moment nobody was looking: #481 found ten of thirteen outboxes with no job at all, four of which were added after the ticket was filed and never provisioned. Two of those ten had no ADR-0013 nudge either, so they had no way to run at all.

**What changed is the caller, not the endpoints.** Each outbox keeps its own path — the nudge is aimed there and a person invokes it there — and `POST /api/internal/outboxes/drain` runs every registration in turn, each in its own transaction behind its own RLS door. One Cloud Scheduler job calls the drain, so a new outbox is backstopped by being registered rather than by somebody remembering the console. What this ADR asked for is unchanged: the send still survives a crash, an outage still delays delivery instead of losing it, and the cadence is still the durability half of ADR-0013.

**The cost is that thirteen outboxes now report through one job's status**, so the drain does not stop at the first failure and does not hide one. Every outbox gets its turn regardless of what the ones before it did, each failure is logged against the outbox it belongs to, and the response is `200` only when all of them succeeded and `500` naming the ones that did not — the job goes red for a broken outbox, which is what a per-outbox job used to do.

Web Push already has a working delivery precedent in this codebase: `message.notifyRecipient` calls Mailgun's counterpart, `push.Pusher`, synchronously inside the request that triggers it, and swallows any failure — logged, never surfaced as a 500, no retry (#56's decision, [ADR-0002](0002-message-transport-push-triggered-fetch.md)'s no-content-push discipline). Email delivery ([map #213](https://github.com/markgoho/doula-cloud/issues/213), [ticket #217](https://github.com/markgoho/doula-cloud/issues/217)) deliberately does **not** copy that precedent, even though it is the same shape of problem — "the BFF calls an external delivery service."

**The difference is what the channel is the only path for.** A Web Push failure costs nothing beyond the push itself: the Message it was pointing at is already durably written, and the recipient will see it next time they open the app regardless. A Client portal invite email is, until the sending-identity work on #216 changes it, the *only* way a Client's invite token reaches them — today's hand-pasted link is the fallback this map exists to replace, not a safety net underneath the new path. Swallowing a failed send the way push does would mean an invite silently going nowhere, with nothing durable behind it to fall back on.

**Notification email delivery is an outbox, not an in-request call.** `InviteHandler` writes the invite row and a pending-send row in the same database transaction; a separate internal endpoint, invoked by Cloud Scheduler on a fixed cadence, reads pending rows afterward and calls Mailgun outside any user-facing request. This buys two things a synchronous call can't: the send survives a crash between commit and delivery, and a Mailgun outage delays delivery instead of losing it. It costs one new table and one new endpoint that push's precedent didn't need.

**Retry is bounded, not infinite.** A pending row gets roughly five attempts with exponential backoff over about a day, then is dead-lettered — marked permanently failed rather than retried forever, so a bad address doesn't burn Scheduler invocations indefinitely. A dead-lettered row sets a passive status flag wherever Staff already look at invite status; nothing proactively re-notifies them, which would just be a second Notification reporting on the failure of the first.

**This resolves the idempotency interaction structurally, not by a rule bolted on.** `idempotency.Wrap` only replays a response cached below status 500. Under the outbox, `InviteHandler`'s response depends only on whether the invite and pending-send rows committed — never on Mailgun's later outcome — so a send failure can never produce the 500 that would have skipped caching. A retried request replays the original response instead of re-running `portalinvite.invite()`, which is what would otherwise rotate the invite token out from under an email already in flight.

**A Mailgun bounce or spam-complaint webhook is also built now**, in the shape of the existing Stripe webhook (`billing.PostPurchaseWebhookHandler`): signature-verified, no `staffauth.Middleware` in front of it, dedup table against replayed events. It only records the fact — a status/timestamp on the relevant row — with no decided consequence for the Client who never received their invite; that question is explicitly still open on #213's map.

**Test seam**: a `mail.Sender` interface mirrors `push.Pusher` (a real Mailgun-backed implementation, a `FakeSender` for tests), and the outbox worker exposes a directly-callable `ProcessPending(ctx, tx)` so the existing Podman-backed integration suite exercises retry and dead-letter behavior without a real scheduler or clock.

Nothing here reopens ADR-0002 or push's own delivery shape — push's failure mode is genuinely cheaper than email's, and swallow-and-log remains the right call for it. If a future Notification channel turns out to be some Client's only path the way this one is, treat that as a reason to look at this ADR's reasoning, not push's.
