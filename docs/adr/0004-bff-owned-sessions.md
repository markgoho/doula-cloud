# Session ownership moves to the BFF; Identity Platform stays behind one method

> **Widened by [#613](https://github.com/markgoho/doula-cloud/issues/613) / [#169](https://github.com/markgoho/doula-cloud/issues/169).** Identity Platform's role is no longer one method: the BFF also writes account records via the Admin SDK (`authn.AccountManager` -- `EmailVerified`, `Password`, `Email`) so it can mint its own verification/reset mail through ADR-0010's outbox instead of Identity Platform's. The identity-provider-not-architectural-constraint reasoning below is unaffected; only the interface's method count is.

#138 replaced JavaScript-readable Identity Platform credentials with an HttpOnly `__session` cookie, and built that cookie on the Firebase Admin SDK's own session-cookie feature: `SessionCookie` mints it, `VerifySessionCookieAndCheckRevoked` verifies it, `RevokeRefreshTokens` ends it everywhere. That decision quietly bundled two separate questions — who authenticates the human, and who owns the session — and answered both with "Firebase".

Answering the second question with Firebase is what produces every cost the design carries. Revocation is checked on every request as a network round trip to Identity Platform, because that is where revocation state lives. A Firebase session cookie cannot re-mint itself, so `authn.renewIfStale` has to reuse the Bearer ID token the frontend still sends — which means renewal stops working silently once #151 removes the Bearer path, and every session hard-expires at 12 hours against the acceptance criterion that an actively used session must not expire mid-shift. An "active sessions" screen is out of scope because the design deliberately keeps no session state to list.

**Sessions therefore move to Postgres**: an opaque random token, one row, the same `__session` HttpOnly cookie with the same attributes and the same 12-hour renewed-on-use lifetime. Revocation becomes a local read that folds into the transaction `authn.Begin` already opens per request. Renewal becomes an `UPDATE` needing no Bearer token, which removes the #151 ordering hazard rather than shipping it — run on the pool rather than inside the request's transaction, because renewal is about the credential and not about whatever the handler goes on to do with it: the two `SessionHandler`s only read and never commit, so riding their transaction would send the browser a fresh 12-hour `MaxAge` over a row whose expiry never moved. Ending a Staff member's sessions everywhere becomes a `DELETE` by user, and ordinary sign-out a `DELETE` by token — the same two-tier behaviour #138 specified, without `RevokeRefreshTokens`. Every acceptance criterion in #138 survives unchanged except the one describing `authn.Verifier`'s four methods, which was an implementation detail rather than a requirement.

**Identity Platform stays** as the identity provider, reduced to a single `VerifyIDToken` call at the session-exchange and bootstrap endpoints. Sign-in, the password store, and future federation are unchanged. This is not inertia: leaving would mean owning password hashing, sign-in rate limiting, and account-enumeration protection for a product holding pregnancy and birth records, and it would mean building transactional email before password reset could ship at all — `api/go.mod` has no mail dependency and `api/internal/` has no mail package, so there is nothing to build on today. Behind a one-method interface the provider is a vendor preference, not an architectural constraint, and swapping it later is a contained change.

The cost is that the BFF now owns session storage: a table, an expiry sweep, and the correctness of its own token generation. That is a smaller surface than the credential machinery it replaces, and it is the surface a solo dev can reason about locally instead of over the network.

Nothing is live and there are no users, so this is rework rather than migration. Its substance is confined to `api/internal/authn/` — the only file in `api/` importing Firebase — and `api/internal/session/`, plus a goose migration for the session table; the three bootstrap endpoints and `main.go` change only where the reduced signatures reach them. The app is unaffected: the exchange endpoint's contract is unchanged (POST a Bearer ID token, receive `Set-Cookie: __session`), so #148, #149, #150, #152, #153, and #155 neither know nor care which side mints the cookie, and can proceed in parallel.

Two tickets do depend on it. #151 removes the Bearer path, which is precisely what `renewIfStale` needs to renew; landing #151 against the current design ships the silent-expiry bug, so the Postgres session must come first. #154 is specified as revoking Identity Platform refresh tokens, which is the operation this ADR replaces with a `DELETE` by user — it should not be built twice.

**Resolved (#181):** the open question above resolves favorably. The Identity Toolkit Admin API's `GetConfig` (`GET https://identitytoolkit.googleapis.com/admin/v2/projects/doula-cloud/config`) reports `subtype: "IDENTITY_PLATFORM"` for this project — the output-only field the API distinguishes from `FIREBASE_AUTH`, i.e. this is the upgraded tier, not the free Firebase Authentication tier. Google Cloud's HIPAA-covered-products list names "Identity Platform" explicitly, and its BAA coverage is specific to that upgraded tier — Firebase Authentication alone does not carry it. Google's Identity Platform HIPAA implementation guide further restricts what may go through it: no PHI in display name, photo URL, or custom claims, and no PHI relayed from federated IdPs; `authn.go` sets none of these, so current usage is already inside those bounds. The identity-provider decision in this ADR stands.

**BAA execution confirmed (#165, `docs/research/identity-platform-tier-and-baa.md`):** the two paragraphs above establish tier and covered-products-list *eligibility*, not whether a BAA was actually in force. The Cloud Console's Legal & Compliance page records a single acceptance of the Google Cloud Platform HIPAA Business Associate Addendum, dated 2026-08-30 and made by markgoho@gmail.com, with no earlier acceptance recorded — ten days after #181 closed (2026-08-20). The lack of a formed legal entity for the business (a single-member NY LLC is planned, not yet filed) does not affect today's validity: the BAA's own text defines "Customer" as whoever accepts it and holds the underlying Services Agreement, with no incorporation requirement, and 45 CFR §160.103 defines "Person" as a natural person named separately from every organizational form — Mark Goho, as sole proprietor, is both the accepting party and the entity operating Doula Cloud today. It does mean the BAA must be re-accepted under the LLC's name once the LLC forms and becomes the operating entity, since an LLC is a distinct legal party from its member for contract purposes regardless of its federal tax treatment. See the linked research document for the full analysis.

**Provider surface widened (#169, #605, [ADR-0026](0026-two-populations-two-sign-in-methods-and-one-token-table.md), 2026-09-01):** "reduced to a single `VerifyIDToken` call" no longer holds, deliberately. ADR-0026 makes Doula Cloud — not Identity Platform — the sender of Staff verification, password-reset and email-change mail, and adopts TOTP with a recovery scheme the provider supplies nothing for, so the BFF also reads `GetUser` (for `MultiFactor.EnrolledFactors`) and writes `UpdateUser` with `EmailVerified`, `Password`, `Email` and `MFASettings`. That is the whole widened surface. **Nothing in this ADR's own subject changes**: the session is still a Postgres row, Identity Platform still mints nothing, revocation is still a local read, and every sign-in path — including the Client magic link, which has no Identity Platform account behind it at all — still ends at `authn.MintSession`. The sentence above about transactional email not existing is also out of date; #213 built it (ADR-0009 through ADR-0013), which is what made BFF-sent auth mail available to choose.
