# Terraform owns the shape, not the image, and `apply` stays off CI

[#797](https://github.com/markgoho/doula-cloud/issues/797) asked whether Doula Cloud's GCP project should be in code, and if so which parts. The boundary itself — every resource, owned or not, with its reason — is `docs/infrastructure.md`. This records the decision and what was rejected.

**What is being bought is drift detection, not repeatable provisioning.** One project, one environment, provisioned once; "stand the stack up again from nothing" is not a thing anyone here needs and should not be argued. [#481](https://github.com/markgoho/doula-cloud/issues/481) is the case that matters: `docs/environment.md` said ten Cloud Scheduler jobs existed and three did, four outboxes shipped and were never provisioned, and two of those ran not at all for three days — found only because #481's close-out went and looked at the deployed database. No mechanism could have noticed, and a document is not a mechanism. `terraform plan`, red on trunk, is one.

**Terraform owns the shape of `doula-api`; `ci.yml` owns its image.** This is the decision the whole thing turns on. `deploy-api` writes the image on every merge to trunk, so an owner that also claims the image makes `plan` permanently red, and a permanently red drift check is worse than no drift check — it trains the one person here to ignore the signal the effort exists to produce. Two consecutive real CI deploys were diffed to find out what a deploy actually moves, and only two of the differences reach a field Terraform declares: the image, and the `commit-sha` label on the revision template. A `lifecycle { ignore_changes }` block over those is the whole mechanism. It was proved, not asserted: the live service was imported into a throwaway state, planned clean, then planned again against a configuration holding a divergent image and label — red without the block, naming those fields and nothing else, and clean with it. `docs/infrastructure.md` carries the field-by-field working and the plan output; this decision does not restate it, so the two cannot drift apart. What makes the split possible is that `deploy-cloudrun` merges rather than replaces, so the environment variables and secret references the action does not name are untouched by every deploy and Terraform can own them without contending with CI for anything.

**`apply` runs from a laptop; CI only reads.** Applying this configuration requires IAM-admin-class permission, and a principal in GitHub Actions holding it could grant itself anything — through, among other things, the Workload Identity provider that the same configuration owns. For a business with one person in it that trade is not worth making, so no service account holds apply-class permission at all. CI gets a read-only account, and a red `plan` is a required check rather than an advisory annotation, for the same reason the drift check exists at all.

**Secret values, Cloud SQL passwords and Identity Platform stay out.** Terraform state is plaintext, so anything owned is as exposed as the state bucket. Owning secret *shells* catches the failure that actually happens — a secret missing, or granted to the wrong service account, which is what #743 walked by hand — while owning the *versions* would move the Stripe key, the Mailgun key and three database DSNs into a file. The same reasoning keeps `google_sql_user` out, and it is why `docs/infrastructure.md` accepts exactly one secret in state: the Scheduler jobs' `X-Internal-Secret` header, which is a field on a job that cannot be owned without it, and which rotates in two commands.

## Considered and rejected

**Doing nothing.** The status quo, and the one option #481 already disproved. Its cost is not hypothetical: four outboxes silently not running for three days, discovered by accident. Documentation was the control, and documentation drifted first.

**A homegrown "assert these resources exist" CI script.** Genuinely appealing — a Go or Bash check that lists the Scheduler jobs and fails if one is missing would have caught #481, needs no state file, no provider, no new service account, and no secrets anywhere. It is rejected for three reasons. It catches *absence* and not *shape*: a Scheduler job that exists on the wrong schedule, pointed at the wrong URL, or with a stale secret passes it, and every one of those is a real #481-shaped failure. It has to be written and extended by hand for each new resource kind, which makes it exactly the artifact that goes stale the way `docs/environment.md` did — the assertion list is another document that has to be remembered. And it can only ever report; it cannot fix, so every finding still becomes a console visit with no record of what was done. Terraform's `plan` compares every attribute of every resource for free, and its `apply` is the fix.

**OpenTofu instead of Terraform.** The fork is a drop-in replacement and its licensing is friendlier — Terraform moved to the BUSL in 2023, OpenTofu stayed MPL-2.0. The BUSL's restriction is on offering a competing product, which Doula Cloud does not do, so it costs nothing here; and #797 names Terraform, the GCP provider is published and tested by HashiCorp against Terraform, and being on the path everything is documented for is worth more to a one-person team than a license improvement that changes nothing for this use. Revisit if HashiCorp's terms change in a way that reaches this use, which is a licensing question and not an engineering one.

**Terraform owning the image too, with CI applying instead of deploying.** The other way out of the image conflict: delete the `deploy-cloudrun` step and have CI run `terraform apply -var image_tag=$GITHUB_SHA`. It removes the conflict entirely and it is what a larger team would probably do. It is rejected because it puts apply-class credentials in GitHub Actions, which is the trade the previous decision just refused, and because it makes every deploy depend on Terraform state being reachable and unlocked — turning a state-bucket problem into a deploy outage.

## Consequences

The image on `doula-api` is unowned by design and always will be, so `plan` can never tell anyone that the deployed image is wrong. That is `ci.yml`'s job and the `commit-sha` label's, and this decision deliberately keeps it there.

Nobody but the maintainer can fix drift. A red `plan` on trunk waits for a laptop, so a drifted project stays drifted until that person sits down — which is the trade `apply`-off-CI makes, and is only tolerable while the team is one person. The day it is two, revisit it.

Terraform state becomes a thing to protect that did not exist before. It holds the internal worker secret, and losing or corrupting it means re-importing every resource by hand. `docs/infrastructure.md` says where it lives and who can read it.
