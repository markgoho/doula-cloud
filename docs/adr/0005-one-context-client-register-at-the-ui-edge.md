# One bounded context; the Client register translates at the UI edge

Doula Cloud's glossary is the language of the model and of the team. It is not automatically the copy a Client reads, and the persona cast made that seam visible: Renata Alvarez and Dee Whitlock say "Engagement" and "Plan Instance" natively, because they are the domain experts. Hannah Sorensen does not. She says "my doula", "my birth plan", "my due date". Nadia Haddad's vocabulary after a stillbirth is different again, and getting it wrong there is not a copy nit. The question this settles is whether the client portal is a **second bounded context** with its own model and its own language, or **one context** whose UI translates at the last step.

**It is one context.** The discriminating test is whether the portal can hold a fact that legitimately disagrees with the staff-side model, or whether it shows less of the same fact in kinder words. `api/internal/portal/detail.go:21` answers it: `EngagementID`, `PracticeName`, and `Status` are the same Engagement, projected and cut down. There is no second model, no Client-side domain expert to talk to, and no lifecycle the portal owns. `api/internal/portal` is a read-side presentation adapter, not a context. Splitting a 77-line glossary in two, and owing a named context relationship between the halves, to serve a surface whose entire client-facing copy is four strings, would buy nothing and cost every future term two entries. There is therefore no `CONTEXT-MAP.md`.

**Translation lives in `CONTEXT.md` as a `_Client says_:` line**, beside the existing `_Avoid_:` line, rather than in a separate copy document. The register records the word one audience hears for a term the team says differently — single words and short phrases, never sentences, so it stays a glossary and does not drift into a copy deck. Keeping it in the same entry means nobody can read the domain word without also seeing the Client word; a separate file would be read by whoever was already looking for it, which is the wrong person.

The register is **binding on the client portal and advisory everywhere else**. The portal is the only Client surface, so the rule has a small and checkable edge: a test plan may assert that portal copy uses the Client word, and a mismatch is a defect. Staff screens keep using the domain words directly, because that is exactly what ubiquitous language is for.

It covers **states, not only nouns**. `Detail.Status` currently sends the raw `intake | active | postpartum | completed` enum to the portal, and status is the single word that tells a Client where she is. Each value gets **one fixed Client label, identical for every Client** — `intake` → Getting started, `active` → Ongoing, `postpartum` → Postpartum, `completed` → Care ended. Labels are deliberately not conditional on circumstance. A conditional label would let the copy layer paper over a modelling failure, and the fixed rule instead surfaces it: **if a status cannot be labelled kindly for every Client, the status set is missing a value.** Nadia is the live instance. "Care ended" is honest for `completed`, and it still says the work finished, which is the wrong thing to say to a woman whose baby died — so the conclusion that `engagement_status` lacks a terminal state for a loss is argued from this rule rather than asserted.

The boundary between this decision and a capability gap is drawn the same way. Where the model **holds** the fact but shows a poor word for it, that is copy, and the register fixes it. Where the model **cannot hold** the fact at all, the register stays silent and it becomes a `journey-gap` issue — Hannah's "my due date" against an `engagements` table with no due date, and Nadia's missing terminal state. The register never invents a word for something the product cannot represent, because copy that names a fact the model lacks is a lie the first test run would have to assert.

One noun diverges today: **Engagement**, which a Client calls **"my care"**. "My pregnancy" is rejected for the same reason the glossary already rejects Pregnancy as the domain term — it excludes postpartum-only work — and additionally because it is cruel on the loss path. Practice, Birth Plan, Contract, and Message do not diverge; the Care Plan is never shown; Visit and Plan Instance have no client-facing surface, and are recorded as such rather than given invented copy.

The cost is a second register to keep current: every future term now carries a question about what a Client calls it, and drift between the register and shipped copy is possible in a way it was not before. That drift is detectable — the portal is small and the register is binding there — and it is a much smaller cost than two glossaries kept in sync by hand.

Nothing is live and there are no users, so the portal's current copy is not migrated but simply wrong: `portal/(authenticated)/+layout.svelte` says "Choose an Engagement" to a Client. It is left in place on purpose. This effort's first test run is meant to produce evidence about the product as built, and correcting the copy inside the deciding ticket would have the client-side test plan assert against an edit made an hour earlier rather than against the product. It is captured as a `journey-gap` issue instead.
