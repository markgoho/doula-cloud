# Outbox delivery gets a Cloud Tasks nudge, not just a Scheduler poll

Amends [ADR-0010](0010-notification-email-delivery-is-an-outbox-not-in-request.md). The sentence "a separate internal endpoint, invoked by Cloud Scheduler on a fixed cadence, reads pending rows afterward" gains a second trigger: **and nudged immediately after each write**.

**Where this ADR says "the `process-*` endpoint Cloud Scheduler already calls", read "the `process-*` endpoint the drain runs".** [#481](https://github.com/markgoho/doula-cloud/issues/481) moved Cloud Scheduler off the per-outbox endpoints and onto one job that drains every outbox — see ADR-0010's amendment. Nothing about the nudge changed: it still POSTs each outbox's own path, and the cadence behind that path is still the backstop for a nudge that never arrives.

ADR-0010 chose an outbox over an in-request send for durability, and it delivered that: `process-portal-invite-outbox` and its four siblings run every five minutes regardless of whether Mailgun, or the BFF itself, is having a bad moment. What it did not solve is latency. A Client waiting on a portal invite link can wait up to five minutes for Cloud Scheduler's next tick — worse than it needs to be for a channel someone is actively watching, and polling alone was never meant to be the answer to that; only to durability.

**One shared Cloud Tasks queue, nudging all five outbox tables.** After a write commits, the write site enqueues an HTTP task calling the same `process-*` endpoint Cloud Scheduler already calls, normally delivered within seconds. Cloud Scheduler's cadence for that outbox is untouched and stays the durability backstop: if the enqueue itself fails, or the process crashes before the task fires, or Cloud Tasks itself has a bad day, the next Scheduler tick still finds the row. This is additive — the outbox tables, retry/dead-letter logic, and every `Worker.ProcessPending` are unchanged. One queue rather than five: the five `process-*` endpoints already share one shared secret (`NOTIFICATION_WORKER_SECRET`) and one `X-Internal-Secret` auth shape, so a nudge task is just "POST this URL with this header," identical five times over except which URL. A per-outbox queue would buy isolation this shared risk profile doesn't need.

**The nudge is a plain `X-Internal-Secret` HTTP task, not OIDC.** Cloud Tasks supports authenticating its own HTTP requests via a service-account OIDC token, which would let the target endpoint drop the shared secret. Reusing the secret instead means all five `process-*` endpoints need zero changes to accept a nudge alongside a Scheduler invocation, and Cloud Scheduler's own jobs already prove the shared-secret shape works in production. Revisit this if the secret's blast radius ever needs narrowing.

**The correctness constraint carries forward from ADR-0010's idempotency section, restated for the new call site.** `InviteHandler`'s response — and every other write site's — must depend only on whether its own row(s) committed, never on whether the Cloud Tasks enqueue succeeded. Nothing about `idempotency.Wrap` changed: it still only skips caching a response below status 500, so an enqueue failure surfacing as a 500 would still re-run business logic on retry (rotating `InviteHandler`'s token out from under an email already in flight, ADR-0010's original concern). The fix here is the same shape as always — enqueue after commit, log-and-swallow any enqueue failure, never surface it as an error — applied at all six call sites (`portalinvite.InviteHandler`; `billing`'s credit-spend path; the two Stripe Connect webhook branches that queue `payout_outbox`/`payment_received_outbox`; and both `sessionnotice` call sites, new-sign-in and session-revoked, since both feed the same outbox table and both deserve the same latency win).

**"After commit" is not always literal inside the handler that queued the row.** Three of the six call sites commit their own write directly — `billing.QueueOutOfCreditsNotification` (autocommitted single statement), `sessionnotice.QueueNewSignInIfDue` (its own transaction), and the two payments webhook branches (`commitAndAck`) — so those fire the nudge immediately after their own successful commit, with no indirection needed. The other two, `portalinvite.InviteHandler` and `staffauth.EndSessionsHandler`'s `sessionnotice.QueueSessionRevoked` call, run inside the request-scoped transaction `staffauth.Middleware` opens and commits only *after* the handler chain returns — by which point `idempotency.Wrap` has already written and cached the response. A nudge fired from inside the handler itself would race that later commit. `internal/tasknudge` solves this with a small per-request registry: a handler registers a closure (already bound to the outbox type) before returning, and `Middleware` runs every registered closure once its own `tx.Commit()` succeeds — never before, and never if the commit fails. The registry lives in its own package, not in `staffauth`, so `sessionnotice` (which `staffauth.EndSessionsHandler` already imports) never has to import back into `staffauth`.

**Test seam mirrors `mail.Sender`**: a `tasknudge.Enqueuer` interface, a real Cloud-Tasks-backed implementation, and a `FakeEnqueuer` injected everywhere in tests — including one that returns a configured error, so each write site's test proves the constraint above directly (the response is unchanged, and on the delayed-commit sites specifically, a retried request still replays the cached response rather than re-running the handler) rather than only exercising the happy path.
